# ChatBI 项目设计文档

> Project Design · v0.1 · 讨论稿

**版本：** v0.1（讨论稿）  
**日期：** 2026-10-22  
**项目：** ChatBI 对话式商业智能

## 文档说明

本文定义 ChatBI（对话式商业智能）项目的业务目标、产品范围、目标用户、总体流程、模块边界与阶段计划。当前版本用于项目立项和需求澄清，不代表所有产品决策均已最终确认。

- 状态标识：已定义 = 本文建议作为基线；待确认 = 需要业务方或技术负责人决策；设计建议 = 可在评审后调整。
- 产品假设：首期面向企业内部业务分析人员，允许用户使用自然语言查询已授权的数据集，并获得数据表、图表及可解释的分析结果。
## 1. 项目背景与问题

传统 BI 的查询通常依赖固定报表、字段知识、SQL 能力或数据分析团队排期。业务人员即使知道自己想问什么，也可能不知道数据在哪张表、指标如何定义、应该使用什么筛选条件。

ChatBI 希望通过自然语言作为交互入口，连接业务问题与受控的数据查询流程。但它不应被理解为“让大模型直接连接数据库并随意生成 SQL”：产品必须具备数据语义、权限控制、查询校验、结果验证和可追溯能力。

- 问题一：业务人员提出的问题与数据库字段、表结构之间存在语义鸿沟。
- 问题二：指标口径不统一，可能出现同一指标被不同团队计算出不同结果。
- 问题三：单纯返回 SQL 或数字难以帮助用户理解趋势、异常和业务含义。
- 问题四：未经治理的模型生成 SQL 可能导致错误查询、敏感数据暴露、资源消耗或结果误导。
## 2. 项目目标与成功指标

总体目标：建设一个可信、可追溯、易使用的自然语言数据分析入口，降低用户获取常规业务数据和完成初步分析的门槛。

| 目标方向 | 建议指标 | 定义 / 统计方式 | 首期目标状态 |
| --- | --- | --- | --- |
| 回答正确性 | 答案正确率 | 在经业务专家标注的标准问题集上，结果与预期口径一致的比例 | 待基线测试后确定 |
| SQL 可靠性 | SQL 执行成功率 | 已通过安全校验的查询中成功执行的比例 | 待确认 |
| 可用性 | 问题解决率 | 无需改写问题或转人工即可得到可用结果的会话比例 | 待确认 |
| 体验 | P50 / P95 响应时间 | 从提交问题到结果可见的耗时 | 待确认 |
| 安全性 | 越权查询拦截率 | 测试集中越权请求被正确拒绝的比例 | 必须通过安全验收 |
| 采用情况 | 周活跃用户 / 复用率 | 按周活跃用户与重复使用情况衡量 | 上线后建立基线 |

不要在没有基准测试的情况下直接承诺某个准确率。建议先构建覆盖常见业务问题、复杂筛选、歧义问题、权限边界和异常数据的评测集，再设定正式 KPI。

## 3. 目标用户与典型场景

| 用户角色 | 主要诉求 | 典型问题 |
| --- | --- | --- |
| 业务运营 / 销售管理 | 快速查看经营表现、发现变化 | 上周各渠道销售额分别是多少？ |
| 电商运营 | 分析商品、流量、转化与订单 | 近 30 天转化率下降最大的商品有哪些？ |
| 管理者 | 查看关键指标和趋势 | 本季度收入与上季度相比变化多少？ |
| 数据分析师 | 快速探索数据、验证假设 | 按地区和渠道拆分新客收入，并显示环比 |
| 数据管理员 | 管理数据源、语义和权限 | 哪些用户可以查询客户级明细？ |

首期应优先支持有明确数据源、明确指标口径、查询频率较高的业务域。开放式预测、自动归因和跨多个不可信来源的研究分析可作为后续能力，避免首期范围失控。

## 4. 产品范围与非目标

### 4.1 首期建议范围

- 用户登录与角色权限；数据源 / 数据集配置与连接状态展示。
- 业务语义配置：指标、维度、同义词、字段说明、关联关系和口径定义。
- 自然语言提问、歧义澄清、多轮追问与会话历史。
- 生成查询计划 / SQL，执行前进行只读、安全与权限校验。
- 展示结果表、基础图表、关键结论、查询时间和数据来源。
- 查看 SQL（按权限控制）、反馈结果、记录审计日志与错误信息。
### 4.2 首期暂不包含

- 未经审批自动修改、删除或写入业务数据库。
- 不经人工确认自动触发退款、发券、下单等业务操作。
- 保证对任意模糊问题都能给出唯一答案；必要时必须追问。
- 替代完整的数据仓库、主数据治理或专业统计建模平台。
- 无数据依据的预测、因果归因或对未来结果的确定性承诺。
## 5. 核心用户流程

建议的主流程：用户选择或进入已授权的数据域 → 输入自然语言问题 → 系统识别意图与相关指标 / 维度 → 检查语义与权限 → 必要时向用户澄清 → 生成查询计划和 SQL → 静态校验与成本保护 → 执行只读查询 → 校验返回结果 → 生成表格 / 图表 / 解释 → 保存会话与审计记录 → 用户追问或提交反馈。

关键原则：先确定问题和指标口径，再生成查询；先检查权限和安全，再执行查询；先验证结果，再生成解释。模型输出不是可信数据本身，数据库查询结果才是事实来源。

## 6. 总体模块设计

| 模块 | 职责 | 关键输出 |
| --- | --- | --- |
| 对话交互层 | 问题输入、历史会话、澄清、结果展示 | 用户问题、会话上下文 |
| 意图与语义解析 | 识别指标、维度、时间范围、筛选条件和歧义 | 结构化分析需求 |
| 语义层 / 指标目录 | 维护指标定义、字段映射、同义词、关系与口径 | 可信语义定义 |
| 查询规划与 SQL 生成 | 根据已确认语义形成查询计划和 SQL | 候选 SQL 与解释 |
| 安全与策略校验 | 权限、只读、表列白名单、行数、超时、成本限制 | 允许执行 / 拒绝 / 需澄清 |
| 查询执行层 | 连接数据源、执行受控查询、处理超时 | 原始结果集与元数据 |
| 结果校验与呈现 | 检查空值、异常规模、单位、图表类型并生成摘要 | 表格、图表、解释 |
| 治理与可观测性 | 日志、审计、反馈、评测、成本和性能监控 | 审计事件、质量指标 |

模块可以在首期以单体应用或模块化服务实现，不要求一开始拆分成微服务。应优先保证边界清晰、接口可测试和安全策略集中管理。

## 7. 数据与安全原则

- 采用最小权限原则：每个用户只能访问授权数据集、表、列及允许的行范围。
- 默认只读账号和只读事务；禁止多语句执行、DDL、DML、系统表访问及未经授权的函数调用。
- 对查询设置最大执行时间、最大返回行数、扫描量 / 成本限制和并发限制。
- 敏感字段应在语义层、查询层和结果呈现层实施一致的访问控制；不能只依赖 Prompt。
- 日志中避免记录不必要的敏感数据；定义保留期限、脱敏方式和访问权限。
- SQL、模型输入输出、用户反馈和执行结果应可关联追踪，以便复现问题。
## 8. 交付计划建议

| 阶段 | 主要交付物 | 退出条件 |
| --- | --- | --- |
| 阶段 0：澄清 | 业务域、数据源、指标清单、权限边界、标准问题集 | 关键业务口径和数据权限责任人明确 |
| 阶段 1：可用原型 | 单一数据源、少量核心指标、问答、表格 / 图表 | 端到端流程可演示，危险查询被拦截 |
| 阶段 2：MVP | 会话、语义配置、SQL 校验、审计、反馈和评测 | 通过功能、安全、正确性测试 |
| 阶段 3：试点 | 真实用户试用、错误分类、性能与成本分析 | 达到双方确认的试点指标 |
| 阶段 4：扩展 | 更多数据源、复杂分析、管理后台和运维能力 | 按实际使用反馈迭代 |

每阶段都应保留退出条件，避免仅以“页面已开发”作为完成标准。

## 9. 风险与待确认事项

| 事项 | 风险 / 影响 | 需要确认的问题 |
| --- | --- | --- |
| 数据源 | 连接方式、网络与性能不确定 | 首期连接哪种数据库？是否存在只读副本？ |
| 指标口径 | 同名指标可能定义不同 | 谁是指标口径负责人？哪些指标必须预先登记？ |
| 权限 | 越权查询可能暴露敏感信息 | 按角色、数据集、行、列分别如何授权？ |
| 模型选型 | 正确率、延迟、成本和数据出境存在差异 | 模型部署位置、预算与供应商限制是什么？ |
| 使用边界 | 用户可能把分析摘要当成确定事实 | 哪些结论需要来源、置信提示或人工复核？ |
| 规模 | 数据量和并发影响架构 | 预期用户数、问题量、数据规模和 SLA 是多少？ |

在这些事项明确前，技术实现可先采用可替换的接口和配置，不应把尚未确认的业务假设写死在代码中。

## 10. 验收原则

- 使用一组版本化的标准问题集验证正确性，包含正常、歧义、无数据、权限不足和异常问题。
- 每个回答应能追溯到数据源、执行查询、使用的指标口径和查询时间。
- 安全测试必须覆盖越权字段、越权数据集、注入式指令、危险 SQL、超时和超大结果集。
- 关键流程应可观测：请求、语义解析、SQL 校验、执行、结果校验和呈现各阶段均有状态。
- 上线前由业务负责人确认指标口径，由数据负责人确认权限，由测试负责人确认测试结果。
