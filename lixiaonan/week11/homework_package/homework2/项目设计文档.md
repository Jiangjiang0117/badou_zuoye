## 1. 项目背景

### 1.1 行业背景

大模型推动 BI 从「IT 主导的固定报表」走向「人人都是数据分析师」的对话式分析：

- **传统 BI → 敏捷 BI → 智能 BI**：主导用户从 IT 人员（1%）扩大到业务人员（90%），开发周期从数月缩短到秒级（Aloudata）。
- **行业收敛链路**：平安人寿、去哪儿、数势、腾讯游戏、Aloudata 五家实践不约而同收敛为——`意图理解 → 澄清/改写 → 知识/语义检索 → 查询生成 → 校验执行 → 可视化 → 解读/归因`。
- **企业级 Text2SQL 远未解决**：Spider 2.0（企业级真实库）上最强 Agent 框架解决率仅约 21%（Spider 1.0 为 91.2%）；BIRD 上最优模型约 70–77%，人类专家约 92%。误差主要来自**口径歧义、业务黑话、隐式时间表达、多表关联**——这决定了本项目必须"语义层优先"而非裸 Text2SQL。

### 1.2 现状与痛点（以 homework1 为起点）

homework1 已实现单轮 SQL Agent 最小闭环，但对照行业实践存在明显差距：

| 痛点 | 现状（homework1） | 行业做法（参考） |
|---|---|---|
| 歧义不澄清 | 有歧义直接生成 SQL，答案可能错 | 去哪儿「问题细化/改写 Agent」、Aloudata「反问澄清」 |
| 口径无治理 | 直接面向裸表结构 | Aloudata/数势：指标语义层固化口径 |
| 单 Agent 包打天下 | 生成/校验/汇总耦合 | 去哪儿：按单一职责拆分多 Agent |
| 无校验闭环 | 校验失败缺少自修复 | 去哪儿/腾讯：ReAct 观察-修正循环 |
| 无评估体系 | 无验证集，准确率不可知 | 去哪儿：「优先准备验证指标和验证集」 |
| 无分析能力 | 只能查数（What） | Aloudata：问数 → 归因（Why）→ 决策（How） |
| 无权限意识 | 全库可查 | 平安：指标+用户权限映射 |

### 1.3 项目定位

在 homework1 基础上，构建一个**小而完整、对标行业架构**的 ChatBI 系统：以 chinook（音乐商店）业务数据为载体，覆盖「问数 → 分析 → 报告」三级能力，验证行业共识架构在真实工程中的落地方式。

## 2. 项目目标与范围

### 2.1 项目愿景

> 用一句自然语言，人人都能完成"取数、看懂、归因、出报告"的完整分析。

### 2.2 项目目标（可衡量）

| 维度 | 目标 | 衡量方式 |
|---|---|---|
| 准确性 | 核心问数场景 SQL 执行准确率 ≥ 85% | 自建验证集（≥ 60 题，按难点分层） |
| 交互性 | 歧义问题澄清率 ≥ 90%（该反问的反问了） | 验证集歧义子集人工评审 |
| 分析能力 | 支持同比/环比/占比/TopN/归因 5 类分析问法 | 功能验收用例 |
| 体验 | 展示思考链与 SQL，全程可追溯 | 每次回答附 SQL + 口径说明 |
| 效率 | 常规问数端到端响应 ≤ 30s | 压测记录 |
| 治理 | 全部指标经语义层定义，零裸口径 | 语义层覆盖率 100% |

### 2.3 范围界定

**本期范围内（In Scope）**

- 单库（chinook.db / SQLite）多表问数；指标语义层（原子/派生/复合指标）
- 多轮对话、歧义澄清、Query 改写、指代消解
- 多 Agent 编排：改写 → 细化 → 生成 → 校验 → 执行 → 汇总 → 归因
- 可视化推荐（表格/折线/柱状）、结果解读、简单归因（时间对比 + 维度拆分）
- 术语库、Few-shot 示例库、验证集与评估脚本
- 简化版权限：指标级授权（用户-指标白名单）

**本期范围外（Out of Scope）**

- 多数据源接入、OLAP 性能加速（chinook 数据量小，无需透明加速层）
- 大行列级权限、审计平台对接（以简化白名单替代）
- 预测预警（模型预警）、深度自主研究报告（列入远期路线）
- 生产级高并发、多租户

### 2.4 目标用户与核心场景

| 用户 | 场景示例 | 核心诉求 |
|---|---|---|
| 业务运营 | "上个月哪个国家的销售额最高？" | 秒级取数，不用学 SQL |
| 管理者 | "对比本月和上月的收入，为什么下降了？" | 直接给归因结论 |
| 数据工程师 | "生成按国家统计客户数的 SQL" | SQL 可复制、口径可信 |
| 所有人 | "最近 3 个月销量 Top5 的艺人是谁？" | 排名类复合问法 |

## 3. 能力模型设计（核心）

> 七大能力域来自行业资料分析与公开检索交叉验证。每一项标注：行业依据 → 本项目落地方式 → 优先级（P0 必做 / P1 应做 / P2 可选）。

### 能力总表

| # | 能力域 | 行业依据 | 本项目落地方式 | 优先级 |
|---|---|---|---|---|
| 1 | 数据与语义层 | Aloudata NoETL 指标语义层；数势 Semantic API 三统一 | 为 chinook 定义语义模型：原子指标（销售额/订单量/客户数）+ 维度（国家/ genre /艺人/时间）+ 计算关系；模型只做"选指标+填条件" | **P0** |
| 2 | 自然语言理解与交互 | 去哪儿改写/细化 Agent；数势时间 Parser；Aloudata 反问澄清 | 意图识别 + 槽位提取（指标/维度/时间/过滤）+ 歧义反问（给可点选候选项）+ 指代消解 | **P0** |
| 3 | 查询生成与执行 | Aloudata 语义编译（100% SQL）；腾讯 SQL 校验闭环 | NL2MQL 为主（语义层填空）、NL2SQL 兜底；生成后 EXPLAIN/试运行校验，失败自动修正（最多 2 轮） | **P0** |
| 4 | 分析能力 | Aloudata 问数→归因→决策；平安解放手→脑→开药方 | 同比/环比/占比/TopN/趋势 + 时间对比归因（维度拆分定位差异来源） | **P1** |
| 5 | Agent 架构与工程 | 去哪儿单一职责多 Agent；腾讯 DFSDT 强流程 | 按职责拆分 Agent（见 §4.2），主流程固定编排 + ReAct 修正循环；展示思考链 | **P0** |
| 6 | 可信与安全 | 平安幻觉对策与指标权限；数势行/列权限 | 语义层限定候选（抑制幻觉）；指标白名单鉴权在执行前强制；回答附口径与 SQL | **P1** |
| 7 | 评估与运营 | 去哪儿"验证集先行"；平安点踩反馈闭环 | 自建分层验证集（时间/聚合/多表/歧义/排序五类各 ≥ 10 题）；badcase 记录回流知识库 | **P0** |

### 关键设计取舍（为什么这样设计）

1. **语义层优先，而非裸 Text2SQL**。Spider 2.0 上裸 Text2SQL 解决率仅 ~21%，语义层把"生成问题"变成"选择问题"，是准确率从 60–75% 提升到 85%+ 的最大杠杆（Aloudata 宣称语义层内 100% 准确生成）。
2. **多 Agent 拆分，而非单 Agent**。去哪儿实践证明单 Agent"生成+优化"会丢三落四，单一职责才稳定。
3. **固定编排为主 + ReAct 修正为辅，而非自由 ReAct**。腾讯对比表明自由 ReAct 稳定性最低、DFSDT/Workflow 最高；生产要求的是可控。
4. **澄清反问给候选项，而非开放式提问**。Aloudata/数势共同结论：降低用户负担，且歧义消解是准确率的前置闸门（去哪儿"积分第二名"案例）。
5. **权限在语义/执行层强制，而非靠 Prompt 约束**。平安经验：公司权限只到表级不够，需指标级映射；行业共识是权限必须代码强制。

## 4. 总体架构设计（概要）

> 详图与接口定义见《技术设计文档》，此处给出分层框架与主链路。

### 4.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  交互层   Web 聊天界面（对话 / 思考链 / SQL / 图表 / 点赞点踩）   │
├─────────────────────────────────────────────────────────┤
│  智能体层  多 Agent 编排                                     │
│   Query改写 → 意图理解/槽位 → 语义检索 → MQL/SQL生成           │
│      → 校验修正(ReAct) → 执行 → 汇总解读 → 归因分析            │
├─────────────────────────────────────────────────────────┤
│  知识与语义层  （项目"地图"，决定准确率上限）                     │
│   指标语义模型 │ 术语库 │ Few-shot 示例库 │ 多表关联知识 │ 验证集 │
├─────────────────────────────────────────────────────────┤
│  数据层   chinook.db (SQLite)  +  查询执行引擎               │
└─────────────────────────────────────────────────────────┘
        横切：指标白名单鉴权 · 全链路日志 · badcase 回流
```

### 4.2 Agent 职责划分（单一职责原则）

| Agent | 职责 | 输入 → 输出 |
|---|---|---|
| Rewrite Agent | 指代消解、补全省略、多轮上下文合并 | (历史对话, 当前问题) → 独立完整问题 |
| Clarify Agent | 歧义检测与反问（含候选项） | 问题 → 通过 / 澄清问题 |
| Semantic Agent | 语义检索与匹配：问题 → 指标+维度+过滤+时间（MQL） | 问题 + 语义层 → MQL |
| SQL Agent | MQL → SQL；无语义命中时裸 NL2SQL 兜底 | MQL / 问题 → SQL |
| Validate Agent | 语法校验、试运行、结果合理性检查，失败给出修正建议 | SQL → 通过 / 错误+建议 |
| Report Agent | 数据 → 自然语言结论 + 图表推荐 + 口径说明 | 结果集 → 解读 + 图表 |
| Analyze Agent（P1） | 时间对比归因：按维度拆分定位波动来源 | (两期结果, 维度) → 归因结论 |

主流程按固定顺序编排（Workflow 式，参考腾讯 DFSDT 结论）；Validate 失败时进入「SQL Agent ↔ Validate」ReAct 循环，最多 2 轮后降级为向用户澄清。

### 4.3 一次问答的主链路

```
用户提问 → 改写 → 歧义? --是--> 反问澄清(候选项) --> 用户选择 --┐
              ↓否                                              │
        语义检索(指标/维度/术语) → 生成 MQL → 生成 SQL            │
              ↓                                              │
        指标权限校验 → SQL 试运行校验 --失败--> 修正循环(≤2轮)     │
              ↓通过                                            │
        执行查询 → 结果集 → 汇总解读 + 图表推荐 ←────────────────┘
              ↓
        （P1）归因分析 → 展示思考链/SQL/口径 → 用户反馈(点赞点踩)
```

## 5. 产品形态与交互原则

- **对话为主，多模态补充**（Aloudata 误区三）：Chat 用于临时查数；SQL 面板与图表满足确定性操作；回答底部给出推荐追问（"要不要按国家拆分？"）。
- **过程透明**：每次回答展示 思考链摘要 + 生成 SQL + 指标口径（去哪儿经验：展示思考过程极大提升信任）。
- **可干预**（Human in the Loop）：用户可点选修改时间/维度/指标后重跑，不必重新提问。
- **反馈闭环**：点赞点踩 + 错误反馈入口，badcase 进入评估集（平安运营机制）。

## 7. 评估体系设计

**验证集构成**（对齐行业误差来源，按难点分层，每层 ≥ 10 题）：

| 难点类别 | 示例（chinook 场景） | 行业对应 |
|---|---|---|
| 时间推理 | "上个月""今年一季度""最近3个月" | 数势难点4（时间 Parser） |
| 聚合口径 | "累计""平均每单金额" | 数势难点2（规划穿越性） |
| 多表关联 | "买了摇滚类目的客户分布" | 去哪儿知识库 V3 |
| 歧义问题 | "第二名""最好的" | 去哪儿"积分第二名"案例 |
| 排序/复合 | "Top5""占比""同比" | 平安问法清单 |

**评估指标**：执行准确率 EX（主指标，结果集一致）→ 分层 EX（五类难点分别统计）→ 澄清率（歧义子集）→ 端到端时延。**评估方法**：自动脚本比对 + 歧义类人工评审；迭代以 badcase 回流驱动（去哪儿："上线才是项目开始"）。

## 8. 非功能性需求

| 类别 | 要求 |
|---|---|
| 性能 | 常规问数端到端 ≤ 30s；语义检索命中 ≤ 1s |
| 可靠性 | 校验失败自动修正 ≤ 2 轮；LLM 异常有降级提示，不输出错误数据 |
| 安全 | 查询仅限 SELECT（拦截 DDL/DML）；指标白名单鉴权先于执行；SQL/结果全链路留痕 |
| 可维护 | 语义模型、术语库、示例库均为配置化文件，增改知识不改代码 |
| 可扩展 | Agent 之间以标准消息结构通信，后续可替换/新增 Agent |

## 9. 风险与应对

| 风险 | 影响 | 应对措施 | 参考 |
|---|---|---|---|
| 语义模型覆盖不足，长尾问法兜底到裸 NL2SQL 后准确率下降 | 高 | 兜底 SQL 强制校验 + 低置信度时澄清；badcase 持续补语义 | Aloudata 双轨设计 |
| 模型幻觉（编造字段/口径错误） | 高 | 候选限定在语义层；结果回验；展示 SQL 供人工核对 | 平安挑战1 |
| 歧义反问过多导致体验繁琐 | 中 | 仅高歧义触发反问；候选项可点选；默认值兜底 | 数势交互原则 |
| LLM 输出不稳定 | 中 | 温度参数收紧；固定编排减少自由发挥；关键步骤结构化输出校验 | 腾讯稳定性结论 |
| 验证集标注成本 | 低 | 从已知答案的常规问法起步，随迭代扩充 | 去哪儿经验 |
