# ChatBI / Data Agent 技术设计文档

版本：1.0｜运行环境：Python 3.10+、SQLite｜课程原型仅使用 Python 标准库

## 1. 架构与职责

```text
CLI / Notebook
    ↓
SQLWorkflow（状态与最多两轮修复）
    ├─ DBParser（schema / 编译校验 / 只读执行）
    ├─ HTTPModel（真实接口）或 DemoModel（固定测试替身）
    └─ 确定性结果汇总 → JSON 轨迹 + CSV
```

使用显式状态机实现 Agent workflow，不依赖特定编排框架。模型负责选表、生成和修复；数据库引擎负责语法/字段校验及执行；汇总通过确定性代码生成，避免凭空生成数字。与课程示例相比，校验阶段使用查询计划编译，避免通过“先执行再判定合法”的方式处理模型 SQL。

## 2. 状态转移

database_parse → table_select → sql_generate → sql_validate。

校验成功进入 sql_execute，再进入 result_summary；校验或执行失败进入 sql_rewrite，再回到 sql_validate。最多初始一次加两次修复，共三次候选查询。选表输出非法、JSON 解析失败、网络异常等直接进入 failure。当前修复沿用已选表，不重新选表；遗漏中间表时应返回失败，再由用户重问或未来的重新规划节点处理。

轨迹保存阶段、候选 SQL、校验结果、错误原因、查询计划和结果。失败对象包含 status=failed 与 error；成功对象包含 question、mode、tables、sql、result、summary、trace。轨迹不包含 API 密钥。

## 3. 核心接口

|接口|契约|
|---|---|
|DBParser(path, max_rows=200, timeout=3)|路径必须存在，解析业务表|
|check_sql(sql, tables)|返回 ok、plan 或 error；编译而非执行完整查询|
|query(sql, tables)|返回 columns、rows、truncated；SQLite 错误抛出|
|model.ask(stage, payload)|select 返回 tables/reason；generate/rewrite 返回 sql|
|SQLWorkflow.run(question)|始终返回可序列化结果或失败状态（初始化错误由调用方处理）|
|save_result(result, folder, stem)|写 JSON；成功时写相同数据的 CSV|

真实模型配置使用 CHATBI_API_KEY、CHATBI_BASE_URL、CHATBI_MODEL。适配器向配置地址的 `/chat/completions` 发送 messages，要求 JSON 对象，不强制使用部分供应商不支持的结构化输出参数；返回值在本地再次验证。具体模型名称和接口支持以用户配置为准，本次未对外部服务做兼容性验证。

## 4. 数据库解析

通过 sqlite_master 获取非 sqlite_% 的表，PRAGMA table_info 获取字段及复合主键序号，PRAGMA foreign_key_list 获取外键，COUNT(*) 获取行数。不抽取客户邮箱、地址等样本。Chinook 的商品关系为 artists → albums → tracks；销售关系为 customers → invoices → invoice_items → tracks；曲风通过 tracks.GenreId 关联 genres。

COUNT(*) 对小型教学数据库可接受；生产环境应优先读取统计信息或缓存元数据，避免初始化扫描大表。当前只处理 SQLite 表，不解析视图、多数据源及跨库关联。

## 5. 执行约束

1. 文件 URI 使用 mode=ro，连接启用 query_only；不调用 executescript。
2. 入口仅接受 SELECT/WITH，再由 SQLite authorizer 实施权限检查；正则不是唯一防线。
3. authorizer 仅放行查询、递归查询、选中表读取及函数白名单；其他动作默认拒绝。
4. fetchmany 读取最多 max_rows+1，以第 201 行判断截断；这不限制聚合前扫描量。
5. progress_handler 每 1000 条虚拟机指令检查时间预算；查询预算默认 3 秒，不能声称这是操作系统级严格资源隔离。
6. 模型请求超时 60 秒；三次候选查询与多次模型调用意味着整项任务可能超过 3 秒。

现有防护不包含用户认证、列级权限、每用户行过滤、严格内存配额或独立进程隔离。选表白名单来自工作流，不能替代管理员授权；生产系统应先基于用户身份限制 schema 和只读视图，再交给模型。

## 6. 正确性与可解释性

提示词明确发票营业额与明细销售额的区别，使用稳定排序及半开日期范围。编译器能识别错误字段，但不能判断错误 JOIN、业务口径和遗漏筛选；必须以人工基准结果检验。禁止用“能执行”作为自然语言理解正确的充分证据。

汇总只列出实际返回行的前五行，并说明总返回行数及截断状态。CSV 仅导出返回行，不能称作完整数据导出。以 =、+、-、@ 开头的文本增加单引号，降低电子表格公式解释风险；数值类型保持数值。

## 7. 测试与复现

`test_sql_agent.py` 覆盖 schema、五例已知结果、修复轨迹、写库与越权拦截、结果截断、递归超时、修复上限、非法选表及未知离线问题。只读测试比较数据库 SHA-256 前后值。测试不声称覆盖真实模型网络行为。

`outputs/case_*.json` 和 CSV 为本地运行证据；notebook 展示阶段对应、正常及失败分支。应保留离线模式标识，避免将固定测试替身当作模型推理性能。

## 8. 产品化技术方案（尚未实现）

服务层增加会话、任务及审计存储；建议 API 为 POST /queries、GET /queries/{id}、POST /queries/{id}/review、POST /queries/{id}/execute、GET /queries/{id}/export。审核以 SQL 内容哈希和版本绑定，任何编辑都使审核状态失效。执行器只接受已审核且未过期版本。

会话持久化指标、时间范围、维度及用户确认记录；不简单拼接无限聊天历史。基于身份创建表/列白名单或受控视图。请求排队并限制并发，每任务独立连接；按 schema 版本和权限范围缓存元数据。模型服务仅接收获授权结构，结果默认不回传模型。日志应脱敏，并设置保留周期。

质量平台记录结果等价率、选表召回率、修复成功率、查询耗时、模型调用量和成本；基准题划分开发集与测试集，防止通过固定题模板获得虚假的模型准确率。
