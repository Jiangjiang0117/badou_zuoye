## 1. 架构与模块职责

### 1.1 部署结构

本机浏览器访问 Vue 页面，开发阶段由 Vite 将 `/api` 代理至 FastAPI；演示构建后由 FastAPI 同源提供前端静态资源。FastAPI 通过配置的模型 API 联网，通过只读连接访问本地 SQLite。所有服务默认只绑定 `127.0.0.1`，不开放局域网或公网。

| 模块 | 输入 | 输出/职责 |
| --- | --- | --- |
| Web UI | 用户问题、浏览器历史 | 请求、澄清回复、图表、表格、CSV、会话持久化 |
| ChatService / RequestService | ChatRequest | 请求状态、共享期限与预算、启动编排、最终响应 |
| AgentOrchestrator | 请求上下文、各 Agent 的结构化输出 | 按固定流程调度三个 SDK Agent，处理分支及短路 |
| IntentAgent | 问题、必要上下文、固定业务元数据 | 理解意图、条件继承、生成 QuerySpec 或澄清 |
| QueryAgent | QuerySpec、原问题、查询错误 | 调用 `query_sales`，在共享预算内修正查询 |
| AnswerAgent | 本次受限事实、图表元信息、原问题 | 选择至多 3 个可验证结论事实，不持有查询工具 |
| QueryService | QuerySpec | 业务校验、SQL 编译、SQL 校验、只读执行、结果封装 |
| MetricRegistry | 指标与维度名称 | 固定表达式、粒度与格式，不由模型改写 |
| ResultService | 执行结果 | 列元数据、图表元数据、受限结论事实、截断信息 |
| SQLite 文件 | 只读 SQL 与参数 | 四张表的数据 |
| BrowserStore | 会话、消息、返回数据 | IndexedDB 事务持久化与跨标签同步 |

三个 Agent 均为独立的 SDK Agent 实例，具有不同的 instructions、工具权限及 output_type，由同一 Python 进程中的代码串行编排；可共享同一个配置模型，不要求三个模型或独立部署。无 Redis、任务队列、向量数据库或 ORM。临时请求任务保存在后端内存，历史保存在浏览器，业务表不混入聊天记录。

### 1.2 核心设计选择

采用受约束的 Text-to-SQL：IntentAgent 产生结构化 QuerySpec，QueryAgent 调用工具从固定指标及维度编译 SQL、校验并执行，AnswerAgent 选择有依据的结论事实。用户可查看实际 SQL；不接受用户或模型任意提交可执行 SQL。此方案保留自然语言交互、多 Agent 协作与自动修正，同时将金额口径和表关联放到可测试的程序规则中。

首版支持的是明确业务模型内的查询，不是通用 SQL 工作台。若将来开放自由 SQL，必须另行评审，不通过向当前工具添加 `raw_sql` 字段实现。

## 2. 数据模型与数据生成

### 2.1 通用约定

- 主键使用稳定文本编号：客户 `C0001`、商品 `P0001`、订单 `O000001`；明细使用整数主键。
- 金额全部以人民币整数分保存与运算；API 传金额字符串或整数分，避免浮点误差。
- 日期使用 `YYYY-MM-DD` 文本，按中国时区业务日；不保存或转换含糊的本地时间字符串。
- 字段除明确说明外均为 `NOT NULL`；初始化启用外键和 CHECK 约束。
- 数据版本固定为 `ecom-demo-v1`，生成器版本为 `1`，随机种子为 `42`。版本、种子、范围、行数及校验和保存在数据库旁的 `dataset-manifest.json`，不增加第五张业务表。

### 2.2 customers：客户

| 字段 | SQLite 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| customer_id | TEXT | PRIMARY KEY | 虚构客户编号 |
| segment | TEXT | CHECK IN ('new','returning','vip') | 预置客户分层，分别展示为新客、普通老客、VIP |
| registered_date | TEXT | 合法 ISO 日期 | 注册日期，不晚于该客户首笔订单 |

分层是演示快照属性，不根据查询日期动态重算；“新客分层销售额”不能解释为“该时期首次购买客户销售额”。不保存姓名、手机号、身份证、邮箱或真实地址。

### 2.3 products：商品

| 字段 | SQLite 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| product_id | TEXT | PRIMARY KEY | 商品编号 |
| product_name | TEXT | UNIQUE | 虚构商品名，如“数码商品01” |
| category | TEXT | CHECK IN ('digital','home','apparel','food','beauty') | 数码、家居、服饰、食品、美妆 |
| list_price_cents | INTEGER | CHECK > 0 | 参考标价，不直接用于计算销售额 |

### 2.4 orders：订单

| 字段 | SQLite 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| order_id | TEXT | PRIMARY KEY | 订单编号 |
| customer_id | TEXT | REFERENCES customers(customer_id) | 客户编号 |
| order_date | TEXT | 2024-01-01～2025-12-31 | 统计归属日期 |
| status | TEXT | CHECK IN ('pending','paid','completed','cancelled') | 待付款、已付款、已完成、已取消 |
| region | TEXT | CHECK IN ('east','south','north','central','west') | 华东、华南、华北、华中、西部 |
| payable_amount_cents | INTEGER | CHECK >= 0 | 折扣后的应付金额 |
| paid_amount_cents | INTEGER | CHECK >= 0 | 实付；paid/completed 等于应付，其他状态为 0 |

首版假定有效订单全额支付，不包含退款、部分支付或取消后已付款的状态。统计时间统一用订单日期，不在部分问题中悄悄切换支付日期。

### 2.5 order_items：订单明细

| 字段 | SQLite 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| item_id | INTEGER | PRIMARY KEY | 明细编号 |
| order_id | TEXT | REFERENCES orders(order_id) | 所属订单 |
| product_id | TEXT | REFERENCES products(product_id) | 商品编号 |
| quantity | INTEGER | CHECK > 0 | 商品数量 |
| unit_price_cents | INTEGER | CHECK > 0 | 商品成交单价，未扣该行分摊的订单折扣 |
| discount_amount_cents | INTEGER | CHECK >= 0 | 该行分摊折扣，不能超过数量×成交单价 |
| payable_amount_cents | INTEGER | CHECK >= 0 | 数量×成交单价－该行折扣 |
| paid_amount_cents | INTEGER | CHECK >= 0 | 该行实付；有效订单等于应付，否则 0 |

`UNIQUE(order_id, product_id)` 保证同单同商品只出现一次；每单 1～5 条明细。同一商品不同订单可有不同成交单价。每张订单必须满足：

1. 订单应付＝其明细应付之和。
2. 订单实付＝其明细实付之和。
3. 有效订单应付＝实付且大于零；未支付或取消订单实付＝0。
4. 明细折扣非负且不超过该行原金额。

跨行金额守恒由生成器事务和初始化验收检查保证，不能只依赖单行 CHECK。

### 2.6 索引与关联

| 索引 | 用途 |
| --- | --- |
| orders(order_date, status) | 时间及有效状态筛选 |
| orders(region, order_date) | 地区趋势 |
| orders(customer_id) | 客户分层关联 |
| order_items(order_id, product_id) UNIQUE | 订单明细关联及去重 |
| order_items(product_id, order_id) | 商品销售查询 |
| products(category) | 品类过滤 |

关联路径固定为 `customers → orders → order_items → products`，分别一对多、一对多、多对一。SQL 编译器按需求选最短必要路径，不为展示商品信息而在订单汇总中无条件加入明细。

### 2.7 固定数据生成规则

1. 离线创建临时 SQLite 文件，启用外键，在一个事务中生成 1,000 客户、100 商品、5,000 订单及对应明细。
2. 商品平均分到 5 个品类，每类 20 个；客户分层按固定概率生成，注册日期不晚于 2024-01-01。
3. 年份权重 2024:2025＝45:55；月份权重为 `[1,1,1,1,1,1.2,1,1,1,1.1,1.5,1.4]`；地区权重华东 35%、华南 25%、华北 18%、华中 12%、西部 10%。这些权重用于采样，不要求实测分布精确等于权重。
4. 状态权重待付款 10%、已付款 25%、已完成 55%、已取消 10%；每单 1～5 个不同商品，每条数量 1～3，金额在品类参考范围内生成，折扣全用整数分。
5. 先确定整单折扣，再按各明细原金额比例向下取整分摊，剩余分按 item_id 顺序分配，确保总折扣和实付严格守恒。
6. 固定保留覆盖样本：每个月有有效订单、五地区均有成交、多明细订单、重复购买客户、待付款和取消记录。通过预留生成槽位完成，不在生成结束后额外追加订单。
7. 完成完整性、行数、金额、范围检查后，输出逻辑数据校验和与 manifest，替换目标文件；服务运行中不允许重建。重新生成必须显式 `--force`，先停服务并保留旧数据。

重现性以有序导出逻辑记录的 SHA-256 为准，不依赖 SQLite 文件字节完全一致。默认数据覆盖每月成交；零分母或缺成交测试通过独立测试数据库构造。生成规则与种子共同决定数据，修改规则必须提升版本。

## 3. 指标、时间与语义模型

### 3.1 指标注册表

| 代码 | 中文名 | 订单粒度表达式 | 明细粒度表达式 |
| --- | --- | --- | --- |
| sales_amount | 销售额 | SUM(o.paid_amount_cents) | SUM(i.paid_amount_cents) |
| order_count | 订单量 | COUNT(DISTINCT o.order_id) | COUNT(DISTINCT o.order_id) |
| average_order_value | 客单价 | 销售额 / 订单量 | 匹配明细销售额 / 匹配订单量 |
| sales_quantity | 销售数量 | 需要转明细粒度 | SUM(i.quantity) |

所有销售指标强制有效状态过滤 `o.status IN ('paid','completed')`。金额 SUM 无记录用 0，订单量无记录为 0；客单价分母为零返回 null。状态筛选若与有效状态冲突，汇总任务拒绝混用并解释，允许改查对应状态明细。

查询包含商品/品类维度或过滤、销售数量、商品明细时进入明细粒度。多指标混合时统一到相同基础行集，但订单量始终去重；不得在明细行上 SUM 订单实付。客户分层 JOIN 不改变订单或明细基数。

可按地区、品类、商品、客户分层及日/月/年分组，最多两维。商品分组同时保留编号和名称；标识符用于稳定排序和条件消歧。首版不支持任意公式、HAVING 自定义表达式、窗口函数、用户自定义 JOIN 和维度以外的自由字段查询。

### 3.2 金额、比率与显示

- 底层销售额以整数分求和，API 用精确十进制字符串表示元，例如 `"123.45"`，不通过 float 中转。
- 客单价、差额和增长率使用 Python Decimal，最终显示时 ROUND_HALF_UP 保留两位。
- 结论和图表使用服务端同一份显示数值；ECharts 可将显示字符串转换为绘图数值，但 tooltip 继续使用原精确字符串。
- 比较增长率基于未提前舍入的指标值计算；null 附带 `missing_baseline` 或 `zero_denominator` 等原因。
- 不支持的“平均值”必须澄清到已定义客单价等指标；不开放对编号等任意列求平均。

### 3.3 时间解析

固定锚点 `2025-12-31`，数据区间 `[2024-01-01, 2026-01-01)`。相对时间先由模型识别成规范令牌，再由后端用标准库日期规则解析：`today`、`this_year`、`this_month`、`previous_month`、`last_n_days`；“最近一个月”固定映射 this_month，last_n_days 包含锚点当天。

QuerySpec 日期允许两种互斥形式：`{kind:"absolute",start:"2025-01-01",end_exclusive:"2026-01-01"}` 或 `{kind:"relative",preset:"this_month"}`。执行前统一成绝对区间。范围部分相交则取交集并给 warning；完整超范围返回 out_of_scope；比较对比期不能通过取交集掩盖覆盖缺失。

月比较使用完整自然月，年比较使用完整自然年；当前周期在数据范围内且完整覆盖才计算。同比将月/年向前推一年；环比按选定粒度前推一月/一年。时间序列每个桶独立求其基准周期，不能简单用返回行的 LAG 替代缺失月份。任意不完整周期的同比环比先澄清，最多两个分组维度且比较任务只支持时间维度或无分组，其他组合返回不支持说明。

趋势桶由后端补齐，销售额、订单量、数量为空桶补 0，客单价补 null。范围无订单的标量汇总仍是成功的一行零值结果；明细或分类分组零行则为 empty。

## 4. QuerySpec、SQL 生成与执行

### 4.1 QuerySpec 契约

以下为结构示例，不是可自由扩展的 SQL DSL：

```json
{
  "task": "aggregate",
  "metrics": ["sales_amount", "order_count"],
  "date": {"kind": "absolute", "start": "2025-01-01", "end_exclusive": "2026-01-01"},
  "dimensions": ["region"],
  "filters": {"regions": ["east"], "categories": [], "product_ids": [], "segments": []},
  "comparison": [],
  "detail_level": null,
  "detail_statuses": [],
  "sort": {"field": "sales_amount", "direction": "desc"},
  "limit": 10
}
```

| 字段 | 约束 |
| --- | --- |
| task | aggregate、ranking、trend、comparison、detail 之一 |
| metrics | 最多 4 个，来自注册表；detail 为空数组 |
| date | 日期结构二选一，执行后必须规范成合法左闭右开区间 |
| dimensions | 最多 2 个，region/category/product/segment/day/month/year；时间维度最多一个 |
| filters | 固定键，值为有限枚举或已有编号列表，单个列表最多 100 项 |
| comparison | comparison 任务必填 yoy/mom，可同时选择；其他任务为空 |
| detail_level | detail 必填 order/item，其余为 null |
| detail_statuses | 仅明细可用；空数组默认有效状态，支持四种已知状态 |
| sort | null 或指标/所选维度及 asc/desc；trend 强制按时间升序，明细默认日期与编号升序 |
| limit | 1～1,000，ranking 默认 10，其余默认 1,000；客户端不能提升服务端上限 |

Pydantic 严格校验，拒绝未知键、任意表达式、非法字段和隐式类型转换。已知但不存在的商品编号可用于空结果查询；商品名称有多个候选时先消歧。复杂超出首版语法的业务问题返回 out_of_scope，不伪装成空数据。

### 4.2 编译步骤

1. 合并并校验继承条件；确定缺失项，必要时停止并澄清。
2. 解析日期、范围及粒度；确定订单或明细基础行集。
3. 根据固定映射加入必要表；选择固定指标表达式和参数占位符。
4. 编译 WHERE、GROUP BY、ORDER BY，业务限制先于返回行数限制。
5. 对已聚合、排序后的结果附加返回限制；补齐趋势与比较结果后再次统一执行输出上限。
6. SQL AST 校验后只读执行，最多 fetch 1,001 行探测截断；返回至多 1,000 行。对于用户要求前 N 且 N<1,000，取 N+1 行探测，保留 N 行，元信息同时说明用户 top N 与是否还有匹配项。图表和事实生成仅使用保留后的数据，探测行随即丢弃。
7. 比较任务可能生成 current/baseline 多条受控 SQL，同一候选内合并执行；返回 SQL 列表及各自参数，不将查询条数当成修正次数。

Top N 的 `selection_limit` 表示用户主动选择的范围，`truncated` 只表示达到硬上限 1,000 后仍有更多数据；`has_more` 可用于说明 Top N 之外还有匹配项，不把正常前 10 名展示成系统截断。

示例：订单级地区销售汇总的 SQL 形态：

```sql
SELECT o.region AS region,
       COALESCE(SUM(o.paid_amount_cents), 0) AS sales_amount_cents,
       COUNT(DISTINCT o.order_id) AS order_count
FROM orders AS o
WHERE o.status IN ('paid', 'completed')
  AND o.order_date >= :date_start
  AND o.order_date < :date_end
GROUP BY o.region
ORDER BY sales_amount_cents DESC, o.region ASC
LIMIT :fetch_limit;
```

固定 SQL 字面量由程序提供，用户值一律绑定；表名、列名、排序和别名来自注册表，不能用参数拼接替代标识符校验。按商品汇总改为 `SUM(i.paid_amount_cents)`，不使用 `SUM(o.paid_amount_cents)`。

### 4.3 只读校验与资源控制

采用 `sqlglot` 解析 SQLite AST，校验单条 SELECT/只读 WITH SELECT、四表白名单及固定函数/列引用；拒绝 DDL、DML、PRAGMA、ATTACH、事务语句、递归 CTE、系统表、未知函数及多语句。AST 不能替代数据库权限。

运行时使用标准库 sqlite3：URI `mode=ro`；连接初始化设置 query_only；set_authorizer 再次限制写、附加数据库、危险函数与系统对象；关闭扩展加载。不将只读 PRAGMA 当作模型可调用工具。数据库操作在工作线程中使用该线程创建的连接，避免事件循环阻塞和跨线程误用。[SQLite URI 只读模式](https://www.sqlite.org/uri.html)、[Python sqlite3 控制接口](https://docs.python.org/3.11/library/sqlite3.html)

SQLite 查询阶段默认总预算 5 秒，使用 progress handler 检查单调时钟及取消标记，必要时 interrupt；建立连接的锁等待也必须小于剩余期限。超时、资源拒绝、安全错误是终止错误，不用重试来延长执行。

## 5. Agent 编排与模型接入

### 5.1 模型配置与 SDK 边界

使用 Python OpenAI Agents SDK 的 Agent/Runner 执行本地编排，模型端点、密钥、模型名由后端注入；兼容 Chat Completions 的服务通过 SDK 对应的模型适配路径接入，不假设仅修改 URL 就兼容所有能力。正式实现时锁定并记录通过预检的 SDK、模型及适配路径。[官方模型与供应商说明](https://developers.openai.com/api/docs/guides/agents/models)

接入预检必须实际验证：认证和请求成功；工具参数能正确返回；一次工具调用后能继续回答；本项目结构化结果可校验；错误、超时与关闭 tracing 生效。结构化输出可使用服务原生结构能力或工具参数加 Pydantic 校验，必须通过相同契约测试。预检失败时不将该服务标成已支持。

不指定供应商和模型默认值，不在设计阶段编造模型延迟、价格或正确率。一个模型服务不通过时由部署者修复配置或选择能通过的模型，不自动切换到另一个付费服务。

### 5.2 三个 Agent 的职责和权限

| Agent | 输入 | 输出 | 工具权限 |
| --- | --- | --- | --- |
| IntentAgent | 当前问题、必要历史、上次合法条件、待澄清项、业务元数据 | IntentDecision：ready/clarify/unsupported/refused | 无数据库及外部工具 |
| QueryAgent | 已校验 QuerySpec、原始问题、固定指标说明、错误与剩余预算 | QueryDecision；真实结果由工具写入 RequestContext | 仅 query_sales(query_spec) |
| AnswerAgent | 原始问题、最终筛选、有限结果事实、fact_id 与限制信息 | AnswerDecision：claims | 无数据库及外部工具 |

每个 Agent 使用独立 instructions 和结构化 output_type；后端通过共享模型配置建立三个实例。IntentAgent 说明中包括四表语义、指标定义、日期基准、支持范围和继承规则；QueryAgent 明确已确定业务条件不可改变；AnswerAgent 只能引用允许事实。只向 IntentAgent 传最近最多 6 轮必要文本（总计最多 8,000 字符），不发送旧结果表或历史 SQL；后两个 Agent 仅接收完成各自任务必需的交接数据。

query_sales 是 SDK function tool，定义在本地 `agent/tools.py`，调用 `services/query_service.py`；数据库、SQL 编译、校验和结果保存均在服务层完成。无 shell、文件、浏览器、任意 SQL 或外部搜索工具。元数据直接注入说明，无需为四表增加检索基础设施。

| 工具执行结果 | 返回给 QueryAgent | 服务端保存 |
| --- | --- | --- |
| 可修正失败 | 安全错误代码、可纠正字段、剩余次数 | 候选和共享计数，不泄漏堆栈 |
| 查询成功 | result_ref、行数、截断标识，要求结束查询阶段 | 至多 1,000 行数据、SQL、参数、规范条件 |
| 空结果 | empty 标识和条件 | 成功执行依据，无虚构数值 |
| 拒绝/超时 | 终止标识和原因 | 终止状态 |

每次请求最多一个成功的业务查询候选。成功后再次调用查询工具立即拒绝；不能通过切换 Agent、新建 Runner 或重新请求工具绕开限制。比较所需的多条 SQL 由同一工具调用内部完成，不增加数据库访问角色。

### 5.3 编排流程、交接数据与结构化输出

采用代码控制的串行编排：`agent/orchestrator.py` 分别通过 SDK Runner 运行 IntentAgent、QueryAgent、AnswerAgent，并校验各自输出。编排器是普通 Python 控制逻辑，不是第四个需要模型调用的 Agent。各 Agent 不自主更换后继节点或启动另一 Agent；业务流程与终态由应用控制。SDK 提供不同职责 Agent、工具与交接能力，本项目基于稳定的三个阶段显式传递数据。[官方多 Agent 编排说明](https://developers.openai.com/api/docs/guides/agents/orchestration)

```text
ChatService 创建共享 RequestContext
  → IntentAgent
      clarify / unsupported / refused → 返回对应终态
      ready → 服务层验证意图与条件
        → QueryAgent → query_sales → SQL 编译、校验、只读执行
            可修正失败 → QueryAgent 修正 → 同一 query_sales（最多 2 次修正）
            空结果 / 拒绝 / 最终失败 → 直接返回，不调用 AnswerAgent
            成功 → ResultService 构建事实与图表元信息
              → AnswerAgent 选择事实 → 后端校验并渲染结论 → success
              → 总结失败或期限到达 → partial，保留数据
```

| 契约 | 判别字段与内容 | 交接/校验规则 |
| --- | --- | --- |
| IntentDecision | action=ready，query_spec；或 action=clarify，question/missing_fields/options；或 unsupported/refused，reason_code/suggestion | Pydantic 判别联合；ready 才进入查询；澄清时无 SQL |
| QueryDecision | action=executed，result_ref；或 action=clarify/unsupported/refused，相关原因及补充项 | executed 必须存在本次工具真实结果；QueryAgent 不能自行生成结果行 |
| AnswerDecision | claims：fact_id 与允许的表达风格，最多 3 项 | 只能引用 ResultService 生成的本次事实编号 |
| RequestContext | request_id、deadline、已批准意图、候选计数、SQL 与数据、事实、阶段 | 由应用创建；引用同一对象，不由各 Agent 复制或重新初始化 |

IntentAgent 的 ready 输出先经业务校验。查询中若发现关键歧义，且还没有成功执行，则返回澄清；需要改变已批准业务意图时不能自行修正后继续查询。所有模型输出均为不可信输入，QueryDecision.executed 不代表执行成功，工具写入的 RequestContext 才是依据。

查询工具成功后，ResultService 产生标量指标、已返回排行首项、趋势最大/最小月份及可计算比较值等事实。AnswerAgent 仅接收有界事实、必要样本和范围，不接收数据库连接或查询工具。后端用固定中文模板和事实值渲染句子，禁止添加自由因果解释或自行数值运算。无效 fact_id、输出格式错误或 AnswerAgent 故障均按总结失败降级。

若 QueryAgent 已把成功数据写入上下文，但它最后的格式输出失败或达到轮次上限，编排器仍可直接依据真实数据进入 AnswerAgent；若期限或全局预算已耗尽则立即返回 partial。不得为了取得一个“成功”声明重新执行 SQL。该方式不宣称能够可靠核验任意自由文本分析。

### 5.4 共享预算、修正与总期限

SDK 提供各 Agent 内部的模型/工具循环，应用层负责跨 Agent 的业务计数与数据权限；不能把 SDK 轮数当成 SQL 修正次数。[官方运行机制](https://developers.openai.com/api/docs/guides/agents/running-agents)

| 控制项 | 默认值 | 解释 |
| --- | --- | --- |
| QUERY_MAX_REPAIRS | 2 | 整个请求第一次候选之后最多修正 2 次 |
| 每请求候选上限 | 3 | 查询工具的参数、编译或执行可修正失败都消耗候选；更换 Agent 不重置 |
| AGENT_MAX_TURNS | 8 | 每个 Runner 的 SDK 轮次上限，不代表每个 Agent 都会用满 |
| MODEL_MAX_TURNS_TOTAL | 12 | 三个 Agent 累计模型轮次上限，调用前由共享预算检查 |
| REQUEST_TIMEOUT_SECONDS | 60 | 从 POST 接受到最终状态，三个阶段共用一个期限 |
| DB_TIMEOUT_SECONDS | 5 | 全部数据库执行的累计预算，同时受请求剩余时间约束 |
| MODEL_CALL_TIMEOUT_SECONDS | 20 | 单次模型调用上限，不超过请求剩余时间 |

每个请求创建唯一 RequestContext：deadline、active_agent、model_turns_used、attempt_count、repair_count、db_elapsed、last_error、query_result、validated_spec。上下文由 ChatService 创建并传给编排器和三个 Agent；工具修改计数和执行结果，不能接受模型传入的“剩余次数”。关闭并行查询工具执行；同一请求入口锁确保即便模型发出多个工具调用也串行检查预算。

可修正错误包括结构字段不合法、可纠正的编译/SQLite 执行错误；QueryAgent 根据安全错误重新生成 QuerySpec 并重编译 SQL，不能直传模型改写 SQL。修正保留已批准的指标、时间与业务筛选，不通过缩小范围、改指标或放宽权限“修好”错误；需要改变业务含义时停止并澄清。编译器自身缺陷须由开发者修复。IntentAgent 和 AnswerAgent 输出格式失败不消耗 SQL 修正预算，也不能触发查询重跑。

可修正查询失败回传同一次 QueryAgent 运行继续处理；第三候选失败立即终止，禁止第四候选，不再调用 AnswerAgent。安全拒绝、业务不支持、配置故障、资源超时和外部 API 错误均不自动 SQL 修正。全局模型预算耗尽时，有已成功数据则 partial，无数据则 failed，并使用 AGENT_TURN_LIMIT。

总期限使用单调时钟，所有 Agent/Runner、模型和工具共享 deadline，不在交接或修正时重置。关闭模型客户端内建自动重试；认证、限流等错误直接返回可解释状态。期限到达后停止后继 Agent，取消模型活动并中断 SQLite；已有成功查询快照返回 partial，否则 timeout。后台清理有界等待，不继续消耗模型调用。三个 Agent 可增加模型轮次和时延，必须在实际联调中验证 60 秒预算，不能把阶段超时相加当作新的总期限。

## 6. 结果、图表和错误契约

### 6.1 列与图表

结果列统一包含 `key`、`label`、`type`、`unit`、`nullable`，type 为 string/integer/decimal/date/percent。decimal、percent 值使用字符串，空值用 JSON null，不传 NaN/Infinity。金额表格按元显示，底层校验按分进行。

聚合列 key 使用指标代码，维度列使用 region/category/segment/date_bucket；商品维度展开为 product_id、product_name。比较结果按指标生成 `{metric}_current`，以及所选 yoy/mom 的 `{metric}_{kind}_baseline`、`{metric}_{kind}_difference`、`{metric}_{kind}_growth_rate`、`{metric}_{kind}_reason`。单月/单年比较返回一行，序列比较每个时间桶一行；单独一个周期时按日期边界确定月或年，跨多周期必须明确 month/year 维度。原因字段 null 表示可计算，否则为 missing_baseline 或 zero_denominator。每列 label 与 unit 必须随响应提供，前端不自行猜列名。

chart 为后端生成的受限描述：type、x_key、y_keys、series_key、display_limit；type 为 metric/line/bar/table，key 必须存在于返回列。前端不能接收可执行 ECharts option、HTML formatter 或 URL。两维普通分组默认表格；折线或柱状适用于单时间/分类维度；图表最多展示 20 项且提示。

### 6.3 状态与可空规则

| status | result | evidence | context_update | 解释 |
| --- | --- | --- | --- | --- |
| success | 有数据 | 成功 SQL | 更新条件 | 完整成功 |
| partial | 有数据 | 成功 SQL | 更新条件 | summary.status=unavailable，数据成功 |
| empty | 零行列结构 | 成功 SQL | 更新合法条件 | 无匹配明细/分类数据 |
| clarification | null | 无执行查询 | 更新 pending，不替换 last_spec | 用户需补充 |
| out_of_scope | null | 无执行查询 | 不更新 | 超出数据或能力范围 |
| rejected | null | 无执行查询 | 不更新 | 安全或只读拒绝 |
| failed | null | 可含安全失败候选，标明未成功 | 不更新 | 不可恢复失败 |
| timeout | null | 可含已尝试安全查询 | 不更新 | 尚无成功数据时到期 |

最终 response.status 由应用决定，不能直接相信 Agent 声称成功。partial 对应错误置于 warnings 和 summary，不把顶层 error 渲染为整次查询失败。empty 用固定“当前条件没有匹配记录”，不调用模型继续总结。

### 6.4 错误代码

| code | 常见状态 | 自动 SQL 修正 | 用户建议 |
| --- | --- | --- | --- |
| INVALID_QUERY_SPEC | 工具内部 / failed | 可，受总次数限制 | 调整条件或简化问题 |
| QUERY_COMPILE_ERROR / QUERY_EXECUTION_ERROR | 工具内部 / failed | 可，限安全且可纠正错误 | 调整查询范围，附请求编号 |
| READ_ONLY_VIOLATION / UNSAFE_QUERY | rejected | 否 | 仅支持查询 |
| UNSUPPORTED_METRIC / UNSUPPORTED_QUERY | out_of_scope | 否 | 使用支持指标或查询形态 |
| DATE_OUT_OF_RANGE | out_of_scope | 否 | 使用已覆盖日期 |
| MODEL_AUTH_ERROR / MODEL_RATE_LIMIT / MODEL_UNAVAILABLE | failed | 否 | 检查后端配置或稍后重试 |
| MODEL_OUTPUT_INVALID / AGENT_TURN_LIMIT | failed 或 partial | 否 | 有数据则保留，否则重试 |
| QUERY_TIMEOUT / REQUEST_TIMEOUT | timeout 或 partial | 否 | 缩小范围或手动重试 |
| RESULT_TOO_LARGE | failed | 否 | 减少维度或返回行数 |
| DATASET_UNAVAILABLE / DATASET_MISMATCH | failed | 否 | 检查本地数据版本 |

前端不展示 Python/SQLite 堆栈、模型 HTTP 原始错误、密钥及机器绝对路径。开发日志默认也只记录安全错误类别，详细诊断需开发者主动在受控环境开启。

## 7. HTTP 接口契约

### 7.1 请求生命周期与阶段获取

为展示真实阶段且不引入逐字流，采用短 POST 创建内存任务、GET 轮询状态。轮询不调用模型。首版单进程，最多 4 个同时运行的任务，超出返回 503，接受时即起算 60 秒，不设置隐形排队。

| 方法与路径 | 输入 | 输出 | HTTP |
| --- | --- | --- | --- |
| GET /api/health | 无 | 进程存活、数据可读标记 | 200；数据异常仍通过元信息说明 |
| GET /api/meta | 无 | 数据版本、范围、锚点、指标/维度、模型配置/预检状态、限制、API 版本 | 200 / 503 |
| POST /api/chat/requests | ChatRequest | request_id、state、phase、created_at | 202；格式 422；来源 403；繁忙 503 |
| GET /api/chat/requests/{request_id} | UUID | state、phase、revision、progress、response | 200；不存在或已过期 404 |

不提供通用 SQL、数据库文件下载、后端聊天历史、远程模型配置或 CSV 服务端接口。完成数据在响应中已返回，CSV 由前端生成。

`/api/meta` 的固定字段包括 api_version、dataset（id、start、end_inclusive、anchor_date、seed、generator_version、counts）、metrics（key、label、unit、definition）、dimensions（key、label、可用枚举代码与中文标签）、limits（max_rows、page_size、request_timeout_seconds）以及 model（configured、preflight_status、safe_message）。preflight_status 为 not_configured/checking/passed/failed；应用启动后执行有界模型预检，在 passed 前禁止创建查询任务，返回 503 和安全原因。`python main.py check-model` 调用同一套预检逻辑，验证三个 Agent 的结构契约及 QueryAgent 的工具循环，不另设一套判断标准。

### 7.2 ChatRequest

```json
{
  "conversation_id": "客户端生成的 UUID",
  "dataset_id": "ecom-demo-v1",
  "message": "2025 年销售额是多少",
  "history": [],
  "context": {
    "last_spec": null,
    "pending_clarification": null
  }
}
```

上例为新会话的首次提问，last_spec 为 null；实际追问应携带上次成功的完整 last_spec。conversation_id 只作关联，无用户身份/权限含义。history 仅允许 user/assistant 纯文本，不接受 system、工具结果或模型指令字段；最多 12 条、总 8,000 字符。整请求体最多 32 KiB，超出 413；message 1～2,000 字符。数据版本不匹配返回 409，要求新会话。

pending_clarification 包含 original_message、draft_spec、missing_fields、question、options；后端把它视为不可信业务数据重新校验。未经执行成功的 draft_spec 不替代 last_spec。

### 7.3 任务状态响应

```json
{
  "request_id": "uuid",
  "state": "running",
  "phase": "repairing",
  "revision": 4,
  "progress": {"active_agent": "QueryAgent", "model_turns_used": 3, "attempt_count": 2, "repair_count": 1, "elapsed_ms": 8000},
  "response": null
}
```

state 为 running/completed；phase 为 understanding/querying/repairing/summarizing/done。completed 时 response 为第 6 章最终响应，phase=done；不要将 transport completed 等同业务 success。active_agent 为 IntentAgent/QueryAgent/AnswerAgent 或 null；model_turns_used 为跨 Agent 累计模型轮次。阶段来源于编排器进入阶段、SDK 钩子和工具回调，revision 每次状态变更递增。切换 Agent 时保留已有候选计数及耗时。

前端每 1 秒轮询，后台标签可降至 3 秒。总期限由后端控制，浏览器超过 65 秒仍无法取得终态时显示通信中断，并允许再次读取状态，不把未知状态冒充查询失败。任务完成后保留 10 分钟供恢复读取，内存最多保留 100 个任务；满额时仅清理最旧的已完成任务，禁止驱逐运行任务。请求编号为不可预测 UUID，只存在本机访问边界，不提供任务列表。

HTTP 标准错误体统一为 `{error:{code,message,retryable},request_id}`；无已创建任务时 request_id 可为 null。业务错误置于任务终态 response，不用轮询的 HTTP 500 表达“这个问题不支持”。所有接口和静态敏感响应使用 Cache-Control: no-store。

## 8. 信息边界、只读与日志

### 8.1 外发数据

模型可接收当前问题、必要对话、固定表结构/业务指标、工具安全错误、有限查询证据。不发送 SQLite 文件、环境文件、密钥、完整历史或所有结果明细。

提交给 AnswerAgent 的证据包最多展示 20 行样本、合计至多 16,000 字符，并附本次已返回行的确定性事实及范围标记。超出时只减少样本，不截断 SQL 执行或丢弃前端结果。QueryAgent 仅接收查询引用、状态及修正所需信息，不重复接收整份证据。结论只能使用事实表；样本不能概括全量。完整 1,000 行保存在请求任务内供浏览器返回，不默认全部送模型。

所有数据是虚构编号和属性；模型服务自身的数据处理政策由具体供应商决定，文档不宣称“零留存”。默认关闭 SDK tracing 及其导出器；实现时验证使用的 SDK 关闭路径，并检测无额外 trace 网络出口。[官方可观测性说明](https://developers.openai.com/api/docs/guides/agents/integrations-observability)

### 8.2 本机 Web 边界

监听本机不能代替浏览器来源校验。生产同源服务只接受本应用 Origin；开发模式仅允许 `http://127.0.0.1:5173`，Host 仅允许配置的回环 host，不允许 CORS `*`。POST 必须 application/json，拒绝未知 Origin；GET 任务读取拒绝来自其他站点的 Origin/跨站 Fetch Metadata，防止第三方网页触发本地付费调用或读取结果。

不做账号认证，边界是用户控制的本机浏览器和进程；不声称能抵御已控制本机的程序。生产仅启动一个 worker，避免内存任务被分流到其他进程。

### 8.3 日志约定

默认记录时间、request_id、active_agent、阶段、elapsed_ms、model_turns_used、attempt_count、repair_count、安全错误代码和脱敏模型标识，以便核对交接与共享预算。禁记 Authorization、API key、完整 API URL 查询参数、完整问题、结果行、模型输入输出及工具原始响应。SQL 在回答依据中可查看，但默认不写日志。

## 9. 前端实现与本地存储

### 9.1 组件与状态

| 组件/模块 | 职责 |
| --- | --- |
| AppShell / DatasetBanner | 布局、元信息、全局提示 |
| ConversationSidebar | 列表、新建、切换、删除 |
| ChatPanel / Composer | 问题、澄清、运行状态、输入 |
| AnswerCard | 分派不同业务终态 |
| ResultTable / ResultChart | 50 行分页、适用图表、空值和单位 |
| EvidencePanel / ExportButton | SQL/参数、口径、CSV |
| useConversations / apiClient / storage | Vue 响应状态、请求轮询、IndexedDB |

首版使用 Vue 自带响应能力和 fetch，无需为小规模状态额外引入全局状态框架。所有结果为纯文本或固定组件，禁用不可信 v-html；只展示简短阶段，不展示 chain-of-thought。

### 9.2 IndexedDB 模型

数据库名 `chatbi-local`，schema version=1；两个 object store：conversations（key=id）和 messages（key=id，索引 conversation_id、created_at）。会话存 last_spec、pending_clarification、dataset_id、时间；消息存用户文本或完整最终响应、request_id、尝试状态。新消息和会话摘要在同一读写事务提交，不用全量旧数组覆盖数据库。

采用 Web Locks 以 conversation_id 锁住运行提交，BroadcastChannel 通知其他标签页状态变更。锁服务于浏览器交互，不替代后端安全控制。刷新后凭 request_id 尝试恢复轮询；404 则标 interrupted；重新提交需要用户点击，避免自动重复计费。

数据版本不同的会话只读展示旧结果，下一次提问提示新建；不混合两个数据集。用户删除会话时事务删除关联消息。出现 QuotaExceededError 等异常时保留内存结果并提示，不自动删旧记录。目标验收浏览器需具备 IndexedDB、Web Locks、BroadcastChannel。

### 9.3 CSV 与复制

从 result.columns 和全部 result.rows 生成 CSV，非当前页。使用 UTF-8 BOM，双引号包裹和双写内部引号，换行统一 CRLF。字符串单元格在去除前导空白后若以 `= + - @` 或控制字符起始，则添加单引号前缀；整数/十进制按字段类型输出合法数值，不把负数误当公式。

金额字符串保留两位，null 导出为空；地区等枚举导出与界面相同的中文标签。生成 Blob、下载后释放 Object URL。复制 SQL 使用 Clipboard API，失败时提供可选中的纯文本，不用不安全字符串拼接生成“带值 SQL”。

### 10.1 层次依赖与命名约束

| 入口/层 | 职责边界 | 允许的调用 |
| --- | --- | --- |
| main.py | 创建 FastAPI app、注册路由/生命周期/静态资源、解析启动与维护子命令 | api.routes、服务配置与离线初始化入口 |
| api/ | HTTP 参数校验、状态码与响应封装 | services.chat_service/request_service；不直接运行 Agent 或 SQL |
| services/ | 任务状态、共享预算、指标、执行、数据与结果 | chat_service 调用 agent.orchestrator；底层服务不依赖 chat_service 或 API |
| agent/ | SDK Agent 定义、提示词、工具、交接和编排 | 工具调用 query_service；编排器用 result_service 及共享类型 |

实际调用链为 `api.routes → services.chat_service → agent.orchestrator → 三个 Agent`；查询工具返回链为 `QueryAgent → agent.tools → services.query_service → chatbi.db`。QueryService、ResultService、共享类型不反向导入 ChatService/编排器，防止循环依赖；共用的业务模型放 services.schemas，HTTP 模型放 api.schemas，Agent 输出模型放 agent.schemas。

本地只使用单数包名 `agent/`；不创建 `agents/` 或 `agents.py`。例如本地编排导入 `from agent.orchestrator import ...`，SDK 导入 `from agents import Agent, Runner`，不能通过修改 sys.path 把一个包伪装成另一个。路径均由后端根目录定位，不依赖终端当前目录。

### 10.2 依赖

技术基线选 Python 3.11、Node.js 22；这是实现目标环境，不宣称是最新版本。后端依赖为 fastapi、uvicorn、openai-agents、openai、pydantic-settings、sqlglot；sqlite3、Decimal、csv、calendar、hashlib 使用标准库。测试使用 pytest、httpx；前端依赖 Vue 3、ECharts，开发工具 TypeScript、Vite、vue-tsc。具体补丁版本由实际接入验证后写入锁文件，设计阶段不填写未经测试的版本号。

### 12.2 独立基准示例

订单级 2025 年销售额与订单量的人工基准：

```sql
SELECT COALESCE(SUM(paid_amount_cents), 0) AS sales_amount_cents,
       COUNT(*) AS order_count
FROM orders
WHERE status IN ('paid', 'completed')
  AND order_date >= '2025-01-01'
  AND order_date < '2026-01-01';
```

商品排行基准使用 orders JOIN order_items JOIN products，按 product_id 分组求明细实付；专门使用一张含两条明细的订单验证“订单金额不被算两次”。客单价用上述基准总分金额除以订单量后再格式化；不要对各订单金额先转浮点后求均值。

### 12.3 验收映射与通过条件

完整题目及交互预期见功能文档 AC-01～AC-20。AC-02～AC-08、AC-20 使用默认固定数据；AC-05 边界及 AC-14～AC-17 使用测试数据库/模型替身；AC-13 同时验证输入层、工具层和数据库层；AC-18 校验聚合先于限制且 CSV 与返回数据完全一致。

通过条件：20 个案例及其规定边界有记录；核心金额按分、计数按整数完全一致，派生值按既定舍入一致；读写边界无绕过；成功查询的结果在总结故障后保留；期限到达后不继续调用模型或执行数据库查询；真实模型预检通过。外部服务的波动需记录，不把重跑到成功后的单次结果当作稳定性证据。

编排测试还需验证：IntentAgent 澄清时后两个 Agent 调用次数为 0；空结果不运行 AnswerAgent；只有 QueryAgent 持有查询工具；创建任何新 Runner 都不能重置 RequestContext；AnswerAgent 失败保留已成功数据；所有 Agent 共享关闭 tracing 的配置，运行日志能按 request_id 还原交接顺序。

实际开发后，应提供在 backend 根目录执行 `python -m pytest tests`、在 frontend 根目录执行 `npm run typecheck` 与 `npm run build` 的验证记录；这些是计划检查，本次文档交付没有运行不存在的应用测试。
