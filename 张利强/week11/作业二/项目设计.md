# ChatBI 自助问数系统 项目设计文档

**版本**：v1.0（立项基线）  
**阶段**：立项 / MVP 设计  
**目标周期**：1 个月开发最初版本  
**文档性质**：立项评审与开发启动依据

---

## 1. 项目背景与目标

### 1.1 背景

企业日常数据报表开发需求持续存在，业务用户获取数据的路径依赖分析师排期。当前数据基础为 MySQL，约 20 张表，最大单表约 100 万行，尚无统一语义层与指标口径体系。首期不追求完整数据治理，而是以少量核心指标为切入点，验证“业务用户自助问数”的可行性。

### 1.2 项目目标

建设一个独立的 Web 对话式问数系统，使业务用户能够通过自然语言查询核心指标，获得图表、文字结论与口径说明，并导出分析报告。系统通过“自动校验全量拦截 + 人工抽检质量监控”的机制，在快速上线与口径可信之间取得平衡。

### 1.3 成功指标

| 指标 | 目标值 | 计算口径 |
| :--- | :--- | :--- |
| 首答可用率 | ≥80% | 复核前，分母为首次回答数，自动规则判定 |
| 口径正确率 | ≥95% | 20% 人工抽检估计整体，分母为首次回答数，以分析师基准 SQL 为基准 |
| 人工抽检率 | ≤20% | 人工抽检回答数 / 总回答数 |
| 交付周期 | 1 个月 | 从开发启动到最初版本可验收 |

## 2. 范围与边界

### 2.1 首期范围（必须交付）

- 独立 Web 对话页，登录后区分 `business_user` 与 `analyst` 两种角色。
- 4 个核心指标问数：销量、收入、客户数、转化率。
- 20 张 MySQL 表，单表查询为主，支持已登记的少量简单关联。
- 对话内图表、文字结论、口径说明。
- 分析报告导出：对话记录 + 图表 + 结论 + 口径说明，支持 Markdown/HTML 下载。
- 展示前自动校验全量覆盖：语法安全、可执行性、结果合理性、口径一致性。
- 分析师抽检工作流：待抽检、通过、更正/撤回、问题记录。
- 基准 SQL 比对评测与标准问数测试集跑批。

### 2.2 明确不做（首期）

- 不做 Data Agent 多步自主规划与自动任务执行。
- 不做自动报表开发、模板化周报/月报。
- 不做外部系统集成（审批、工单、企微/钉钉/飞书等）。
- 不做行列级数据权限与全链路审计留痕。
- 不做复杂多表 Join、跨主题域分析、即席指标自定义。
- 不做私有化部署要求。

### 2.3 默认假设

- 4 个指标各有一份由分析师确认并版本化管理的基准 SQL。
- 20 张表的元数据、字段含义、同义词由分析师与业务共同确认。
- 首期用户规模与并发量较小，按单实例部署设计。
- 查询以聚合汇总为主，不返回明细行级数据。

## 3. 用户角色与核心场景

| 角色 | 职责 | 核心操作 |
| :--- | :--- | :--- |
| 业务用户 `business_user` | 自助问数、查看图表与结论、导出报告 | 自然语言提问、查看回答、下载报告 |
| 分析师 `analyst` | 维护基准 SQL 与语义配置、人工抽检、问题处理 | 配置指标口径、抽检回答、通过/更正/撤回、维护测试集 |

**核心场景**：

1. 业务用户提问“上月各区域销量是多少” → 系统解析为指标+维度+时间 → 编译 SQL → 自动校验 → 展示图表、结论与口径说明。
2. 业务用户提问“线上渠道收入环比” → 若涉及未登记组合或低置信度，系统返回可回答范围提示或降级回答，并标记低置信度。
3. 分析师在抽检工作台查看待抽检回答 → 核对 DSL、SQL、结果与口径 → 通过或撤回 → 问题回写至配置修复队列。
4. 分析师变更基准 SQL 后，跑批标准测试集，回归口径正确率。

## 4. 总体架构

### 4.1 架构原则

- **LLM 只做意图解析，不直接生成 SQL**：模型输出结构化 DSL，SQL 由语义层确定性编译。
- **口径优先**：命中基准 SQL 模板时优先使用参数化基准 SQL；未命中时走受控编译路径并标记低置信度。
- **展示前全量自动校验**：不通过校验的回答不展示确定性答案。
- **人工抽检不阻塞展示**：抽检用于质量监控与问题发现，发现问题后撤回/更正。
- **做减法**：不建完整语义层，只建 5 张核心配置表；不做 Agent 编排，只做单次问数状态机。

### 4.2 逻辑架构

```
┌─────────────────────────────────────────────┐
│                 Web 对话页                    │
│   登录 / 提问 / 图表 / 结论 / 口径说明 / 导出   │
└─────────────────────┬───────────────────────┘
                      │ HTTP API
┌─────────────────────▼───────────────────────┐
│              应用服务层（FastAPI）             │
│  会话管理 / 角色鉴权 / 问数编排 / 报告导出      │
└───────┬─────────────┬─────────────┬─────────┘
        │             │             │
┌───────▼──────┐ ┌────▼─────┐ ┌────▼─────────┐
│ 意图解析层    │ │ 语义编译层│ │ 自动校验层     │
│ LLM + 检索    │ │ DSL → SQL│ │ AST/EXPLAIN/  │
│ 输出 DSL JSON │ │ 确定性拼装│ │ 合理性/口径比对 │
└───────┬──────┘ └────┬─────┘ └────┬─────────┘
        │             │             │
┌───────▼─────────────▼─────────────▼─────────┐
│              语义配置库（MySQL）              │
│ sl_metric / sl_dimension / sl_synonym /      │
│ sl_metric_caliber / sl_join_path             │
└─────────────────────┬───────────────────────┘
                      │
┌─────────────────────▼───────────────────────┐
│              业务数据库（MySQL）              │
│              20 张表，最大单表 100 万行        │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│         抽检与评测子系统（分析师端）           │
│  抽检工作台 / 问题回写 / 标准测试集跑批        │
└─────────────────────────────────────────────┘
```

### 4.3 问数主链路

```
用户提问
  → 同义词/指标/维度召回
  → LLM 输出 DSL JSON
  → DSL 合法性校验
  → 语义编译：查配置、注入口径、固定 Join 路径
  → SQL 执行（超时/行数护栏）
  → 自动校验四层
      ├─ 通过 → 生成图表与结论 → 展示 → 进入抽检池
      └─ 不通过 → 一次重试 → 仍失败则返回“无法回答/需人工确认”
```

## 5. 功能设计

### 5.1 登录与角色

- 用户名/密码登录，会话保持。
- 角色：`business_user`、`analyst`。
- `business_user` 可见对话页、历史回答、报告导出。
- `analyst` 额外可见抽检工作台、配置管理入口、测试集跑批入口。
- 首期不做行列级数据权限，所有登录用户可查询已登记指标。

### 5.2 对话问数

- 输入自然语言问题，支持多轮上下文中的**指标/维度/时间指代**，但首期不追求复杂多轮推理。
- 回答包含：
  - 图表：根据维度数量自动选择柱状图/折线图/饼图/单值卡片。
  - 文字结论：基于结果生成简短描述，不编造未查询的数据。
  - 口径说明：展示指标定义、基准 SQL 说明、数据时间范围、过滤条件。
  - 置信度标签：高/低；低置信度回答优先进入抽检。
- 无法回答时给出明确原因：未登记指标、超出支持维度、校验未通过、执行失败等。

### 5.3 报告导出

- 将当前对话中的问题、图表、结论、口径说明组装为 Markdown/HTML。
- 支持下载；首期不生成模板化周报/月报。
- 导出内容标注“生成时间、数据范围、口径版本”。

### 5.4 分析师抽检工作台

- 待抽检列表：按时间、置信度、指标筛选。
- 回答详情：原始问题、DSL、编译 SQL、执行结果、口径说明、自动校验记录。
- 操作：
  - **通过**：记录抽检通过，计入正确率估计样本。
  - **更正/撤回**：回答状态变更，业务用户侧显示“已更正/已撤回”；记录问题类型（口径错误/结果错误/图表问题/其他）。
- 抽检触发：每周按 ≤20% 比例抽取，低置信度优先；支持手动加抽。
- 问题回写：抽检问题进入修复队列，关联到指标/同义词/Join 路径配置，修复后回归。

### 5.5 配置管理（分析师）

- 指标管理：名称、同义词、物理表达式、默认聚合、所属表。
- 维度管理：名称、同义词、来源字段、所属表。
- 同义词管理：原始词 → 指标/维度/枚举值。
- 口径管理：指标口径名称、定义、基准 SQL 模板、是否默认、版本号。
- Join 路径管理：允许的 from/to 表、关联键、关联类型；未登记路径禁止编译。
- 配置变更需记录版本，变更后触发测试集回归。

## 6. 语义层设计

### 6.1 设计原则

- 只建 MVP 必需的 5 张表，不引入完整 12 表语义层。
- 基准 SQL 模板是口径权威载体，编译时优先参数化复用。
- Join 路径白名单化，LLM 不得指定表关联。
- 所有配置支持版本化，便于回归与回滚。

### 6.2 核心配置表

#### `sl_metric` 指标表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| metric_id | VARCHAR(64) PK | 指标唯一标识 |
| name | VARCHAR(128) | 指标名称 |
| synonyms | JSON | 同义词列表 |
| preferred_table | VARCHAR(128) | 首选物理表 |
| physical_expr | TEXT | 物理表达式，如 `SUM(order_amount)` |
| default_agg | VARCHAR(32) | 默认聚合方式 |
| status | TINYINT | 启用/停用 |
| version | INT | 配置版本 |

#### `sl_dimension` 维度表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| dim_id | VARCHAR(64) PK | 维度标识 |
| name | VARCHAR(128) | 维度名称 |
| synonyms | JSON | 同义词 |
| source_column | VARCHAR(128) | 来源字段 |
| table_name | VARCHAR(128) | 所属表 |
| status | TINYINT | 启用/停用 |

#### `sl_synonym` 同义词映射表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| raw_term | VARCHAR(128) PK | 原始词 |
| canonical_type | VARCHAR(32) | metric / dimension / value |
| canonical_id | VARCHAR(64) | 对应标准 ID |
| priority | INT | 匹配优先级 |

#### `sl_metric_caliber` 口径表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| caliber_id | VARCHAR(64) PK | 口径标识 |
| metric_id | VARCHAR(64) | 关联指标 |
| caliber_name | VARCHAR(128) | 口径名称 |
| definition | TEXT | 业务定义说明 |
| base_sql_template | TEXT | 参数化基准 SQL |
| is_default | TINYINT | 是否默认口径 |
| version | INT | 版本号 |
| updated_by | VARCHAR(64) | 更新人 |

#### `sl_join_path` 关联路径表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| path_id | VARCHAR(64) PK | 路径标识 |
| from_table | VARCHAR(128) | 左表 |
| to_table | VARCHAR(128) | 右表 |
| join_keys | JSON | 关联键对 |
| join_type | VARCHAR(16) | INNER / LEFT |
| status | TINYINT | 是否允许 |

### 6.3 基准 SQL 模板示例

```sql
-- 指标：收入；口径：默认收入口径；时间：{start_date} ~ {end_date}
SELECT {dimension_select}
       SUM(o.pay_amount) AS revenue
FROM orders o
WHERE o.order_status = 'paid'
  AND o.pay_time >= '{start_date}'
  AND o.pay_time <  '{end_date}'
  {extra_filters}
GROUP BY {dimension_group}
```

编译层只替换已登记维度和过滤条件，不允许模型改写 `WHERE` 中的口径条件。

## 7. 查询生成设计

### 7.1 DSL 定义

LLM 输出 JSON DSL，示例：

```json
{
  "metric": "revenue",
  "dimensions": ["region"],
  "filters": [
    {"field": "channel", "op": "=", "value": "线上"}
  ],
  "time_range": {
    "type": "month",
    "value": "2025-12"
  },
  "chart_hint": "bar"
}
```

约束：

- `metric` 必须来自召回候选。
- `dimensions` 必须来自已登记维度且与指标表存在合法 Join 路径。
- `filters` 字段必须来自已登记维度或枚举值。
- 不接受模型输出表名、Join 条件、原生 SQL。

### 7.2 编译规则

1. 根据 `metric` 查 `sl_metric` 与默认 `sl_metric_caliber`。
2. 若 DSL 组合命中基准 SQL 模板可覆盖范围，优先使用参数化基准 SQL。
3. 否则按固定模板拼装：`SELECT` 维度 + 指标表达式，`FROM` 首选表，`WHERE` 口径条件 + 时间 + 过滤，`GROUP BY` 维度。
4. 涉及多表时，仅允许使用 `sl_join_path` 已登记路径；否则拒绝编译。
5. 强制追加护栏：`LIMIT`、时间范围必填、禁止 `SELECT *`、禁止无聚合明细查询。

### 7.3 重试机制

- SQL 执行失败或自动校验不通过时，将错误信息回传 LLM，允许**一次**修正 DSL 重试。
- 重试仍失败：返回“无法回答，已记录”，标记低置信度，进入抽检候选池。
- 重试不计入首答分母，单独统计重试成功率。

## 8. 自动校验设计

所有回答展示前必须通过以下四层校验，全部通过才展示确定性答案。

| 层级 | 校验内容 | 实现要点 | 失败处理 |
| :--- | :--- | :--- | :--- |
| L1 语法与安全 | 仅 SELECT；禁止 DDL/DML；禁止无时间条件全表扫描；禁止过深嵌套 | sqlglot/JSqlParser AST 校验 + 关键字白名单 | 拦截，不展示 |
| L2 可执行性 | SQL 可执行、不超时、扫描行数可控 | `EXPLAIN` 预检 + 5 秒执行超时 + 行数上限 | 触发一次重试，仍失败则拒绝 |
| L3 结果合理性 | 结果非空或有合理空结果说明；指标值域合理；时间范围匹配 | 规则引擎：收入≥0、转化率 0–1、行数上限、时间范围比对 | 标记低置信度或拦截 |
| L4 口径一致性 | 与基准 SQL 在相同条件下结果一致 | 对命中基准模板的回答自动执行基准 SQL 比对；容差可配置 | 不一致则拦截，转人工确认 |

**低置信度标记**：未命中基准模板、经过重试、L3 存疑的回答标记为低置信度，优先进入抽检。

## 9. 抽检与质量闭环设计

### 9.1 抽检规则

- 人工抽检率 ≤20%，不阻塞展示。
- 抽样策略：每周分层随机 + 低置信度优先 + 分析师手动加抽。
- 抽检样本覆盖 4 个指标与主要维度组合。

### 9.2 状态机

```
回答生成 → 自动校验通过 → 已展示
                              ├─ 进入抽检池（待抽检）
                              │     ├─ 抽检通过 → 已抽检
                              │     └─ 发现问题 → 已更正 / 已撤回
                              └─ 未被抽中 → 保持已展示
```

### 9.3 问题回写

抽检发现问题必须回写到配置层，而非仅记录聊天日志：

- 口径错误 → 修正 `sl_metric_caliber` 或基准 SQL。
- 同义词缺失/歧义 → 修正 `sl_synonym`。
- Join 路径错误 → 修正 `sl_join_path`。
- 结果合理性问题 → 补充校验规则。
- 修复后跑批标准测试集，确认回归。

## 10. 评测体系

### 10.1 首答可用率

- 计算时点：复核前。
- 分母：首次回答数；重试回答单独统计。
- 自动判定规则：

> 首答可用 = DSL 合法 + SQL 编译成功 + 可执行未超时 + 结果非空或空结果有合理提示 + 未触发 L4 口径拦截 + 图表可渲染。

### 10.2 口径正确率

- 以 20% 人工抽检结果估计整体。
- 分母为首次回答数，基准为分析师基准 SQL 结果。
- 同时维护 50–100 条标准问数测试集（含标准 SQL 与预期结果），配置变更或模型升级后全量回归，作为交叉证据。
- 验收报告需同时给出抽检正确率与置信区间。

### 10.3 抽检率

- 人工抽检回答数 / 总回答数 ≤20%。
- 报告实际抽检率、抽检覆盖率、问题发现率。

## 11. 技术栈与部署

| 层 | 选型 | 说明 |
| :--- | :--- | :--- |
| 前端 | React + 图表库（ECharts/Recharts） | 对话页、图表、抽检工作台 |
| 后端 | Python 3.11+ / FastAPI | 问数编排、语义编译、校验、抽检 API |
| 对话状态 | LangGraph（轻量） | 仅单次问数状态流转与重试，不做多步自主规划 |
| 语义配置库 | MySQL | 5 张配置表 |
| 业务数据库 | MySQL | 20 张表，只读账号 |
| SQL 解析 | sqlglot | AST 校验与安全白名单 |
| LLM | 企业可用的大模型 API | 输出 DSL JSON，不直接输出 SQL |
| 部署 | 单实例服务 + MySQL | 不要求私有化；按小规模并发设计 |

**部署拓扑**：Web 前端静态资源 + FastAPI 服务 + 配置库/业务库。业务库使用只读账号，查询强制超时与行数限制。

## 12. 接口设计（核心）

### 12.1 问数接口

`POST /api/chat/query`

请求：

```json
{
  "session_id": "s-001",
  "question": "上月各区域销量是多少"
}
```

响应：

```json
{
  "answer_id": "a-001",
  "status": "answered",
  "confidence": "high",
  "chart": {"type": "bar", "data": []},
  "conclusion": "上月各区域销量...",
  "caliber": {"metric": "销量", "definition": "...", "version": 3},
  "sql_preview": "SELECT ...",
  "warnings": []
}
```

无法回答时 `status` 为 `rejected` 或 `needs_human`，并给出原因码。

### 12.2 抽检接口

- `GET /api/analyst/reviews?status=pending`
- `GET /api/analyst/reviews/{answer_id}`
- `POST /api/analyst/reviews/{answer_id}/approve`
- `POST /api/analyst/reviews/{answer_id}/reject`，请求体含问题类型与说明。

### 12.3 配置接口

- 指标/维度/同义词/口径/Join 路径的 CRUD。
- 变更后触发版本号递增与回归任务。

### 12.4 报告导出

`GET /api/reports/{answer_id}/export?format=markdown|html`

## 15. 风险与应对

| 风险 | 影响 | 应对 |
| :--- | :--- | :--- |
| 无统一口径，95% 目标偏高 | 验收不达标 | 优先用基准 SQL 覆盖高频组合；自动口径比对拦截偏差；必要时收窄支持维度组合 |
| 1 个月范围偏紧 | 延期或质量不足 | 第 1 周 demo 作为硬检查点；报告导出与抽检工作台做最小可用版；不砍语义层、编译器、自动校验、基准比对、双角色 |
| 20% 抽检估计 95% 存在统计误差 | 验收争议 | 同时报告置信区间；标准测试集作为主要交叉证据；验收前扩样 |
| LLM 输出 DSL 不稳定 | 首答可用率低 | 限定模型只做选词填空；同义词精确匹配优先；DSL 合法性校验前置；最多一次重试 |
| 业务提问超出支持范围 | 用户体验差 | 明确提示可回答范围；低置信度标记；抽检问题驱动配置扩展 |
| 查询拖垮业务库 | 可用性风险 | 只读账号、超时、行数上限、禁止无时间条件查询、EXPLAIN 预检 |

## 16. 验收标准

1. 业务用户可通过 Web 对话页对 4 个指标完成单表为主的自助问数，并获得图表、结论与口径说明。
2. 所有展示回答均通过自动校验；未通过校验的回答不展示确定性答案。
3. 分析师可完成抽检：查看详情、通过、更正/撤回，问题可回写配置。
4. 首答可用率 ≥80%（复核前，首次回答数为分母，自动规则判定）。
5. 口径正确率 ≥95%（20% 人工抽检估计，分母为首次回答数，以基准 SQL 为基准），并附置信区间与测试集回归结果。
6. 人工抽检率 ≤20%，抽检不阻塞展示。
7. 支持报告导出（Markdown/HTML）。
8. 登录与双角色可用；语义配置版本化；问数日志可追溯。

## 17. 附录：术语表

| 术语 | 说明 |
| :--- | :--- |
| DSL | 领域特定语言，本系统指 LLM 输出的结构化查询意图 JSON |
| 基准 SQL | 分析师确认的指标口径 SQL，作为口径正确性比对基准 |
| 低置信度 | 未命中基准模板、经过重试或结果合理性存疑的回答标记 |
| C 方案 | 展示前全量自动校验，人工抽检 ≤20% 做质量监控，发现问题撤回/更正 |
| 首答 | 用户一次提问后系统首次生成的回答，不含重试后的回答 |
| 口径拦截 | 自动校验 L4 发现结果与基准 SQL 不一致时阻止展示确定性答案 |

---

**文档结论**：本设计以“最小语义配置 + 确定性编译 + 全量自动校验 + 抽检质量闭环”为主线，在 1 个月周期内优先保障 4 个核心指标的可信问数能力。第 1 周端到端 demo 是排期成立的关键检查点；基准 SQL 与语义配置是口径正确率的单点依赖，需在开发启动前冻结。
