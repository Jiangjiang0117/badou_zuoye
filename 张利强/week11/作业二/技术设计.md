# ChatBI 自助问数系统 技术设计文档

**版本**：v1.0（与项目设计文档 v1.0、功能设计文档 v1.0 对齐）  
**阶段**：MVP 技术设计  
**约束**：4 指标、20 张 MySQL 表、单表为主、1 个月交付、FastAPI + React + LangGraph  
**文档用途**：开发任务拆分、技术评审、测试用例设计


## 1. 技术设计原则

三条刚性原则决定所有技术选型与实现方式，在进入具体模块前需首先确认：

**原则一：LLM 不触碰 SQL。** 大模型只做意图解析，输出受约束的 DSL JSON；SQL 的表选择、JOIN 路径、口径过滤、聚合方式全部由确定性编译器完成。这不是对模型能力的否定，而是对“口径正确率 ≥95%”这一验收指标的工程回应——凡能用规则 100% 做对的事，不交给模型“发挥”。NL2DSL 为主、NL2SQL 为辅的混合解析引擎已被验证在维持稳定性的同时显著降低口径漂移。

**原则二：展示前全量自动校验，人工抽检不阻塞展示。** C 方案的技术含义是：自动校验器是展示路径上的**硬门禁**，任何未通过四层校验的回答不得以确定性答案形态展示；人工抽检是展示后的**质量监控回路**，发现问题后撤回/更正，但不承担逐条放行的职责。

**原则三：做减法，但减法不能砍在质量链路上。** 不做完整语义层、不做 Agent 多步规划、不做行列权限与审计留痕。可以砍的是 UI 完整度、报告模板化、配置自动回归的自动化程度；不能砍的是：DSL Schema、确定性编译器、四层自动校验、基准 SQL 比对、登录与双角色、抽检状态机。

**架构上的关键决策**：

- **语义配置读取层做进程内 TTL 缓存（默认 60 秒）** 。配置变更频率低，但每条问数都要读 5 张表；不缓存会让配置库成为每次问数的串行瓶颈。缓存失效策略为“写后主动失效 + TTL 兜底”，不做分布式缓存。
- **DSL 编译器、自动校验器、基准 SQL 比对器均为纯函数模块**，不直接访问数据库连接池之外的资源；校验器需要的基准 SQL 执行结果由编排层注入。这样便于单元测试和后续替换。
- **LangGraph 只承载单次问数的状态流转**，不引入多轮自主规划、工具循环、记忆模块。首期的“重试”是状态图中一个受控的回边，最多走一次，不是 Agent 的自主决策循环。


## 4. 语义配置层技术设计

### 4.1 配置表 DDL 概要（5 张核心表）

```sql
CREATE TABLE sl_metric (
  metric_id       VARCHAR(64) PRIMARY KEY,
  name            VARCHAR(128) NOT NULL,
  synonyms        JSON NOT NULL,              -- ["销量","销售量","销售数量"]
  preferred_table VARCHAR(128) NOT NULL,
  physical_expr   TEXT NOT NULL,              -- SUM(o.qty) 或 COUNT(DISTINCT c.customer_id)
  default_agg     VARCHAR(32) NOT NULL DEFAULT 'SUM',
  status          TINYINT NOT NULL DEFAULT 1,
  version         INT NOT NULL DEFAULT 1,
  updated_by      VARCHAR(64),
  updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE sl_dimension (
  dim_id         VARCHAR(64) PRIMARY KEY,
  name           VARCHAR(128) NOT NULL,
  synonyms       JSON NOT NULL,
  source_column  VARCHAR(128) NOT NULL,
  table_name     VARCHAR(128) NOT NULL,
  data_type      VARCHAR(32) NOT NULL,        -- string / number / date
  status         TINYINT NOT NULL DEFAULT 1
);

CREATE TABLE sl_synonym (
  raw_term       VARCHAR(128) PRIMARY KEY,
  canonical_type VARCHAR(16) NOT NULL,        -- metric / dimension / value
  canonical_id   VARCHAR(64) NOT NULL,
  priority       INT NOT NULL DEFAULT 100
);

CREATE TABLE sl_metric_caliber (
  caliber_id        VARCHAR(64) PRIMARY KEY,
  metric_id         VARCHAR(64) NOT NULL,
  caliber_name      VARCHAR(128) NOT NULL,
  definition        TEXT NOT NULL,
  base_sql_template TEXT NOT NULL,            -- 参数化模板，{dimension_select} 等占位符
  is_default        TINYINT NOT NULL DEFAULT 0,
  version           INT NOT NULL DEFAULT 1,
  updated_by        VARCHAR(64),
  UNIQUE KEY uk_metric_default (metric_id, is_default)  -- 保证每指标仅一个默认口径
);

CREATE TABLE sl_join_path (
  path_id    VARCHAR(64) PRIMARY KEY,
  from_table VARCHAR(128) NOT NULL,
  to_table   VARCHAR(128) NOT NULL,
  join_keys  JSON NOT NULL,                   -- [{"left":"user_id","right":"id"}]
  join_type  VARCHAR(8) NOT NULL DEFAULT 'LEFT',
  status     TINYINT NOT NULL DEFAULT 1
);
```

**设计要点**：

- `sl_metric_caliber` 上的 `UNIQUE KEY uk_metric_default (metric_id, is_default)` 通过数据库约束保证“每指标仅一个默认口径”，而不是仅靠应用层逻辑。`is_default=0` 的口径允许存在多个，但默认口径必须唯一——在 MySQL 中该唯一索引对 `is_default=0` 的多行并不冲突（因为 `0` 不唯一），对 `is_default=1` 则强制唯一。
- `sl_synonym` 的 `raw_term` 作为主键意味着一个原始词只能映射到一个标准对象。如果业务上存在“同名不同义”（如“转化率”在不同指标下含义不同），首期通过**在提问上下文中结合指标共现来消歧**，不引入更复杂的仲裁表；这是 MVP 的显式取舍，待抽检问题积累后再迭代。
- `sl_join_path` 是**有向白名单**。`from_table` 为事实表、`to_table` 为维度表的路径优先登记；编译器只允许按已登记方向关联，不做反向推导。

### 4.2 基准 SQL 模板的参数化规范

基准 SQL 模板使用命名占位符，由编译器替换，**模板中已写定的口径过滤条件不可被 DSL 覆盖**：

```sql
-- 收入：默认口径
SELECT {dimension_select}
       SUM(o.pay_amount) AS metric_value
FROM orders o
{join_clause}
WHERE o.order_status = 'paid'          -- 口径条件，DSL 不可修改
  AND o.pay_time >= '{start_date}'     -- 时间参数，由 DSL 时间范围编译
  AND o.pay_time <  '{end_date}'
  {extra_filters}                      -- 仅允许追加已登记维度过滤
{group_by}
```

编译器的替换边界：`{dimension_select}`、`{join_clause}`、`{extra_filters}`、`{group_by}`、时间参数可替换；`WHERE` 中的口径条件、聚合表达式（`SUM(o.pay_amount)`）不可替换。替换后由 sqlglot 解析验证 AST 中口径条件节点未被修改，否则编译失败。


## 5. NL2DSL 模块技术设计

### 5.1 DSL Schema（Pydantic 模型）

```python
from pydantic import BaseModel, Field
from typing import List, Optional, Literal

class TimeRange(BaseModel):
    type: Literal["month", "quarter", "year", "recent_days", "absolute"]
    value: str                       # "2025-12" / "2025-Q4" / "30"
    start_date: Optional[str] = None # 编译后填充
    end_date: Optional[str] = None

class FilterItem(BaseModel):
    field: str
    op: Literal["=", "!=", ">", ">=", "<", "<=", "in", "like"]
    value: str | List[str]

class DSL(BaseModel):
    metric: str                      # metric_id，必须来自召回候选
    dimensions: List[str] = []
    filters: List[FilterItem] = []
    time_range: TimeRange
    chart_hint: Optional[Literal["bar", "line", "pie", "card"]] = None
```

**DSL 的硬约束**：`metric` 只能是语义层已注册的 `metric_id`；`dimensions` 只能来自该指标 `available_dimensions`（或在 `sl_dimension` 中登记且与指标表存在已登记 Join 路径）；`filters.field` 只能来自已登记维度或指标可用的枚举值字段；`time_range` 必填。Pydantic 的 `Literal` 与自定义 validator 在解析阶段拦截大部分非法结构，不合法 DSL 不进入编译器。

### 5.2 意图解析流程

```
用户问题
  → 关键词/同义词精确召回（MySQL sl_synonym + sl_metric.synonyms）
  → 组装 Prompt（含候选指标、维度、时间解析规则、DSL Schema 说明）
  → LLM JSON mode 输出
  → Pydantic 解析 + 合法性校验
      ├─ 失败 → 一次修复调用（携带校验错误）
      └─ 成功 → 进入编译
```

**召回策略**：首期不引入向量检索。从 `sl_synonym` 按 `raw_term` 对问题做子串匹配，结合 `sl_metric.synonyms` 和 `sl_dimension.synonyms` 的 JSON 数组做精确/前缀匹配，产出候选指标和维度列表注入 Prompt。4 个指标、20 张表的规模下，精确匹配的召回率足够；引入向量检索的收益不足以抵消其运维与调试成本。

**LLM 调用的工程约束**：

- 使用 JSON mode（或 function calling）强制结构化输出，不在 Prompt 中“请求”模型输出 JSON。
- Prompt 中明确列出候选 `metric_id`、`dim_id` 及其同义词，要求模型**只能从列表中选择**，不得创造新值。
- 时间解析优先用规则（“上月”“近30天”“2025-12”等模式），规则无法覆盖时才由模型推断；推断结果必须落入 `TimeRange` 的合法枚举。
- 超时 10 秒；超时视为解析失败，走重试/降级路径。

### 5.3 LLM 不直接写 SQL 的约束落地

意图解析的 System Prompt 中显式禁止输出表名、字段名、JOIN 条件、原生 SQL 片段。解析后的 DSL 不包含任何物理层信息，从结构上杜绝模型“越权”。如果模型输出中检测到 SQL 关键字（`SELECT`、`FROM`、`JOIN` 等）出现在非预期字段，DSL 校验阶段直接拒绝。


## 6. 确定性编译器技术设计

### 6.1 编译算法

```
输入：合法 DSL + 语义配置快照

1. 查 sl_metric[dsl.metric] → preferred_table, physical_expr, default_agg
2. 查 sl_metric_caliber[metric_id, is_default=1] → base_sql_template
3. 判断维度与过滤条件是否全部落在基准模板可覆盖范围
     ├─ 是（命中模板）→ 使用 base_sql_template，参数化替换
     └─ 否（即席组合）→ 使用固定模板拼装
4. 时间范围编译：TimeRange → {start_date}, {end_date}
5. Join 路径解析：
     - 若涉及多表，查 sl_join_path 寻找 from_table → 维度表的有向路径
     - 无已登记路径 → 编译失败（E2006）
     - 存在多条路径时，取最短路径；首期只允许单跳路径
6. 拼装 SQL：
     - SELECT: dimension_select + physical_expr AS metric_value
     - FROM: preferred_table
     - WHERE: 口径条件（不可改写）+ 时间条件 + extra_filters
     - GROUP BY: dimensions
     - LIMIT: 强制 1000
7. sqlglot 解析编译后 SQL，校验：
     - 口径条件 AST 节点与模板中的口径条件等价（AST 归一化后比较）
     - 无 SELECT *
     - 无明细无聚合查询（metric_value 必须是聚合表达式）
     - 无未登记表/字段
8. 输出 CompileResult { sql, hit_template: bool, caliber_version, warnings }
```

**“命中模板 vs 即席组合”的分界**：如果 DSL 的维度和过滤条件在基准模板的 `{dimension_select}`/`{extra_filters}` 可安全替换范围内，走模板路径，该回答在自动校验 L4 中可自动比对口径；否则走即席拼装路径，编译成功但标记 `low_confidence=True`，L4 无法自动比对，转入人工抽检优先池。这是“口径正确率”可度量的关键设计——尽可能让高比例回答命中模板，使自动口径比对覆盖足够大的样本。

### 6.2 编译器的确定性保障

编译器的输出只依赖于 DSL 和语义配置快照，不依赖模型或外部状态。同一 DSL + 同一配置快照必须产生**逐字节相同**的 SQL（时间参数已解析为具体日期后）。这一性质使得：

- 基准 SQL 比对可以进行 AST 级等价性判断；
- 配置变更后的回归测试可以精确对比 SQL 变化；
- 问题复现不需要重放 LLM 调用。


## 7. 自动校验四层技术设计

### 7.1 L1：语法与安全（sqlglot AST 校验）

```python
import sqlglot
from sqlglot import exp

FORBIDDEN_EXPRESSIONS = (
    exp.Insert, exp.Update, exp.Delete, exp.Create, exp.Drop,
    exp.Alter, exp.Command,
)

def validate_syntax_and_safety(sql: str) -> ValidationResult:
    try:
        tree = sqlglot.parse_one(sql, dialect="mysql")
    except sqlglot.errors.ParseError as e:
        return ValidationResult(False, "L1", f"SQL 解析失败: {e}")

    if not isinstance(tree, exp.Select):
        return ValidationResult(False, "L1", "仅允许 SELECT 查询")

    for node in tree.walk():
        if isinstance(node, FORBIDDEN_EXPRESSIONS):
            return ValidationResult(False, "L1", f"禁止的操作: {type(node).__name__}")
        if isinstance(node, exp.Star):
            return ValidationResult(False, "L1", "禁止 SELECT *")

    # 时间条件必填检查
    where = tree.args.get("where")
    if where is None:
        return ValidationResult(False, "L1", "必须包含 WHERE 条件（时间范围）")

    return ValidationResult(True, "L1", "ok")
```

L1 在**数据库执行之前**拦截写操作、DDL、`SELECT *` 和无条件全表扫描。不依赖数据库权限作为唯一防线——只读账号是第二层保险，不是第一层。

### 7.2 L2：可执行性（EXPLAIN + 超时执行）

- **预检**：执行 `EXPLAIN FORMAT=JSON`，检查 `table` 节点的 `rows_examined_per_scan` 是否超过阈值（默认 50 万行）；超过则标记 `suspicious=True`，但不直接拦截（即席组合可能确实需要扫描较大范围）。
- **执行**：在只读连接上执行，会话级设置 `SET SESSION max_execution_time = 5000`（MySQL 5.7.8+ 支持），配合应用层超时（`asyncio.wait_for` 6 秒）双重保险。
- **行数护栏**：编译时已注入 `LIMIT 1000`；执行后再次检查返回行数，超限截断并记录警告。
- **失败处理**：执行异常（超时、语法错、权限错）触发一次重试；重试仍失败返回无法回答。

### 7.3 L3：结果合理性（规则引擎）

| 规则 | 实现 | 失败处理 |
| :--- | :--- | :--- |
| 结果非空 | `len(rows) > 0` | 空结果允许展示，但附带“未查询到数据，请检查时间范围”说明；标记 `empty_result=True`，提高抽检优先级 |
| 指标值域 | 收入/销量 ≥ 0；转化率 ∈ [0, 1]（若定义为比率） | 越界则拦截，标记低置信度 |
| 时间范围匹配 | 结果中的时间字段落在 DSL 请求的 `start_date ~ end_date` 内 | 不匹配则标记 `suspicious`，进入抽检优先池 |
| 行数上限 | 结果行数 ≤ 1000 | 超出则截断并警告 |
| 聚合一致性 | 若 DSL 无维度，结果应只有一行 | 多行则标记异常 |

L3 是“软拦截”与“硬拦截”的结合：值域越界硬拦截；空结果、时间不匹配、行数接近上限做软标记，不阻止展示但提高抽检概率。

### 7.4 L4：口径一致性（基准 SQL 自动比对）

仅对 `hit_template=True` 的回答执行。流程：

```
1. 从 CompileResult 中取出 hit_template=True 的 SQL 和 caliber_version
2. 用同一 DSL 的时间/过滤参数，从基准模板重新编译一份“基准 SQL”
   （编译器保证与主 SQL 同源，但独立执行以捕获执行期差异）
3. 分别执行主 SQL 和基准 SQL，获取结果集
4. 对结果集做规范化排序（按维度列排序）
5. 逐值比对：
   - 数值型：相对误差 ≤ 1e-6 或绝对误差 ≤ 0.01（可配置）
   - 字符串/日期：精确相等
   - 行数不一致：直接判定不一致
6. 不一致 → 拦截，不展示确定性答案，标记 needs_human=True
```

**为什么“同源编译再执行”而不是直接信任主 SQL**：主 SQL 可能因为即席过滤条件的注入方式与基准模板预期不同，导致口径条件被意外改变；独立执行基准 SQL 比对可以在展示前捕获这类编译层面的口径漂移。AST 归一化比对用于静态检查口径条件未被改写；结果比对用于动态捕获执行层面的差异，二者互补。

**L4 的覆盖边界**：即席组合（`hit_template=False`）无法自动比对，直接标记 `low_confidence=True`，进入抽检优先队列。首期的目标是通过模板覆盖让尽可能高比例的回答走 L4 自动比对；L4 覆盖率本身应作为评测指标之一记录（“口径自动校验覆盖率”）。

### 7.5 校验结果与展示决策

| L1 | L2 | L3 | L4 | 展示决策 | 置信度 |
| :---: | :---: | :---: | :---: | :--- | :--- |
| ✓ | ✓ | ✓ | ✓ | 展示确定性答案 | high |
| ✓ | ✓ | ✓（软标记） | ✓ | 展示，带说明/警告 | high（带标记） |
| ✓ | ✓ | ✗（硬拦截） | — | 不展示确定答案，返回原因 | low |
| ✓ | ✓ | — | ✗ | 不展示确定答案，转人工确认 | low |
| ✓ | ✓ | — | 未覆盖 | 展示，标记低置信度 | low |
| ✓ | ✗（重试后） | — | — | 返回无法回答 | — |
| ✗ | — | — | — | 不展示 | — |

**关键原则**：L4 不通过时**不展示确定性答案**，但可以展示“该问题已转人工确认”的提示；即席组合（L4 未覆盖）允许展示但强制标记低置信度并进入抽检优先池——这是在不牺牲可用率的前提下对无法自动比对的部分做显式风险标注。


## 8. 问数编排（LangGraph）技术设计

### 8.1 状态图定义

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Optional

class QueryState(TypedDict):
    session_id: str
    user_id: str
    question: str
    recall_candidates: dict
    dsl: Optional[dict]
    dsl_valid: bool
    compile_result: Optional[dict]
    exec_result: Optional[dict]
    validation: Optional[dict]
    retry_count: int
    final_status: str          # answered / rejected / needs_human / retry_failed
    answer_id: Optional[str]

graph = StateGraph(QueryState)

graph.add_node("recall", recall_node)
graph.add_node("parse_dsl", parse_dsl_node)
graph.add_node("validate_dsl", validate_dsl_node)
graph.add_node("compile", compile_node)
graph.add_node("execute", execute_node)
graph.add_node("auto_validate", auto_validate_node)
graph.add_node("retry_parse", retry_parse_node)
graph.add_node("persist_answer", persist_answer_node)
graph.add_node("reject", reject_node)

graph.set_entry_point("recall")
graph.add_edge("recall", "parse_dsl")
graph.add_edge("parse_dsl", "validate_dsl")

graph.add_conditional_edges("validate_dsl", route_after_dsl_validate, {
    "valid": "compile",
    "invalid": "retry_parse",
})
graph.add_edge("compile", "execute")
graph.add_edge("execute", "auto_validate")

graph.add_conditional_edges("auto_validate", route_after_validate, {
    "pass": "persist_answer",
    "retry": "retry_parse",
    "reject": "reject",
})
graph.add_conditional_edges("retry_parse", route_after_retry, {
    "retry": "validate_dsl",
    "exhausted": "reject",
})
graph.add_edge("persist_answer", END)
graph.add_edge("reject", END)
```

**设计要点**：

- 状态图的节点边界与功能设计中的 F-M2-02~F-M2-10 一一对应，便于测试覆盖和日志埋点。
- `retry_parse` 是一个**受控回边**：进入时递增 `retry_count`，`route_after_retry` 在 `retry_count > 1` 时直接走向 `exhausted`。它不是 Agent 的自主循环，而是硬编码的一次重试。
- `persist_answer` 在事务中写入 `answer` 记录并更新会话；`answer` 记录包含 DSL、编译 SQL、四层校验结果、置信度、口径版本，供抽检工作台和日志追溯使用。

### 8.2 重试的输入注入

重试不是简单重复调用。`retry_parse` 节点将上一轮的失败原因（DSL 校验错误信息、编译失败原因、SQL 执行错误、L4 不一致摘要）注入 Prompt，要求模型**在原有 DSL 基础上修正**，而不是重新生成。这显著提高一次重试的成功率，也避免重试完全偏离原意图。


## 9. 基准 SQL 比对与评测技术设计

### 9.1 首答可用率自动计算

`answer` 表增加 `first_answer_usable` 布尔字段，由 `persist_answer` 节点在写入时计算：

```python
first_answer_usable = (
    dsl_valid
    and compile_success
    and exec_success
    and not exec_timed_out
    and (row_count > 0 or empty_result_explained)
    and not l4_blocked
    and chart_rendered
)
```

- 仅对 `retry_count == 0` 的回答计入首答分母；重试后的回答不改变首答可用率的分子分母，但单独统计重试成功率。
- `chart_rendered` 由展示层回调或服务端渲染结果判定；如果图表渲染失败，该回答不计为可用。

### 9.2 口径正确率的抽检估计

- 抽检样本来自 `answer` 表中 `status IN ('shown','low_confidence')` 且被抽中的记录。
- 分析师在抽检工作台对每条样本标记 `caliber_correct = true/false`，并选择问题类型。
- 口径正确率 = 抽检样本中 `caliber_correct=true` 的比例，附 Wilson 置信区间；分母为抽检样本量，整体估计时按分层权重（低置信度优先）加权。
- **同时报告**标准测试集回归正确率作为交叉证据；验收时两者并列展示，不互相替代。

### 9.3 标准测试集跑批

- `eval_case` 表存储 `question, expected_dsl, standard_sql, expected_result`。
- 跑批复用与线上完全相同的 `parse_dsl → validate → compile → execute → auto_validate` 链路，但不写 `answer` 表、不触发抽检。
- 结果写入 `eval_run` 表，按 `run_id` 聚合通过率、失败原因分布、与上次跑批的 diff。


## 10. 抽检工作流技术设计

### 10.1 抽样算法

```python
def sample_for_review(week: str, max_rate: float = 0.20) -> list[str]:
    total = count_answers(week)
    target = int(total * max_rate)

    low_conf = fetch_answers(week, confidence="low", status="shown")
    high_conf = fetch_answers(week, confidence="high", status="shown")

    # 低置信度优先：先全部纳入，但不超过 target
    selected = low_conf[:target]
    remaining = target - len(selected)
    if remaining > 0:
        # 按指标分层随机
        selected += stratified_random(high_conf, remaining, strata="metric_id")
    return selected
```

- 低置信度优先是硬规则，保证风险最高的回答优先被人工检查。
- 分层随机按 `metric_id` 分层，避免抽检样本集中在某一个指标上。
- 周重置抽样池，但手动加抽不受周限制。

### 10.2 抽检状态机实现

`review` 表：

```sql
CREATE TABLE review (
  review_id     VARCHAR(64) PRIMARY KEY,
  answer_id     VARCHAR(64) NOT NULL,
  status        VARCHAR(16) NOT NULL,   -- pending / approved / corrected / withdrawn
  reviewer_id   VARCHAR(64),
  problem_type  VARCHAR(32),            -- caliber_error / result_error / chart_issue / conclusion_issue / other
  note          TEXT,
  reviewed_at   DATETIME,
  UNIQUE KEY uk_answer (answer_id)
);
```

状态流转在事务中完成：`pending → approved` 或 `pending → corrected/withdrawn`。撤回/更正时同步更新 `answer.status`，业务用户侧查询时据此展示“已撤回/已更正”。**撤回操作需二次确认**，且 `review` 记录不可删除，只能追加新状态记录（或通过 `review_log` 表记录全量状态变迁），满足质量追溯要求。

### 10.3 问题回写与修复队列

`fix_queue` 表：

```sql
CREATE TABLE fix_queue (
  fix_id        VARCHAR(64) PRIMARY KEY,
  review_id     VARCHAR(64) NOT NULL,
  target_type   VARCHAR(16) NOT NULL,   -- metric / synonym / caliber / join_path / validation_rule
  target_id     VARCHAR(64),
  description   TEXT NOT NULL,
  status        VARCHAR(16) NOT NULL,   -- open / in_progress / resolved
  resolved_at   DATETIME
);
```

抽检发现问题后，分析师选择问题类型并关联配置对象，系统自动创建 `fix_queue` 记录。修复动作本身通过配置管理 API 完成；修复后分析师手动触发测试集回归（P0）或系统自动触发（P1）。**问题不可只存聊天日志**：`fix_queue` 是配置修复的工作入口，而非可选记录。


## 11. 安全与护栏技术设计

| 护栏 | 技术实现 | 参数 |
| :--- | :--- | :--- |
| 只读账号 | 业务库专用 MySQL 账号，仅 `SELECT` 权限，无 `INSERT/UPDATE/DELETE/DDL` | — |
| SQL 执行超时 | 会话级 `SET SESSION max_execution_time = 5000`；应用层 `asyncio.wait_for(6s)` 兜底 | 5 秒 |
| 返回行数上限 | 编译期强制 `LIMIT 1000`；执行后二次检查截断 | 1000 行 |
| 禁止全表扫描 | L1 要求 WHERE 必填；L2 `EXPLAIN` 检查扫描行数，超 50 万标记 `suspicious` | 50 万行 |
| 禁止写操作 | L1 sqlglot AST 白名单；只读账号作为第二层防线 | — |
| 问题长度 | API 层 Pydantic 校验 | 500 字 |
| 单用户频率 | FastAPI 中间件基于 `user_id` 滑动窗口计数 | 默认 20 次/分钟 |
| 会话超时 | Session 表 `expires_at`；中间件校验 | 8 小时 |

**关键原则**：护栏参数（超时、行数上限、频率）存放在 `system_config` 表中，分析师/运维可通过 API 调整，但**超时和行数上限不允许设为“无限制”**——API 层校验参数下限。

## 14. 性能与可观测性

### 14.1 性能目标与分解

| 环节 | 目标 P95 | 技术保障 |
| :--- | :--- | :--- |
| 同义词/指标召回 | ≤100ms | MySQL 索引 + 进程内配置缓存 |
| LLM DSL 解析 | ≤5s | JSON mode；超时 10s；单次调用 |
| DSL 校验 | ≤50ms | 纯内存 Pydantic + 配置缓存 |
| 编译 | ≤120ms | 纯函数，无 I/O；配置缓存预热 |
| SQL 执行 | ≤5s | 只读账号 + `max_execution_time` + `LIMIT` |
| 自动校验（含 L4 基准比对） | ≤2s | L4 仅在 `hit_template` 时执行；基准 SQL 与主 SQL 并行执行 |
| 整体问数 P95 | ≤15s | 上述环节串行主导，LLM 和 SQL 是主要耗时 |

### 14.2 可观测性

- **结构化日志**：每条问数在关键节点输出 JSON 日志，字段包括 `trace_id`、`session_id`、`answer_id`、`stage`、`duration_ms`、`status`。`trace_id` 贯穿 LangGraph 全链路。
- **answer 表即日志**：`dsl_json`、`compiled_sql`、`validation_json`、`retry_count`、`hit_template` 等字段本身就是可追溯记录，不依赖额外日志系统即可回答“当时为什么展示/拦截了这条回答”。
- **关键指标**：首答可用率、L1–L4 各层拦截率、重试成功率、L4 覆盖率、平均 LLM 耗时、平均 SQL 耗时。首期通过定时 SQL 查询 `answer` 表计算，不引入 Prometheus/Grafana。

## 16. 技术风险与应对

| 风险 | 技术表现 | 应对措施 |
| :--- | :--- | :--- |
| LLM JSON 输出不稳定 | DSL 解析失败率偏高 | JSON mode + Pydantic 严格校验 + 一次修复调用；召回候选注入 Prompt 缩小选择空间 |
| 基准 SQL 模板覆盖率不足 | L4 自动比对覆盖率低，口径正确率估计依赖高比例人工抽检 | 第 1 周优先确认 4 指标基准 SQL 对常见维度组合的覆盖；模板未覆盖的组合标记低置信度并优先抽检 |
| 即席组合口径漂移 | 编译器拼装 SQL 与基准口径不一致 | 即席组合强制 `hit_template=False` + `low_confidence=True`；L4 不适用时不展示为 high confidence |
| 20% 抽检估计 95% 的统计不确定性 | 置信区间宽，验收争议 | 验收报告同时给出 Wilson 置信区间和标准测试集回归结果；测试集作为交叉证据 |
| LangGraph 状态图复杂度失控 | 节点膨胀，调试困难 | 严格限定首期为单次问数状态机，不引入工具循环、记忆、多 Agent；节点数与功能编号一一对应 |
| MySQL 版本不支持 `max_execution_time` | 5.7.8 以下版本无法会话级超时 | 部署前确认版本；若不支持，使用应用层 `asyncio.wait_for` + `SHOW PROCESSLIST` 手动 kill 作为降级方案 |
| 配置缓存与数据库不一致 | 配置变更后短时间仍用旧缓存 | 写后主动失效 + TTL 60 秒兜底；配置管理接口返回当前缓存版本号，分析师可感知生效延迟 |

## 18. 技术验收对照

| 验收项 | 技术证据 |
| :--- | :--- |
| LLM 不直接生成 SQL | 意图解析 System Prompt + DSL Schema 约束 + L1 禁止非 SELECT；代码审查确认编译器路径无 LLM 介入 SQL 拼装 |
| 展示前自动校验 100% 覆盖 | `answer.validation_json` 每条记录均含 L1–L4 结果（L4 可标记 `not_applicable`，但不可缺失字段） |
| 口径正确率 ≥95% | L4 自动比对覆盖率 ≥ 约定阈值；抽检估计 + Wilson 置信区间 + 标准测试集回归结果并列报告 |
| 首答可用率 ≥80% | `answer.first_answer_usable` 按 `retry_count=0` 分组统计；判定规则代码可审查 |
| 抽检率 ≤20% | 抽样算法硬上限 + `review` 表按周统计 |
| 只读与护栏 | 业务库账号权限核查；`max_execution_time` 会话设置核查；`LIMIT 1000` 在编译产物中强制注入 |
| 配置可追溯 | `config_version` 快照 + `answer.caliber_version` 关联；历史回答不受配置变更影响 |
| 问题闭环 | `fix_queue` 记录可从 `review` 追溯到配置对象，修复后可回归验证 |


**文档结论**：本技术设计的核心是三条刚性约束的工程落地——**LLM 只输出 DSL、编译器确定性生成 SQL、自动校验是展示硬门禁**。语义层做减法到 5 张表，编排做减法到单次问数状态机，但 DSL Schema、确定性编译器、四层自动校验、基准 SQL 比对、抽检状态机不做减法。第 1 周的端到端 demo 和 4 份基准 SQL 是排期成立的两个硬前置；L4 自动比对覆盖率是口径正确率能否被可信度量的关键变量，应在第 2 周结束前有第一版数据。
