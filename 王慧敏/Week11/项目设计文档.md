---

## 1. 项目背景与动机

传统 BI 的使用门槛高：业务同学想查一个数，要么自己写 SQL，要么提需求排队等数仓/BI 工程师排期，从「想知道答案」到「拿到答案」往往以天计。大模型的出现让「用自然语言直接问数」成为可能——这就是 ChatBI（对话式智能分析）。

本项目的目标是建设一个 **ChatBI 产品/平台**，让非技术用户用一句话获得数据答案，同时保证答案可信、口径一致、权限可控、过程可解释。

本文档的能力模型参考了以 **腾讯云 ChatBI、腾讯 DataTalk（数据说）** 为代表的商业 ChatBI 产品的公开能力（自然语言问数、指标语义层、多轮追问、图表生成、数据洞察/归因、权限管控等），并在此基础上结合课程 Demo 的实际约束做了取舍与落地方案。

> 说明：本文档中标注「对标腾讯 ChatBI」的内容，指上述产品公开宣传的通用能力，不涉及其内部实现细节；具体技术实现以本文档第 6 章及《技术设计文档》为准。

---

## 2. 项目目标

| 维度 | 目标 |
|---|---|
| 业务价值 | 把「取数」从小时/天级降到秒级，降低数据使用门槛，释放数仓/BI 人力 |
| 核心能力 | 自然语言 → 可信的数据答案（表格 + 图表 + 结论），支持多轮追问 |
| 可信保障 | 统一指标口径（语义层）、SQL 只读 + 校验自愈、权限对齐、过程可解释 |
| 平台化 | 多数据源接入、多租户、评测与反馈闭环、可观测，可扩展成私有化/数据不出域部署 |

**一句话定位**：面向业务人员的「会自己写 SQL、懂口径、守权限、还会解释结果」的智能问数助手。

## 3. 目标用户与使用场景

### 3.1 目标用户

| 角色 | 诉求 | 典型问题 |
|---|---|---|
| 业务/运营人员 | 快速看数，不写 SQL | 「上个月华东区 GMV 环比涨了多少？」 |
| 管理层 | 要结论、要趋势、要归因 | 「为什么这个月转化率下降了？」 |
| 数据分析师 | 提效，快速探查 + 复用 | 「帮我按渠道拆一下最近 30 天的复购」 |
| BI/数仓工程师 | 口径治理、指标沉淀 | 「把『活跃用户』这个指标固化下来」 |
| 数据管理员 | 权限、安全、审计 | 「哪些人问过敏感的薪资字段？」 |

### 3.2 使用场景

1. **即时问数（Ad-hoc）**：一句话得到某指标、某维度、某时间范围的结果。
2. **多轮追问**：在上一问基础上追加条件、切换维度、改时间范围（指代消解）。
3. **洞察与归因**：不只给数，还给出「涨跌、异常、原因」。
4. **报告生成**：把多次问答沉淀为一份可分享的分析报告。
5. **指标口径咨询**：问「活跃用户怎么定义的」，返回统一口径。

## 4. 项目范围

### 4.1 范围内（In Scope）

- 自然语言问数（NL2SQL / NL2指标）核心链路
- 指标语义层 / 数据字典（口径、同义词、别名）
- 多轮对话与上下文记忆
- 结果呈现：表格 + 自动选图 + 自然语言结论
- 数据洞察与异动归因（一期做基础版）
- 权限管控（行级/列级 + 敏感字段拦截）
- SQL 安全（只读白名单、改写自愈）
- 反馈闭环与评测体系
- 多数据源接入（一期支持 MySQL/SQLite/PostgreSQL，二期数仓）

### 4.2 范围外（Out of Scope，一期）

- 语音交互、多语言（一期只做中文）
- 复杂预测/机器学习建模
- 实时流式数据的毫秒级问数（一期面向离线/准实时表）
- 完全替代分析师的专业深挖分析

## 5. 能力清单（对标腾讯 ChatBI）

这是本项目要具备的能力全集，按模块分层。详见《功能设计文档》逐条展开。

```
┌─────────────────────────────────────────────────────────────┐
│  A. 交互层    自然语言输入 / 多轮追问 / 澄清反问 / 联想推荐      │
│  B. 理解层    意图识别 / 实体链接 / 指标语义层 / 同义词字典       │
│  C. 生成层    NL2SQL / 指标路由 / SQL生成-校验-改写自愈          │
│  D. 执行层    只读执行 / 权限注入 / 结果取数（分页、降采样）      │
│  E. 洞察层    结果解读 / 图表自动选择 / 异动归因 / 报告生成       │
│  F. 治理层    元数据 / 血缘 / 权限 / 审计 / 评测 / 反馈闭环       │
│  G. 平台层    多数据源 / 多租户 / 可观测 / 成本控制 / 私有化      │
└─────────────────────────────────────────────────────────────┘
```

各层之间的依赖关系：`G(平台) ⊃ F(治理) ⊃ A/B/C/D/E(主链路)`，其中 B/C/D 是「可信问数」的核心，E 是差异化价值，F/G 是规模化前提。

## 6. 与课程 Demo 的关系

课程已实现的 7 阶段 SQL Agent（`chatbi_agents.py`）是本项目 **C 生成层 + D 执行层** 的最小可行原型（PoC）：

| 课程 Demo 阶段 | 对应本产品能力 | 产品化要补的差距 |
|---|---|---|
| Stage1 数据库解析 | F 治理层元数据 | 从「一次性内省」升级为「持续采集 + 血缘 + 变更感知」 |
| Stage2 表选择 | B 理解层实体链接 | 引入指标语义层与同义词，不再只做「表名匹配」 |
| Stage3 SQL 生成 | C 生成层 NL2SQL | 指标路由、Few-shot 库、复杂问题分解 |
| Stage4/5 校验改写 | C 生成层自愈 | 执行计划校验、结果校验、口径校验 |
| Stage6 执行 | D 执行层 | 权限注入、分页、超时与并发控制 |
| Stage7 汇总 | E 洞察层结果解读 | 图表自动选择、异动归因、报告 |

也就是说，**课程 Demo 证明了「链路能跑通」，本产品设计回答「如何做成一个可信、可用、可运营的产品」**。

## 7. 成功指标（OKR）

| 指标 | 定义 | 一期目标 | 备注 |
|---|---|---|---|
| 问答正确率 | 用户点「采纳/点赞」的比例 | ≥ 85% | 人工抽检兜底 |
| 语义准确率 | SQL 语义正确占比（评测集） | ≥ 90% | 见评测体系 |
| 平均响应时长 | 从提问到出答案 | ≤ 10s（P95） | 缓存命中更短 |
| 取数时效提升 | 相对人工取数的耗时比 | ≤ 1/10 | 业务侧访谈 |
| 指标覆盖率 | 已固化指标占高频指标的比 | ≥ 60% | 语义层建设进度 |
| 周活提问数 | 平台每周有效提问 | 目标值按业务定 | 衡量渗透率 |

## 9. 关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 生成 SQL 错误/幻觉 | 答错、误导业务 | 校验-改写自愈 + 语义层约束 + 结果展示附 SQL 可审计 |
| 指标口径不一致 | 同一问题不同答案 | 统一指标语义层，SQL 一律映射到官方口径 |
| 数据安全/越权 | 泄露敏感数据 | 权限注入（行/列级）+ 敏感字段拦截 + 只读白名单 |
| 模型成本与延迟 | 规模化后不可控 | 模型路由（小模型/规则兜底）+ 缓存 + 降级 |
| 用户信任不足 | 低采纳率 | 过程可解释（展示 SQL/口径）+ 反馈纠错闭环 |
| 元数据质量差 | 影响准确率 | 数据字典治理 + 同义词维护 + 血缘校验 |

## 11. 附录：对标产品的公开能力速览

以下为公开渠道可查的商业 ChatBI 通用能力，作为本项目能力清单的来源参考（非内部资料）：

- **自然语言问数**：NL 转 SQL / 转指标，支持时间、维度、过滤、聚合等表达。
- **指标语义层 / 统一指标平台**：预定义指标与口径，问数时优先路由到官方指标，保证一致。
- **多轮对话**：上下文记忆、指代消解、条件追加与撤销。
- **可视化**：自动选择合适图表（趋势→折线、占比→饼、对比→柱）。
- **智能洞察/归因**：自动解读涨跌、检测异常、给出可能原因。
- **权限与安全**：与数仓权限对齐，敏感数据拦截。
- **反馈与评测**：点赞点踩、人工纠错、Few-shot 沉淀、准确率看板。
