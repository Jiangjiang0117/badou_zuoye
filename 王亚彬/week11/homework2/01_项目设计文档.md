## 1. 背景与问题

### 1.1 现有 BI 的断点

| 断点 | 表现 | 代价 |
|---|---|---|
| 学习成本 | 需要会拖拽建模、会写公式 | 业务方等排期，分析师被大量临时取数需求占满 |
| 语义断层 | 系统认识 `order_price`，不认识销售额 | 同一指标不同人算出不同数 |
| 交付断层 | 出图即结束，不给结论 | 用户拿到图还要自己解读 |
| 权限断层 | BI 权限不等于数据库权限 | 要么过宽导致越权，要么过窄干不了活 |

### 1.2 为什么是 Agent 而不是 Text2SQL

Text2SQL 是一次模型调用：问题加表结构进，SQL 出。它在单表统计上够用，在真实业务上失效率高，原因不只在模型：

- 表结构塞不完，大库几十张表上千字段，必须先做表选择
- 生成的 SQL 会语法错，需要执行反馈到改写的闭环
- SQL 跑通了不代表业务含义对，需要静默错误校验
- 用户问的是问题不是 SQL，需要结果到结论的转换

所以 ChatBI 的形态必然是工作流：多步、可控、可观测，而非单次推理。单次模型调用适合简单任务，多步工作流适合可分解的复杂任务，且每一步都能把控。

### 1.3 ChatBI 与通用 Agent 的差异

| 维度 | 通用 Agent | ChatBI 数据 Agent |
|---|---|---|
| 上下文来源 | 用户输入加工具返回 | 数据库元数据、指标口径、历史问答是主要上下文 |
| 核心风险 | 说得不对 | 数算错了，且错误看起来很像对的 |
| 成功标准 | 回答有用 | 结果可复现、可验证、口径一致 |
| 工具形态 | 通用 API | 大量只读查询工具，少量写入需确认 |
| 幻觉成本 | 低，重问一次 | 高，进了报表就是决策依据 |

## 2. 项目目标

### 2.1 业务目标

1. 业务方用自然语言完成 80% 的临时取数与指标查询，无需分析师介入。
2. 关键指标口径统一，一个指标一个公式、一个责任人，跨部门不再对数。
3. 每个结论都可溯源，给出所用 SQL、数据表、时间范围、数据更新时间。

### 2.2 技术目标

| 目标 | 量化 |
|---|---|
| SQL 一次执行成功率 | ≥ 85%，含改写后 |
| SQL 业务正确率 | ≥ 80%，按评测集口径 |
| 首字延迟 | P95 ≤ 2s |
| 单次问答成本 | ≤ ¥0.05 |
| 表选择准确率 | Top-3 命中 ≥ 95% |

## 3. 用户与场景

### 3.1 角色

| 角色 | 诉求 | 关键约束 |
|---|---|---|
| 业务分析师 | 快速取数、导出、做初版图表 | 不懂 SQL，但懂业务口径 |
| 运营与销售 | 看自己范围内的数据 | 只能看本区域或本部门 |
| 管理者 | 要结论和趋势，不要明细 | 关注可信度与口径 |
| 数据工程师 | 维护元数据、指标字典、工具 | 关注接入成本与稳定性 |
| 平台管理员 | 模型、工具、权限、审计 | 关注成本与合规 |

### 3.2 核心场景

| # | 场景 | 输入 | 期望输出 | 难点 |
|---|---|---|---|---|
| S1 | 临时取数 | 上个月华东区销售额 | 数字加 SQL 加口径说明 | 口径歧义，含税与退款处理 |
| S2 | 趋势分析 | 近 3 个月手机销量走势 | 折线图加结论 | 时间窗与粒度 |
| S3 | 排名对比 | 销售额最高的前 5 位艺术家 | Top-N 表 | 多表关联 |
| S4 | 归因 | 为什么 6 月掉了 20% | 拆解维度加假设 | 需要多次查询编排 |
| S5 | 股票分析 | 分析下 600519 最近走势 | K 线图加基本面摘要 | 工具调用与可视化回填 |
| S6 | 文档问答 | 上传 CSV 或 Excel 后提问 | 表格答案 | 文件解析与结构推断 |

## 4. 能力模型

四层能力不是并列清单，而是有依赖顺序的层次，下层缺失会放大上层错误。

### L1 数据理解层

| 能力 | 落地方式 | 判定标准 |
|---|---|---|
| Schema 抽取 | SQLAlchemy `inspect` 取表、字段、类型、主外键 | 覆盖 100% 表，注释缺失时降级为字段名 |
| 数据画像 | 逐字段统计唯一值数、众数、空值率、极值、三个样例值 | 大表采样，单表画像耗时 ≤ 3s |
| 业务语义 | 字段中文名、单位、枚举映射，维护在元数据表 | 关键表 100% 有中文名 |
| 表关系 | 主外键加推断的关联路径与基数 | 能画出实体关系图 |
| 指标字典 | 指标等于公式加口径加粒度加责任人 | 核心指标 ≥ 30 个 |

### L2 语义对齐层

| 能力 | 落地方式 | 失败表现 |
|---|---|---|
| 表选择 | 先输出候选表名 Top-3，再取结构 | 上下文超长，模型乱挑表 |
| 口径澄清 | 命中歧义词时反问，如销售额、活跃、新客 | 自选一种口径，静默算错 |
| 同义词映射 | 业务词典，销量、单量、成交笔数映射到字段 | 生成不存在的字段 |
| 时间解析 | 相对时间转绝对区间，明确时区与闭开区间 | 少算或多算一天 |
| 多轮改写 | 结合会话历史补全指代 | 那上个月呢，被重新理解成新问题 |

### L3 查询执行层

| 能力 | 落地方式 |
|---|---|
| SQL 生成 | 强约束提示只输出 SQL，低温度，声明方言 |
| 静态预检 | `EXPLAIN` 加只允许 SELECT 加禁用 DDL 与 DML 加表白名单 |
| 报错改写 | 把错误信息、原 SQL、问题一起回灌，最多 3 轮 |
| 静默错误校验 | 结果行数、量级、空值、口径与预期比对 |
| 执行防护 | 只读账号、超时 30s、`LIMIT` 兜底、大表强制分区 |
| 沙箱 | 代码解释器任务在容器内执行，禁网禁写 |

### L4 交付与运营层

| 能力 | 落地方式 |
|---|---|
| 流式 | SSE，工具调用过程也推给前端 |
| 可视化 | 时间序列用折线，分类对比用柱状，占比用饼图或堆叠，明细用表格 |
| 可验证 | 展示 SQL、数据源、时间范围、数据更新时间 |
| 反馈 | 赞与踩加一句话原因，差评自动进评测候选集 |
| 评测 | 标准答案四元组，问题、SQL、结果、自然语言答案，加回归集 |
| 权限 | 工具白名单加行级过滤加审计日志 |
| 成本 | token 计数、按用户日配额、简单问题路由小模型 |

## 5. 范围与边界

### 5.1 本期范围

- 单库自然语言查询，支持 MySQL 与 PostgreSQL，开发用 SQLite
- 六个功能模块：用户、对话、数据、股票、MCP 工具中心、评测看板
- 三端：MCP Server 占用 8900，FastAPI 占用 8000，前端采用 Streamlit 或 Next

### 5.2 数据隐私分级

| 级别 | 数据 | 可用模型 |
|---|---|---|
| L0 公开 | 新闻、行情 | 任意云端模型 |
| L1 内部 | 脱敏后的聚合指标 | 公有云模型，关闭训练 |
| L2 敏感 | 明细订单、客户手机号 | 私有化部署模型，或仅出聚合结果 |
| L3 机密 | 薪资、密钥 | 禁止进入大模型，字段级拦截 |

拦截必须发生在数据画像和 SQL 生成之前：敏感字段不进提示词，不出现在结构描述里，出现在 SQL 中被规则拒绝。

## 6. 交付计划与投入

| 里程碑 | 内容 | 产出 | 参考工时 |
|---|---|---|---|
| M1 | 数据理解 | 数据库解析器、元数据表、画像脚本 | 2 天 |
| M2 | 查询链路 | 表选择到生成、预检、改写、执行、汇总，加过程轨迹 | 3 天 |
| M3 | 工具化 | FastMCP 服务，从 FastAPI 导入接口，加工具白名单 | 2 至 3 天 |
| M4 | 后端 | FastAPI 三层结构，routers、services、models，加 SSE | 3 至 4 天 |
| M5 | 前端 | 对话、工具勾选、K 线回填、历史会话 | 1 至 2 天 |
| M6 | 评测与加固 | 标准答案集 200 条，回归脚本，权限审计 | 2 天 |

合计约两周，单人全栈投入。风险最高的两段是 M2 的正确率打磨和 M5 的前端调试，前端联调与测试非常消耗时间。

## 7. 关键决策记录

| # | 决策 | 备选 | 选择理由 |
|---|---|---|---|
| D1 | 开发库用 SQLite | MySQL | 零安装、单文件、易分享；ORM 抽象后切 MySQL 只改连接串 |
| D2 | 自研查询链路 | Vanna、DB-GPT | 需要暴露每一步中间结果做评测与排障，黑盒不可控 |
| D3 | MCP 作为工具协议 | OpenAI function calling | 工具可跨语言跨进程复用，服务端可独立部署与鉴权 |
| D4 | SSE 而非 WebSocket | WebSocket | 单向流式足够，HTTP 兼容性好，前端按块消费即可 |
| D5 | 会话状态用内置 SQLite 会话 | 自己维护历史表 | 省事；但可观测性差，因此业务库同时落一份 |
| D6 | 前端用 Streamlit | Next.js | 内部工具优先交付速度，企业版另起 Next 项目 |
| D7 | 不缓存工具列表 | 缓存工具列表 | 工具频繁迭代期，缓存会导致改了不生效 |
| D8 | 模型可切换加降级 | 固定最强模型 | 兼顾成本与稳定性；换模型会带来效果波动，需回归集兜底 |

## 8. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 静默错误，SQL 对业务错 | 高 | 高 | 口径字典加结果合理性校验，结论附 SQL 供核对 |
| 换模型后效果回退 | 高 | 中 | 每次换模型跑回归集，提示词与模型解耦 |

| 前端体验拖慢交付 | 中 | 中 | 先用 Streamlit 验证闭环，再换正式前端 |
| 成本失控 | 中 | 中 | 按用户配额，简单问题路由小模型，结果缓存 |

## 9. 验收标准

### 9.1 功能验收

- 六个模块主流程可走通，无阻塞性缺陷
- 对话支持多轮、历史切换、流式输出、工具勾选
- 每条回答都能看到 SQL 与数据来源

### 9.2 指标验收

| 档位 | 指标 | 目标 | 数据来源 |
|---|---|---|---|
| 能用 | 接口成功率 | ≥ 99% | 网关日志 |
| 能用 | SQL 执行成功率 | ≥ 85% | 运行轨迹表 |
| 好用 | 首字延迟 P95 | ≤ 2s | 前端埋点 |
| 好用 | 完整回答 P95 | ≤ 15s | 前端埋点 |
| 好用 | 差评率 | ≤ 10% | 反馈表 |
| 敢用 | 业务正确率 | ≥ 80% | 200 条标准答案回归 |
| 敢用 | 越权拦截率 | 100% | 权限测试用例 |
| 敢用 | 结论可溯源率 | 100% | 抽查，必须带 SQL |

没有标注数据时的起步办法：反向构造标准答案，遍历表与字段组合，让模型生成自然语言问题，再生成 SQL 并校验执行，人工抽检 20% 校正，随后逐步替换为真实用户问题。

## 10. 多模型选型结论

| 用途 | 首选 | 备选 | 依据 |
|---|---|---|---|
| SQL 生成，复杂多表 | 强推理模型 | qwen-max | 推理链长，改写次数少 |
| 表选择与轻量意图识别 | qwen-plus 或小模型 | 豆包 | 便宜、快，任务简单 |
| 结果汇总与用户话术 | qwen-max 或豆包 | gpt 系列 | 中文表达自然 |
| 架构评审与方案评审 | ChatGPT | DeepSeek | 分层与失败模式枚举完整 |

路由策略：先判定任务复杂度，看涉及表数量、是否需要聚合或关联。简单问题走小模型，复杂问题走强模型。两者都进同一套预检与改写链路，保证下限。
