## 1. 架构总览

系统分五层。表现层是前端页面，接入层有 FastAPI 与 MCP Server 两个入口，业务层承载对话编排、股票服务、用户服务与查询链路，能力层封装智能体运行时、MCP 客户端、数据库解析器与代码沙箱，数据层存放业务库、对话库与外部工具数据源。

请求路径有两条。用户提问走 HTTP 加 SSE 进入 FastAPI，由对话服务编排智能体，智能体通过 MCP 客户端调用工具服务。工具列表与调试走 MCP 协议直连，不经过业务接口。

三层解耦要点：

| 解耦 | 做法 | 收益 |
|---|---|---|
| 前端与后端 | 只走 HTTP 与 SSE，不共享状态 | 可替换前端实现 |
| 后端与工具 | 走 MCP 协议，不直接引入工具代码 | 工具可独立部署、升级、鉴权 |
| 业务与模型 | 统一模型适配层加环境变量 | 换模型不改业务代码 |

## 3. 数据层设计

### 3.1 业务库表结构

```sql
-- 用户
user(id PK, user_name, user_role, password, register_time, status)
-- 数据源
data(id PK, path, data_type, create_user_id FK->user.id, create_time, alter_time)
-- 自选股
user_favorite_stock(id PK, stock_id, user_id FK->user.id, create_time)
-- 会话，一次对话
chat_session(id PK, user_id FK, session_id, title, start_time, feedback, feedback_time)
-- 消息，一条记录
chat_message(id PK, chat_id FK, role, content, generated_sql, generated_code,
             create_time, feedback, feedback_time)
```

设计要点：

1. 会话标识用 12 位随机串，与自增主键分离，对外不暴露自增 ID。
2. 消息表单独存生成 SQL 与生成代码字段，结果与意图分开存，便于事后审计模型到底查了什么。
3. 反馈字段允许空值，表示未评价，不用布尔默认值代替三态。

### 3.2 元数据表设计

```sql
-- 表级
meta_table(id, datasource_id, table_name, cn_name, row_est, update_freq, owner)
-- 字段级
meta_column(id, table_id, column_name, data_type, cn_name, unit, enum_map,
            is_sensitive, is_pii, distinct_cnt, null_rate, min_val, max_val, sample_values)
-- 关系
meta_relation(id, from_table, from_column, to_table, to_column, cardinality, verified)
-- 指标字典
meta_metric(id, metric_name, synonyms, formula, caliber, grain, owner, status, version)
-- 问答标准答案
eval_case(id, question, gold_sql, gold_result, gold_answer, tables, tags, source, created_by)
-- 运行轨迹
run_trace(id, trace_id, session_id, question, tables_selected, sql_initial, sql_final,
          rewrite_cnt, exec_ms, token_in, token_out, status, error_type, created_at)
```

指标字典是复杂查询正确率的关键资产。口径写在库里，不写在提示词里，因为提示词会随模型漂移，表不会。

### 3.3 数据库解析器

职责是把一个陌生库变成模型能读懂的结构、统计与样例三部分信息。

| 步骤 | 实现 | 产物 |
|---|---|---|
| 列表 | `inspector.get_table_names` | 表名列表 |
| 字段 | `inspector.get_columns` | 名称、类型、是否可空 |
| 外键 | `inspector.get_foreign_keys` | 关系边 |
| 唯一值数 | `count(distinct col)` | 基数，判断是否适合分组 |
| 众数 | `group by col order by count desc limit 1`，仅文本字段 | 最高频值 |
| 空值 | 统计空值条数 | 空值率 |
| 极值 | 最大值与最小值 | 量级参考 |
| 样例 | 去重后取 3 个不同值 | 值样式，模型据此判断格式 |
| 表样例 | 取一行完整记录 | 端到端示例 |

输出给模型的最小上下文形如：

```markdown
| name       | type    | distinct | mode | nan_count | max   | min  | random         |
|------------|---------|----------|------|-----------|-------|------|----------------|
| InvoiceId  | INTEGER | 412      |      | 0         | 412   | 1    | 1, 340, 92     |
| CustomerId | INTEGER | 59       |      | 0         | 59    | 1    | 12, 33, 7      |
| Total      | NUMERIC | 412      |      | 0         | 25.86 | 0.99 | 1.98, 15.86    |
```

工程约束：

- 大表不跑全量唯一值统计，改用近似统计或采样十万行。
- 全库画像结果落缓存表，只在结构变更时重算，否则每次对话都扫库。
- 敏感字段在输出前替换为掩码，样例值不进提示词。

### 3.4 存储选型

| 用途 | 选型 | 原因 |
|---|---|---|
| 开发与演示 | SQLite | 单文件，零安装，便于分享 |
| 生产业务 | MySQL 或 PostgreSQL | 支持远程连接、并发与分布式部署 |
| 会话状态 | 独立 SQLite 文件 | 与业务库隔离，避免互相污染 |
| 向量检索 | 先用表存向量 | 内部知识规模小，暂不引入专用向量库，注意向量库不等于检索增强 |

## 4. 查询链路

### 4.1 七步链路

问题输入后依次经过：解析数据库结构、表选择、SQL 生成、静态预检、失败时改写、执行、结果校验与汇总。

### 4.2 各步输入输出与失败信号

| 步 | 输入 | 输出 | 失败判定信号 | 处理 |
|---|---|---|---|---|
| 1 解析 | 连接串 | 结构明细与简要结构 | 表数超过 30 | 只传简要结构，明细按需二次取 |
| 2 表选择 | 问题加简要结构 | 表名列表 | 返回为空或表名不存在 | 回退全表简要结构，记录表选择失败 |
| 3 生成 | 问题加选中表明细 | SQL 字符串 | 含代码围栏或解释文字 | 用正则抽取 SQL，不重试 |
| 4 预检 | SQL | 通过或错误信息 | 执行计划报错，含写操作，表白名单外 | 进入改写，危险语句直接拒绝并审计 |
| 5 改写 | 问题、SQL、错误信息 | 新 SQL | 改写后仍失败 | 最多 3 轮，超限返回错误分类 |
| 6 执行 | SQL | 列名与数据行 | 超时、行数超限、结果为空 | 超时建议缩小范围，空结果区分真无数据 |
| 7 汇总 | 问题、列名、数据行 | 自然语言结论 | 行数过多，超过 30 行 | 先聚合再喂，不把上千行塞进提示词 |

### 4.3 提示词设计

按步隔离，不一次成 SQL。

```text
# 表选择
从下列表中选出回答该问题所需的表，只输出表名，多个用逗号分隔，不要解释。
<简要结构>
问题：{question}

# SQL 生成
你是 {dialect} 专家。根据给定的表结构生成一条 SQL，只输出 SQL，不要解释。
约束：
- 只允许 SELECT，不允许 UPDATE、DELETE、DROP、ALTER
- 时间范围必须显式写出起止日期
- 指标口径若在下方给出，必须严格遵守
<选中表结构>
<指标口径>
问题：{question}

# 改写
下面的 SQL 在 {dialect} 执行报错，请修正，只输出修正后的 SQL。
<详细结构>
SQL：{sql}
报错：{err}
问题：{question}

# 汇总
根据查询结果回答问题，用简洁的自然语言，不要提 SQL。
若结果为空，说明可能原因；若为单值，给出单位和口径。
问题：{question}
结果列：{cols}
结果行：{rows}
```

设计原则：

1. 一步一职责。生成步不负责解释，汇总步不负责计算。
2. 约束显式化。方言、只读、时间显式、口径优先，都写进提示词，不依赖模型自觉。
3. 温度分离。生成用 0 保证稳定，汇总用 0.3 保证自然。
4. 不写模型特化指令，换模型才能平滑迁移。

### 4.4 静默错误校验

静态预检抓不到的一类错误是 SQL 能跑通、结果非空、业务含义错。五类校验：

| 校验 | 规则 | 示例 |
|---|---|---|
| C1 量级 | 结果与字段画像的极值比对，超出一个数量级即告警 | 销售额两百万，但金额字段最大值只有 25.86，必然是聚合或单位错误 |
| C2 聚合语义 | 检测求和作用在比率、单价、标识类字段上 | 对单价求和得到总单价，无业务含义 |
| C3 时间窗 | 解析 SQL 中的日期字面量，与问题里的时间表达比对 | 问最近一个月，SQL 却从年初开始取数 |
| C4 空值与全表 | 结果为空，或行数等于表行数 | 全表返回说明过滤条件没生效 |
| C5 口径一致 | SQL 过滤条件与指标字典的口径比对 | 字典要求剔除退款，SQL 未过滤退款状态 |

实现方式不依赖人工：

```python
def sanity_check(sql, cols, rows, schema_stats, metric):
    issues = []
    for col in cols:
        stat = schema_stats.get(col)
        if stat and is_sum_like(sql, col) and max_of(rows, col) > stat["max"] * 10:
            issues.append(("C1", f"{col} 结果量级异常"))
    if is_rate_or_price(cols) and "sum(" in sql.lower():
        issues.append(("C2", "比率或单价字段不应聚合"))
    if not time_range_match(sql, question_time):
        issues.append(("C3", "时间窗与问题不一致"))
    if len(rows) == 0:
        issues.append(("C4", "结果为空"))
    if metric and metric["caliber"] and not caliber_in_sql(metric, sql):
        issues.append(("C5", "口径过滤缺失"))
    return issues
```

命中 C1 至 C3 时不直接作答，带着问题再生成一次。命中 C4 时区分真无数据与条件过严，去掉最严条件重试一次，行数变化即说明条件过严。

### 4.5 重试与终止

| 策略 | 值 | 理由 |
|---|---|---|
| 最大改写轮次 | 3 | 第 4 轮起成功率增益低于 2%，成本线性上升 |
| 同一错误重复出现 | 立即终止 | 说明模型卡在同一误解，重试无意义 |
| 总超时 | 60 秒 | 超时返回已得部分加失败原因 |
| 单 SQL 执行超时 | 30 秒 | 防止拖垮数据库 |
| 结果行数上限 | 1000 | 超出提示增加聚合维度 |

### 4.6 过程轨迹

每次运行写一条记录，包含表选择结果、初始 SQL、每轮错误与改写结果、改写次数、执行耗时、输入输出 token 数、错误类型。

## 5. 工具化设计

### 5.1 三种工具来源

| 来源 | 实现 | 适用 |
|---|---|---|
| 装饰器定义 | 加注解、类型标注与文档字符串 | 业务自定义工具，如新闻、语录、天气 |
| 从 FastAPI 导入 | `FastMCP.from_fastapi` | 已有 HTTP 接口直接变工具，不改代码 |
| 从接口描述导入 | 读取外部接口描述文件 | 第三方系统接入 |

```python
mcp = FastMCP.from_fastapi(app=app)
async def setup():
    await mcp.import_server(news_mcp, prefix="")
    await mcp.import_server(saying_mcp, prefix="")
    await mcp.import_server(tool_mcp, prefix="")
mcp.run(transport="sse", port=8900)
```

函数文档字符串就是工具描述，模型靠它判断该不该调用，描述写得含糊等于这个工具不存在。

### 5.2 工具粒度原则

| 原则 | 反例 | 正例 |
|---|---|---|
| 一个工具一件事 | 用类型参数在单个工具里做所有查询 | K 线与基本信息拆成两个工具 |
| 参数语义自解释 | 参数类型只写字符串 | 周期限定为枚举值 |
| 返回值结构化 | 返回长字符串 | 返回可读文本加结构化数据两部分 |
| 失败给空而不抛异常 | 直接抛 500 | 捕获后返回空列表，模型可继续推理 |
| 保持无状态 | 工具内缓存用户状态 | 用户状态由后端管，工具只做数据访问 |

### 5.3 传输与连接

| 方式 | 场景 | 配置 |
|---|---|---|
| stdio | 本地进程，如 SQLite 工具服务 | 指定命令与参数，客户端拉起子进程 |
| SSE | 本地或内网长连接 | 直连服务地址 |
| 流式 HTTP | 对外服务推荐 | 支持请求头鉴权、重试与超时 |

```python
MCPServerStreamableHttp(
    name="HTTP Server",
    params={"url": url, "headers": {"Authorization": f"Bearer {token}"}, "timeout": 10},
    cache_tools_list=True,
    max_retry_attempts=3,
    client_session_timeout_seconds=20,
)
```

对外服务推荐流式 HTTP，支持请求头鉴权与超时控制。开发期不缓存工具列表，否则服务端新增工具后客户端无法感知。工具稳定后再开启缓存降低握手开销。

### 5.4 鉴权与权限

| 层 | 手段 |
|---|---|
| 传输层 | 请求头携带令牌，服务端中间件校验 |
| 工具层 | 按允许列表过滤可用工具，前端勾选即白名单 |
| 业务层 | 工具内部按用户身份过滤数据行 |
| 审计 | 每次调用记录用户、工具、参数与耗时 |

三层各自负责不同问题：传输层确认身份，工具层控制能用什么，业务层限定能看哪些行。

## 6. 智能体编排

### 6.1 两种模式切换

```python
if not tools:
    agent = Agent(name=..., instructions=..., model=..., model_settings=ModelSettings(parallel_tool_calls=False))
    result = Runner.run_streamed(agent, input=content, session=session)
else:
    async with mcp_server:
        behavior = "stop_on_first_tool" if viz_tool_selected else "run_llm_again"
        agent = Agent(name=..., instructions=..., mcp_servers=[mcp_server], tool_use_behavior=behavior)
        result = Runner.run_streamed(agent, input=content, session=session)
```

| 行为 | 语义 | 适用 |
|---|---|---|
| 结果回灌再总结 | 工具结果重新喂模型生成结论 | 需要解释的数据查询 |
| 首个工具即答案 | 第一个工具结果作为最终答案，跳过后续工具 | K 线这类结果本身就是答案的工具 |

首个工具即答案会跳过后面的工具调用，因此只在单选可视化工具时使用。

### 6.2 提示词模板化

```jinja2
你是一位名叫 {{ agent_name }} 的专业人工智能。
你的核心任务是 {{ task_description }}
## 基本信息
 当前日期和时间: {{ current_datetime }}
 用户语言偏好: {{ user_language | default('中文') }}
```

按任务类型注入不同任务说明，股票分析、数据 BI、闲聊三套，实现一套代码三种人格。股票任务里显式要求说明数据来源与模型局限，并声明不构成投资建议，合规约束写进提示词，不靠人提醒。

### 6.3 流式事件处理

```python
async for event in result.stream_events():
    if event.type == "raw_response_event":
        if isinstance(event.data, ResponseTextDeltaEvent):
            yield event.data.delta
        if isinstance(event.data, ResponseOutputItemDoneEvent) and isinstance(
            event.data.item, ResponseFunctionToolCall
        ):
            yield "\n```json\n" + event.data.item.name + ":" + event.data.item.arguments + "\n```\n"
```

前端消费两个通道：正文渲染与工具参数解析。工具调用过程对用户可见，用户能看到智能体到底查了什么，这是让用户敢用的前提。

### 6.4 记忆管理

| 方式 | 实现 | 优缺点 |
|---|---|---|
| 框架会话 | 内置 SQLite 会话，按会话标识区分 | 省事，内部不透明，难做精细控制 |
| 业务库 | 消息表全量存储 | 可审计可回放，需手工截断 |
| 上下文控制 | 只取最近 10 轮 | 过长会让模型忘记最初信息 |

两套并行：框架会话负责喂模型，业务库负责给用户看和审计，两者用同一个会话标识关联。

## 7. 后端接口设计

### 7.1 分层

```
routers/   参数校验、调服务、包响应，不含业务逻辑
services/  业务编排，对话、股票、用户
models/    请求响应契约与表映射
agent/     查询智能体与股票智能体实现
api/       底层数据源，行情、新闻、语录、工具
```

### 7.2 流式响应

```python
@router.post("/")
async def chat(req: RequestForChat) -> StreamingResponse:
    async def gen():
        async for chunk in chat_services.chat(...):
            yield chunk
    return StreamingResponse(gen(), media_type="text/event-stream")
```

优势是生成一块推一块，首字延迟低；同步模式必须等全部生成完再返回。注意流式响应期间不要加会缓冲的中间件，否则会攒够才发。

### 7.3 错误处理约定

```python
try:
    ...
except Exception:
    print(traceback.format_exc())
    return BasicResponse(code=500, message=type(e).__name__, data=[])
```

日志留全栈，响应只给异常类型，不把 SQL、库名、表结构泄露给前端。

## 8. 前端设计

| 机制 | 用途 |
|---|---|
| 会话状态消息列表 | 当前会话消息缓存 |
| 会话标识 | 关联后端会话，切换即拉历史 |
| 带过期时间的缓存 | 缓存工具列表，避免每次重连 |
| 多选组件 | 工具白名单 |
| 占位符增量刷新 | 流式打字机效果 |
| 异步运行入口 | 在同步渲染流中执行异步客户端 |

已知问题：Streamlit 的样式与页面逻辑写在一起，定制受限；前端联调与测试耗时明显。因此先用 Streamlit 验证闭环，正式版再换 Next.js。

## 9. 评测体系

### 9.1 标准答案构造

采用反向生成法：

```
for table in tables:
  for field in 字段组合，取 1 至 3 列:
    ① 生成提问，给出表名、字段、样例与结构，让模型扮演用户提问
    ② 生成 SQL
    ③ 静态预检，失败丢弃
    ④ 执行，只保留单值结果，多行丢弃避免歧义
    ⑤ 改写提问，去掉表名，更像人话
    ⑥ 改写答案为自然语言
    ⑦ 存为问题、表名、SQL、结果、自然语言答案五元信息
```

规模建议先做 200 条，取 5 张核心表每张 40 条，人工抽检 20% 校正。

### 9.2 指标

| 指标 | 定义 | 门槛 |
|---|---|---|
| 执行准确率 | 可执行且结果与标准一致，数值容差 ±0.5% | ≥ 80% |
| 表选择召回 | 正确表出现在候选前三 | ≥ 95% |
| 改写效率 | 一轮内改写成功的占比 | ≥ 70% |
| 静默错误率 | 结果错但未触发告警的占比 | ≤ 5% |
| 延迟 P95 | 端到端耗时 | ≤ 15 秒 |

### 9.3 轨迹评测

单点指标不够，多步任务需对轨迹打分。做法是人工标注理想轨迹，即选哪些表、调用哪个工具、中间结论是什么，用步骤匹配率衡量。不要求每一步都对，只判定是否走了致命弯路。

### 9.4 报告类任务评测

无标准答案的任务按四个维度打分：

| 维度 | 打分方式 |
|---|---|
| 完整性 | 覆盖的必要小节数除以应有小节数 |
| 逻辑性 | 结论与数据是否因果一致，人工 1 至 5 分 |
| 深度 | 是否给出归因与建议，而非罗列指标 |
| 排版美观 | 结构、表格、图表使用是否得当 |

这类任务不需要标准答案数据集，需要的是评测标注标准，即明确什么是好报告，什么是坏报告。

## 10. 安全与合规

| 风险 | 手段 | 落地位置 |
|---|---|---|
| 越权取数 | 行级权限注入，在 SQL 后追加范围过滤 | 执行前，不靠提示词 |
| 危险 SQL | 语法树白名单，仅允许查询，禁用建删改与导出文件 | 预检步 |
| 拖库 | 只读账号加 30 秒超时加强制行数上限 | 连接层与预检 |
| 敏感字段外泄 | 敏感标记字段不进结构描述、不进样例，出现在 SQL 中即拒绝 | 元数据层 |
| 数据出网 | 按分级选模型，L2 以上私有化部署，关闭供应商训练 | 模型配置 |
| 代码执行 | 容器内运行，禁网、只读挂载、超时 | 沙箱 |
| 写入误操作 | 生成待确认操作，人工确认后执行 | 工具层 |
| 审计缺失 | 记录用户、问题、SQL、结果、耗时与 token 数 | 运行轨迹表 |

敏感信息红线：薪资、密钥、密码等不得进入大模型，在采集侧拦截，不依赖模型自觉。

## 11. 部署

```yaml
services:
  mcp:
    command: python main_mcp.py
  api:
    command: uvicorn main_server:app --host 0.0.0.0 --port 8000
    environment:
      - OPENAI_BASE_URL
      - OPENAI_MODEL
  web:
    command: streamlit run demo/streamlit_demo.py
  db:
    # 生产用 MySQL，开发挂载 SQLite 文件
```

| 环境变量 | 说明 |
|---|---|
| `OPENAI_API_KEY` 与 `OPENAI_BASE_URL` | 模型接入，必须走密钥管理，不入库不入仓 |
| `OPENAI_MODEL` 与 `OPENAI_VISON_MODEL` | 默认模型与多模态模型 |
| `MCP_SERVER_URL` | 工具服务地址 |
| `DATABASE_URL` | 业务库连接串 |

启动顺序为数据库、工具服务、后端、前端。前端启动即拉工具列表，工具服务未启动时自动降级为纯对话。

密钥必须走环境变量或密钥管理服务，仓库加忽略规则与密钥扫描钩子。开发期把密钥写进源码只适合本地验证，不能进入版本库。

## 12. 性能与成本

| 项 | 量级 | 优化 |
|---|---|---|
| 表选择 | 一次小模型调用 | 表数少于 5 张时跳过 |
| SQL 生成 | 一次强模型调用 | 同问同参数 5 分钟内复用结果 |
| 改写 | 0 至 3 次 | 收敛死循环，按错误类型命中已知修法 |
| 汇总 | 一次小模型调用 | 单值结果用模板直出，不调模型 |
| 单次成本 | 约 2000 至 6000 token | 简单问题路由小模型，可降 60% |

并发方面，内部 100 人使用峰值低于 1 QPS，同步阻塞式足够；对外服务需异步化改造。
