# ChatBI / Data Agent 能力建设 —— 与 LLM 的多轮对话记录

> 对话对象：DeepSeek（deepseek-v4-flash），通过 API 实际调用

> 时间：2026-10-20


## 第 1 轮

**问**：我们要做一个面向企业内部用户的 ChatBI / Data Agent 项目（自然语言问数、自动出图表和结论）。第一轮讨论：这类项目相比传统 BI，核心价值是什么？一个成熟的 ChatBI 产品需要具备哪些核心能力？请从【数据理解、语义层、NL2SQL、查询执行、可视化、结果解释、准确性保障、安全权限】等维度系统梳理，每个能力点说明：为什么需要、做不好会怎样。

**答**：

## 一、先给结论：ChatBI 的核心价值不是“聊天框”，而是压缩“问题→可信答案”的链路

传统 BI 的核心是：**把稳定的业务问题固化成报表/看板，靠排期交付，靠权限和口径治理保证一致性**。  
ChatBI 的核心是：**让业务用自然语言直接提出长尾、临时、探索性问题，在受控语义层和权限体系下即时得到图表、结论和依据**。

一句话对比：

| 维度 | 传统 BI | ChatBI / Data Agent |
|---|---|---|
| 交互方式 | 拖拽、固定报表、看板 | 自然语言、多轮追问、任务式分析 |
| 交付链路 | 提需求→排期→开发→验收 | 即问即答，分钟级 |
| 覆盖场景 | 高频、稳定、合规、规模化报表 | 长尾、临时、探索、解释、下钻 |
| 输出形态 | 图表、报表、看板 | 图表 + 结论 + 依据 + 可追溯 SQL/口径 |
| 用户门槛 | 需要一定数据技能 | 业务人员可直接使用 |
| 核心风险 | 口径分散、需求积压 | 答错放大、越权、幻觉、不可追溯 |
| 定位 | 确定性分析的“骨架” | 探索式分析的“入口和助手” |

**成熟 ChatBI 的价值主张应该是：**
1. **降低使用门槛**：业务不需要知道表名、字段名、SQL。
2. **缩短需求链路**：临时问题从“周级排期”变成“分钟级自助”。
3. **覆盖长尾需求**：传统 BI 覆盖不到的大量临时分析。
4. **支持多轮探索**：追问、下钻、对比、归因，而不是一次性查数。
5. **输出结论而不只是图表**：给关键变化、异常、驱动因素和限制条件。
6. **沉淀语义资产**：问数反馈反哺指标口径、同义词、业务知识。
7. **治理前置**：权限、口径、审计在查询链路中统一控制。

但要明确边界：**ChatBI 不替代财务对账、监管报送、高频固定报表等强确定性场景**；它更适合“分析辅助和探索入口”。成熟产品的竞争力不是模型参数，而是：**语义层覆盖度 × 查询执行可靠性 × 解释可信度 × 权限合规性 × 运营闭环**。

## 二、成熟 ChatBI 的核心能力地图

下面按你给的维度展开，每个能力都说明“为什么需要”和“做不好会怎样”。另外补充两个容易被低估的维度：**意图理解与对话管理**、**运营与评测闭环**。

---

### 1. 数据理解与知识构建

**关键能力：**
- 物理元数据：表、字段、类型、注释、主外键、枚举值、样例数据、空值率、更新频率、血缘、数据质量。
- 业务知识：指标定义、同义词、业务实体、组织架构、时间口径、常见问法、业务域知识。
- 检索与 Schema Linking：把“销售额”“大客户”“上月”映射到正确的表、字段、过滤条件和时间范围。

**为什么需要：**  
自然语言天然模糊。用户说“上个月大客户销售额”，系统必须知道“上个月”是自然月还是滚动 30 天、“大客户”按什么标签、“销售额”是含税还是不含税、退款是否抵扣。没有数据理解，NL2SQL 就是猜。

**做不好会怎样：**
- 选错表、选错字段、join 错，结果看似合理但完全错误。
- 同名不同义，各部门口径打架。
- 复杂问题无法拆解，频繁答非所问。
- 用户第一次问错后失去信任，再也不会用。

**产品要求：**  
元数据自动采集 + 知识后台可运营 + 同义词/口径版本化 + 低置信度主动澄清。

---

### 2. 语义层 / 指标层

**关键能力：**
- 统一指标、维度、实体关系、聚合方式、时间粒度、派生指标、过滤条件、同义词、别名。
- 指标与权限绑定：指标级、维度级、行级、列级权限。
- 语义查询能力：用户问题先转成“指标 + 维度 + 过滤 + 排序 + 粒度”的语义查询，再编译成 SQL。

**为什么需要：**  
语义层是 ChatBI 准确性的天花板。生产环境不建议让大模型直接自由生成 SQL，而应优先走：**NL → 语义查询 → SQL 编译器**。自由 SQL 只放在受控沙箱或分析师模式。这样口径可复用、可审计、可权限控制。

**做不好会怎样：**
- 同一个“销售额”每次生成的 SQL 口径不同。
- 指标无法复用，问数结果不可审计。
- 权限绕过语义层，出现越权查询。
- 业务不信任，ChatBI 退化成“SQL 生成器玩具”。

**验收标准：**  
核心业务域指标覆盖率高、指标唯一口径、语义查询可解释、权限可下推。

---

### 3. 意图理解与对话管理

**关键能力：**
- 意图分类：问数、趋势、对比、排名、归因、异常、解释、导出、操作。
- 歧义澄清：时间范围、指标、维度、过滤条件、聚合粒度不明确时主动追问。
- 多轮上下文：指代消解、继承上一轮过滤条件、支持下钻和追问。
- 任务规划：复杂问题拆成多步查询，先查整体再拆维度。

**为什么需要：**  
企业用户的问题往往不完整。“为什么华东跌了”背后需要先确认指标、时间、对比基准，再查趋势、拆维度、看贡献度。没有对话管理，系统只能猜。

**做不好会怎样：**
- 频繁反问，体验差；或者不反问直接猜错。
- 多轮对话丢失上下文，用户要重复描述。
- 把“归因”当成普通查询，只给一张图没有解释。
- 高风险问题缺少确认，直接给出误导结论。

**原则：**  
**澄清优先于猜测**；低置信度、高风险、权限敏感问题必须确认。

---

### 4. NL2SQL / 查询规划

**关键能力：**
- Schema Linking、Join 路径选择、查询分解、聚合与去重、时间边界处理、窗口函数、TopN、同环比。
- SQL 方言适配、AST 校验、Dry Run、成本预估、结果合理性检查。
- RAG Few-shot、规则约束、语义层编译、错误修复重试。

**为什么需要：**  
自然语言最终要变成可执行、可审计的查询。复杂问题还涉及多表 join、子查询、指标聚合和权限过滤。

**做不好会怎样：**
- SQL 语法错、笛卡尔积、重复计数、时间边界错。
- 复杂问题不会拆，简单问题生成低效 SQL。
- 查询拖垮生产库，或返回截断结果导致错误结论。
- 错误 SQL 不可解释，无法定位和修复。

**架构建议：**  
生产默认走“语义层受控查询”；自由 SQL 只对分析师开放，并放在只读、限流、沙箱环境。LLM 负责理解、规划和修复，不负责绕过治理。

---

### 5. 查询执行与数据接入

**关键能力：**
- 多数据源连接器、引擎路由、下推执行、预聚合、缓存、队列、限流、超时、资源组。
- 结果集大小控制、采样、异步查询、数据快照、执行计划预览。
- 只读账号、最小权限、生产库保护。

**为什么需要：**  
企业数据源多、数据量大、权限复杂。ChatBI 会产生大量临时查询，不能像报表一样只跑固定 SQL。

**做不好会怎样：**
- 查询慢、超时，用户等不及。
- 大查询拖垮生产库，影响核心业务。
- 结果被截断但用户不知道，得出错误结论。
- 并发不可控，成本失控。

**产品要求：**  
执行网关统一管控：**限流、超时、成本预估、结果上限、缓存、审计**一个不能少。

---

### 6. 可视化

**关键能力：**
- 根据问题意图和数据形状推荐图表：趋势用线图、分类对比用柱状图、占比谨慎用饼图/堆叠图、分布用直方图/箱线图、相关用散点图。
- 编码映射、聚合粒度、排序、TopN、颜色、注释、交互下钻、导出、移动端适配。
- 支持从图表继续追问。

**为什么需要：**  
业务用户不一定懂图表语法。错误图表比没有图更危险，会直接误导决策。

**做不好会怎样：**
- 饼图切太多、双轴误导、截断坐标轴、维度错、聚合错。
- 图表好看但表达错误，用户得出相反结论。
- 不可交互，无法下钻，分析链路断掉。

**原则：**  
图表选择优先服务“问题意图”，不是追求炫酷；关键图表要标注口径、时间范围和过滤条件。

---

### 7. 结果解释与洞察

**关键能力：**
- 自动摘要：回答“是什么、变化多少、和谁比、哪里异常”。
- 关键驱动：贡献度、TopN 变化、结构变化、异常点。
- 对比基准：环比、同比、目标、行业/组织对比。
- 可信解释：引用 SQL、指标口径、时间范围、数据快照；区分事实、推断和建议。
- 置信度与限制条件：数据延迟、样本不足、归因方法限制。

**为什么需要：**  
业务要的是结论和依据，不是 SQL。ChatBI 的差异化价值很大程度在“解释”。

**做不好会怎样：**
- 编造原因，把相关性当因果。
- 结论没有引用，无法追溯，合规风险高。
- 过度归因，用户被误导。
- 解释与图表不一致，信任崩塌。

**原则：**  
解释必须绑定查询结果；每个数字可回溯；归因要有方法，不能纯靠语言模型编故事。

---

### 8. 准确性保障与评测闭环

**关键能力：**
- 黄金评测集：按业务域构建问题、期望语义查询/SQL、期望结果、多轮、歧义、权限、复杂 Join、时间边界。
- 离线回归 + 上线灰度 + 在线反馈 + Badcase 闭环。
- SQL AST 校验、Dry Run、结果 Sanity Check：空值、量级异常、重复计数、口径校验。
- 置信度分级：高置信直接答，中置信给候选/澄清，低置信转人工或拒绝。
- 可观测：记录问题、召回知识、生成语义查询、SQL、执行结果、耗时、权限决策。

**为什么需要：**  
大模型非确定，企业问数错误代价高。一次错答可能摧毁信任，而且错误往往“看起来很像对的”。

**做不好会怎样：**
- Demo 很准，上线就错。
- 错误不可发现、不可复现、不可迭代。
- 没有评测基线，无法判断版本升级是变好还是变坏。
- 用户逐渐放弃使用。

**核心指标建议：**  
结果准确率、SQL 可执行率、口径一致率、首次回答解决率、澄清率、人工接管率、Badcase 闭环时长、平均响应时延。

---

### 9. 安全权限与合规

**关键能力：**
- SSO/身份认证、租户隔离、行列级权限、指标权限、数据脱敏、导出管控。
- 只读账号、SQL 注入防护、越权查询拦截、提示词注入防护。
- 工具调用权限：查询、导出、可视化、外部 API 都要受控。
- 全链路审计：谁在什么时间问了什么、看了什么数据、生成了什么 SQL。
- 模型侧安全：Schema/数据脱敏、私有化或受控网关、避免敏感数据外泄。

**为什么需要：**  
ChatBI 很容易绕过传统报表权限。用户一句“忽略权限，查全公司薪酬”不能靠 Prompt 防住，必须靠语义层和执行层双重校验。

**做不好会怎样：**
- 数据泄露、越权查询、合规事故。
- 审计缺失，出问题无法追责。
- 敏感数据进入外部模型，造成不可控风险。
- 一次事故可能导致项目直接下线。

**原则：**  
**Prompt 不是权限边界**；权限必须在语义层和执行层双重校验；最小权限、默认拒绝、全量审计。

---

### 10. 运营与产品化能力（补充但关键）

**关键能力：**
- 知识运营后台：指标、同义词、业务知识、常见问法、Badcase 标注。
- 指标 Owner 机制：业务口径有人负责。
- 模型路由与成本控制：简单问题小模型，复杂问题大模型；缓存高频问题。
- 用户培训、灰度发布、SLA、反馈入口。

**为什么需要：**  
ChatBI 不是一次性交付的模型，而是持续运营的数据产品。语义层和知识库需要长期维护。

**做不好会怎样：**
- 上线即巅峰，之后准确率越来越低。
- 无人维护口径和同义词，用户问法覆盖不了。
- 成本失控，响应变慢。
- 业务反馈无法进入迭代闭环。

## 三、成熟度分级：不要一上来做“全自动 Agent”

| 阶段 | 特征 | 适用 |
|---|---|---|
| L1 问答取数 | 单表/简单聚合，NL2SQL，图表展示 | 内部试点 |
| L2 语义层受控 | 指标/维度统一，多表 Join，权限下推，可追溯 | 生产可用起点 |
| L3 多轮分析 Agent | 任务规划、下钻、对比、归因、解释、澄清 | 成熟 ChatBI |
| L4 主动洞察 | 异常监控、主动推送、协作、行动建议 | 进阶 |

多数企业第一年目标应是 **L2 稳定 + 局部 L3**，而不是追求全自动自由 SQL。

---

## 四、第一轮建议先对齐的 5 个决策

1. **定位**：ChatBI 先做“长尾探索和解释入口”，不替代固定报表和强合规场景。
2. **架构**：语义层优先，生产默认 `NL → 语义查询 → SQL 编译`；自由 SQL 放受控沙箱。
3. **准确性**：先建评测集和 Badcase 闭环，再扩场景；低置信度澄清优先于猜测。
4. **权限**：语义层 + 执行层双重校验，全链路审计；Prompt 不能作为权限边界。
5. **运营**：指标和知识必须有 Owner，建立反馈标注、灰度发布和回归评测机制。

**总结一句：**  
ChatBI 的产品壁垒不在“能聊天”，而在“**问得懂、查得准、跑得稳、解释得清、权限守得住、错误可迭代**”。传统 BI 是确定性分析的骨架，ChatBI 是探索式分析的入口，两者是互补关系。


## 第 2 轮

**问**：第二轮讨论：聚焦 NL2SQL 准确率这个最大痛点。请给出工程上提升准确率的具体手段清单，包括但不限于：schema 召回与表选择、schema linking、few-shot 与 RAG 检索相似问答、SQL 校验与自动修复（self-correction）、语义层/指标层、用户确认交互、评测集建设等，并说明每项手段的成本收益和优先级。

**答**：

## 一、先纠正一个常见误区：NL2SQL 准确率不是“模型能力问题”，而是“链路工程问题”

上线前建议先做一件事：**人工归因 200–500 条真实 Badcase**，按错误类型统计。经验分布大致如下（需按你的业务实测）：

| 错误类型 | 经验占比 | 主要手段 |
|---|---|---|
| 选错表 / 字段 / 指标 | 30–40% | 语义层、元数据增强、Schema 召回、Schema Linking |
| 口径 / 业务语义错 | 20–30% | 指标层、同义词、澄清交互 |
| Join / 聚合 / 去重错 | 15–25% | Join 路径预置、SQL 校验、Few-shot |
| 时间 / 过滤条件错 | 10–15% | 时间口径规则、值识别、澄清 |
| 语法 / 执行错 | 5–10% | AST 校验、Dry Run、自修复 |
| 结果截断 / 展示错 | 5% | 执行护栏、结果校验 |

**结论：准确率的钱要花在“语义资产 + 上下文召回 + 校验护栏”上，而不是只调 Prompt。** 只调 Prompt 的边际收益很快见顶。

另一个架构判断：**生产环境默认走“NL → 语义查询 → SQL 编译”，LLM 不直接自由写 SQL。** 自由 SQL 只作为分析师模式或长尾兜底，放在只读沙箱里。这一条决定了准确率的上限。

---

## 二、手段清单：成本、收益、优先级

优先级定义：**P0 = 不做就不具备生产可用性；P1 = 显著提升准确率/体验；P2 = 规模化后值得做。**

### A. 数据与语义资产层

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **A1 语义层/指标层** | 核心指标、维度、实体、聚合方式、时间口径、过滤条件、同义词、Join 路径固化；NL→语义查询→SQL 编译 | 中高（建模+业务 Owner） | **极高**，口径一致性和准确率提升最大 | **P0** | 只覆盖核心域，别追求全量；指标必须有唯一 Owner |
| **A2 元数据增强** | 表/字段中文名、业务别名、注释写清“是什么/怎么算/注意什么”、枚举值字典、样例值、主外键、数据量级、更新时间 | 低 | **高**，投入产出比最高 | **P0** | 注释质量决定 Schema Linking 质量；枚举值要内联进上下文 |
| **A3 Join 路径图谱** | 预置实体关系和标准 Join 路径，避免模型自行猜关联 | 中 | 高，直接减少 Join 错和笛卡尔积 | **P0（核心域）** | 多对多关系、事实表-维度表要标清 |
| **A4 业务规则库** | 时间口径（自然月/滚动 30 天）、含税/不含税、退款抵扣、去重规则、特殊过滤 | 低中 | 高 | **P0** | 规则要版本化，变更要可追溯 |

### B. 上下文召回与 Schema Linking

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **B1 业务域路由** | 先把问题分类到业务域（销售/财务/供应链），再域内召回 | 低中 | 高，避免全库 Schema 塞 Prompt | **P0** | 规则 + 小模型分类即可，不必上大模型 |
| **B2 表级召回** | 向量检索 + 关键词 + 业务标签，召回 TopK 表，再精排 | 中 | 高 | **P0** | 召回率优先，TopK 要给足；漏表是硬伤 |
| **B3 字段级 Schema Linking** | 用户词→字段/指标/枚举值映射；同义词表；值识别（“华东”→region='华东'） | 中 | 高 | **P0/P1** | 实体识别 + 向量 + LLM 重排组合；值识别对过滤条件很关键 |
| **B4 Schema 裁剪与表示** | 只给相关表和字段；DDL 精简；列名带注释和类型；枚举值内联；标注 Join 提示 | 低 | 高 | **P0** | 控制 Token；无关表越少越准；别把全库 DDL 一股脑塞进去 |
| **B5 多轮上下文管理** | 指代消解、继承上轮过滤条件、下钻、对比基准继承 | 中 | 中高（多轮场景） | **P1** | 要显式展示“当前继承的条件”，允许用户改 |

### C. 生成策略

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **C1 结构化 Prompt** | 角色、Schema、业务规则、输出格式、禁止事项、自检清单 | 低 | 中高 | **P0** | 输出格式强约束（JSON/语义查询结构），便于校验 |
| **C2 Few-shot RAG** | 建“问题→语义查询/SQL→结果”库，按业务域+相似度检索 3–5 条 | 中 | 中高 | **P1** | 质量比数量重要；要覆盖易错模式（时间、去重、TopN）；冷启动需人工构造 |
| **C3 分步生成** | 先识别指标/维度/时间/过滤→再生成查询→再自检 | 低中 | 中高 | **P1** | 中间结果可展示给用户确认，降低黑盒感 |
| **C4 模型路由** | 简单问题小模型，复杂多表用强模型 | 中 | 中（成本+时延） | **P2** | 先保证准，再谈省 |
| **C5 多候选 + 投票/重排** | 生成 3–5 个候选，用执行结果一致性或重排模型选优 | 高（成本×N） | 中 | **P2** | 只对高价值/高难度问题开；否则成本失控 |
| **C6 SQL 方言适配** | 按引擎适配函数、日期、LIMIT 语法 | 低 | 中 | **P0** | 方言错会直接执行失败 |

### D. 校验与修复

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **D1 AST/SQL 静态校验** | 语法、表列存在性、类型、聚合/Group By 一致性、笛卡尔积检测 | 低 | **高**，可执行率从 ~90% 提到 ~98% | **P0** | 用成熟 SQL Parser，别自己写 |
| **D2 权限过滤强制注入** | 行列级权限、租户隔离在编译层自动注入 | 低中 | 高（准确+合规） | **P0** | Prompt 不是权限边界 |
| **D3 Dry Run / EXPLAIN** | 执行计划、成本预估、超时预判 | 低 | 中高 | **P0** | 防止大查询拖垮库，也提前发现错表 |
| **D4 自修复 Self-correction** | 执行失败/空结果/异常时，把错误信息回灌，重试 1–2 次 | 中 | 中 | **P1** | **有风险**：可能把对的改错；必须限次数、保留历史、对比 diff |
| **D5 结果 Sanity Check** | 空结果、量级异常、NULL 比例、重复计数、时间范围、TopN 占比 | 低 | 中高 | **P1** | 触发澄清或标注“结果可能异常”，不要直接给结论 |
| **D6 置信度分级** | 高置信直接答；中置信给候选/澄清；低置信转人工或拒绝 | 中 | 高 | **P1** | 没有置信度分级，就只能“全信”或“全不信” |

### E. 交互确认

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **E1 理解回显** | 展示“我理解的是：指标 X、时间 Y、过滤 Z、粒度 W”，一键修正 | 低 | **高**，低成本兜底 | **P0** | 这是最便宜的准确率保险 |
| **E2 分级澄清策略** | 只在歧义、低置信、高风险、权限敏感时追问；其余直接答 | 中 | 高 | **P0** | 问太多会烦，问太少会错；要定阈值 |
| **E3 候选方案选择** | 给出 2–3 种口径/时间解释让用户选 | 低中 | 中 | **P1** | 适合“销售额”这类多口径词 |

### F. 评测与运营闭环

| 手段 | 具体做法 | 成本 | 收益 | 优先级 | 关键注意 |
|---|---|---|---|---|---|
| **F1 黄金评测集** | 分业务域、分难度、分题型（单表/多表/同环比/归因/歧义/权限/多轮），300–1000 条 | 中 | **长期最高** | **P0** | 要有“期望结果”而不只是“期望 SQL”；口径类要人工确认 |
| **F2 回归门禁 + 灰度** | 每次改 Prompt/模型/语义层都跑回归；新版本灰度 | 中 | 高 | **P0** | 没门禁的迭代就是赌博 |
| **F3 全链路可观测** | 记录召回结果、Prompt、语义查询、SQL、执行结果、耗时、权限决策、用户反馈 | 中 | 高 | **P0** | 错误不可复现就无法迭代 |
| **F4 Badcase 周会闭环** | 每周归因、进评测集、补知识/同义词/Few-shot | 低中（组织成本） | 高 | **P0** | 这是准确率持续爬坡的唯一机制 |
| **F5 用户反馈按钮** | 赞/踩 + 原因标签 | 低 | 中 | **P1** | 标签设计要能归因 |

### G. 执行与性能护栏（间接影响准确率）

| 手段 | 具体做法 | 成本 | 收益 | 优先级 |
|---|---|---|---|---|
| **G1 结果上限与截断提示** | 超过 N 行明确提示“结果已截断”，并给汇总值 | 低 | 中高 | **P0** |
| **G2 缓存与相似问题复用** | 高频问题缓存；相似问题复用模板 | 中 | 中（时延+成本） | **P2** |
| **G3 限流/超时/资源组** | 防止拖垮生产库 | 中 | 中 | **P0** |

## 四、建议的 90 天落地路线

**第 0–30 天：建基线和护栏**
1. 抽 200–500 条真实问题做人工归因，形成错误分布基线。
2. 核心 3–5 个业务域做元数据增强 + Join 路径 + 业务规则。
3. 上线 AST 校验、权限注入、Dry Run、结果截断提示。
4. 建 300 条黄金评测集（含单表、多表、时间、歧义、权限）。
5. 做“理解回显 + 一键修正”交互。

**第 31–60 天：语义层 + 召回**
1. 核心指标进语义层，生产走“NL→语义查询→SQL”。
2. 上业务域路由 + 表级召回 + 字段级 Schema Linking 初版。
3. 建同义词表和枚举值字典。
4. 全链路日志 + 每周 Badcase 归因。

**第 61–90 天：复杂问题与闭环**
1. Few-shot RAG 冷启动（人工构造 100–200 条高质量样本）。
2. 有限次自修复 + 结果 Sanity Check + 置信度分级。
3. 回归门禁 + 灰度发布。
4. 多轮上下文和下钻。

## 五、几个必须避免的反模式

1. **一上来就让 LLM 对全库自由写 SQL**：Schema 太多、口径失控、错误不可归因。
2. **只调 Prompt，不建语义层和元数据**：Demo 准，上线崩。
3. **没有评测集就上线**：无法判断版本变好还是变坏。
4. **无限 self-correction**：会把正确答案改错，成本和时延都失控；**限 1–2 次、带错误信息、保留 diff**。
5. **把权限交给 Prompt**：必须在语义层和执行层双重校验。
6. **只看 SQL 可执行率，不看结果正确率**：SQL 能跑不代表答对。
7. **Few-shot 堆数量不控质量**：错误示例会带偏模型。
8. **忽略时间口径和去重**：这两类错误最隐蔽、最容易被业务发现。
9. **澄清太频繁**：用户会烦；要按置信度和风险分级。

## 六、参考量化目标（按业务调整）

| 指标 | 参考目标 |
|---|---|
| SQL 可执行率 | ≥ 98% |
| 单表简单问题结果准确率 | ≥ 90–95% |
| 多表/指标类问题结果准确率 | ≥ 75–85% |
| 核心指标口径一致率 | ≥ 95% |
| 低置信度澄清覆盖率 | ≥ 90% |
| 首次回答解决率 | ≥ 70% |
| Badcase 闭环时长 | ≤ 1 周 |
| P95 响应时延 | < 5–10s（缓存命中可更低） |

**一句话总结：**  
NL2SQL 准确率 = **语义资产质量 × 上下文召回质量 × 生成约束强度 × 校验护栏密度 × 交互兜底能力 × 评测迭代速度**。P0 阶段先把“元数据 + 核心域语义层 + 表召回 + AST 校验 + 权限注入 + 理解回显 + 评测集”做扎实，比换更大模型更有效。

### 4. 语义层（架构核心）

| 项 | 内容 |

| MVP | 成熟 |
|---|---|
| 单模型 + 强结构化 Prompt + JSON Schema 输出；失败重试 1 次 | 模型路由（简单问题小模型、复杂多表强模型）；多候选 + 执行一致性投票（仅高价值问题）；领域微调或 SQLCoder 兜底；私有化部署满足数据不出域 |
| **取舍**：先保证“输出可解析”，再谈模型效果 | **取舍**：成本/时延成为一等指标，路由与缓存决定单位经济模型 |

> 自修复必须限次（1–2 次）、带错误信息、保留 diff，禁止无限重试。

### 6. 校验与执行层

| 项 | 内容 |
|---|---|
| 职责 | SQL 静态校验、权限注入、Dry Run、查询网关、限流超时、多源连接 |
| 候选 | SQL 解析 sqlglot / Apache Calcite / JSqlParser；查询引擎 Trino / Presto / Spark SQL / DuckDB（中小数据量加速）；连接 JDBC / Airbyte / SeaTunnel；限流 Sentinel / Redis 令牌桶；队列 Celery / Temporal |

| MVP | 成熟 |
|---|---|

| **取舍**：不建网关，用连接池+超时先撑住 | **取舍**：查询网关是稳定性和成本的生命线，必须独立服务化 |

## 三、MVP 参考组合 vs 成熟参考组合

| 层 | MVP（0–3 个月，单体部署） | 成熟（12 个月+，K8s 微服务） |
|---|---|---|
| 接入 | React + AntD + ECharts，单 Web | 多端 + IM 卡片 + 门户嵌入 |
| 编排 | FastAPI + 确定性流水线 + Redis | 自研图编排 + Temporal 异步 |
| 检索 | pgvector + 关键词 + 规则 | Milvus/Qdrant + ES 混合 + Rerank 服务 |
| 语义 | YAML/DB 配置 + 模板编译 | 独立语义服务 + DSL AST + 权限编译 |
| 生成 | 单模型 + JSON Schema + LiteLLM | 多模型路由 + 多候选 + 私有化推理 |
| 执行 | 只读从库 + sqlglot + 超时 | Trino 查询网关 + 资源组 + 缓存 + 熔断 |
| 可视化 | 规则推荐 + 引用式摘要 | 意图推荐 + 归因算法 + 下钻 |
| 数据 | PG + pgvector + MinIO + 简易日志表 | DataHub + OpenLineage + Langfuse + 评测平台 |
| 安全 | SSO + 行级过滤 + 只读账号 | OPA 策略中心 + 脱敏 + 全审计 |

**MVP 部署形态：** 模块化单体（一个 FastAPI 服务 + PG + Redis + pgvector + 前端），按层划分 Python 包边界，不拆服务。
**成熟形态：** 语义服务、检索服务、查询网关、编排服务、洞察服务独立部署，通过内部 API/消息解耦。

## 四、架构演进的关键取舍

| 维度 | MVP 取舍 | 成熟取舍 | 演进触发条件 |
|---|---|---|---|
| 语义层 | 配置驱动、覆盖核心域 | 独立服务、全量指标、多产品复用 | 指标数 > 200 或接入第二个产品 |
| 查询执行 | 直连只读库 | 查询网关 + Trino 联邦 | 数据源 > 3 个 或 出现拖库事故 |
| 检索 | 单向量库 | 混合检索 + 精排 | 召回 Recall@5 < 85% |
| 编排 | 确定性流水线 | 图编排 + 异步任务 | 归因/多步分析成为主场景 |
| 模型 | 单模型 | 路由 + 多候选 | 月度 LLM 成本超过阈值 |
| 元数据 | 脚本采集 | 平台集成 | 表数 > 500 或 口径变更频繁 |
| 部署 | 单体 | 微服务 | 团队 > 10 人 或 单服务发布阻塞 |

**三条硬原则：**
1. **契约先行**：先定语义查询 DSL、工具调用接口、结构化输出 Schema，再选框架，避免被框架绑架。
2. **先护栏后智能**：AST 校验、权限注入、结果上限、Dry Run 必须在扩场景之前上线。
3. **模块化单体优先**：MVP 用包边界隔离各层，别上微服务；等出现真实的独立扩缩容/发布需求再拆。

**四个反模式：**
- 让 LLM 对全库自由写 SQL 作为默认路径；
- 核心链路深度绑定 LangChain/Dify，升级即重构；
- 没有评测和轨迹日志就扩业务域；
- 过早引入 Trino、DataHub、微服务，团队 5 人撑不起运维成本。
