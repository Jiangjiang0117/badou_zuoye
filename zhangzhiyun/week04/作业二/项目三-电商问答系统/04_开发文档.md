## 二、数据管线(对应"数据准备 → 知识库")

**原始数据**:ModelScope `E_commerce_Customer_Service` 的 `dev_clean_v2.jsonl`(16,205 条,ChatML 格式)。

**清洗规则**(`data.py::clean_records`,逐条说明):

| 规则 | 理由 |
|---|---|
| 仅保留 user+assistant 单轮对 | 数据为客服问答形态 |
| 用户问题去空白后长度 ≥ 4 | 过滤"哦""对的"等无信息量寒暄 |
| 客服答案去空白后长度 ≥ 2 | 过滤纯语气词回复 |
| 问题全数字/过短且无中文 | 过滤订单号等无效输入 |
| 按 (问题,答案) 去重 | 避免冗余索引 |
| 固定种子 42 随机抽取上限 8000 条 | 控制索引体积与构建耗时,便于复现 |

> 清洗后得到 `data/kb.json`,每条约:`{"id", "question", "answer", "topic?"}`。

**为什么清洗很重要**:真实客服语料含大量"好的哦""嗯嗯"等寒暄对,直接建索引会污染召回。
清洗本身就是一个可写进简历的工程动作。

## 三、检索层(BM25 + jieba,默认;TF-IDF 保留为可选)

### 3.1 分词:`tokenize()` 的混合策略

```python
def tokenize(text):
    words = [w for w in jieba.cut(text) if w.strip()]      # ① jieba 词,保留单字
    words = [w for w in words if w not in stopwords]        # ② 停用词过滤
    if not words: words = [text]                            # ③ 空分词兜底
    if len(text) >= 2:
        words += [text[i:i+2] for i in range(len(text)-1)]  # ④ char 2-gram 追加
    return words
```

**为什么混合(实测 4 种策略对比后选定)**:
- 纯 jieba 丢单字:短句(客服语料)单字敏感词被丢,退化明显;
- 纯 bigram:抓不住"退货/退款"等词级组合;
- **jieba 词(保留单字)+ char 2-gram**:词级捕捉语义组合,bigram 兜底脏口语/错字——最优。
- 实测:自检 0.94,换说法 R@1=0.136(优于其他 3 种)。

### 3.2 索引构建与持久化

- `Retriever().build(items)`:按 `RETRIEVER_METHOD` 分派,`bm25` 用 `rank_bm25.BM25Okapi`,`tfidf` 走旧 char n-gram 实现;
- 序列化到 `data/index.pkl`,**带 method 标记**;加载时 method 与配置不匹配会报错提示重新建索引(`build_index.py`);
- BM25 与 TF-IDF **分数量纲不同**(BM25 绝对分可到十几,余弦相似度在 0~1),`query()` 按方法自动选默认阈值(`BM25_MIN_SCORE=0.5` vs `MIN_SCORE=0.12`)。

### 3.3 查询

`Retriever.query(text, top_k, min_score)` → 按分数降序的命中列表 `[{id, question, answer, score}]`。
低于阈值即停止(视为无证据)。

## 四、生成层(双模型 RAG + 降级链)

**统一封装**:`RAGGenerator` 是单路 OpenAI 兼容封装(Deepseek 与 Qwen 各一个实例):

```
POST {base}/chat/completions
headers: Authorization: Bearer {api_key}
payload: {"model", "messages": [system, user], "temperature": 0.3}
```

- **system prompt**:专业电商客服,只用参考知识作答,证据不足回复"暂无相关信息",口语化简洁;
- **user prompt** = `参考知识:{Top-K 证据} 用户问题:{问题}`。

**双模型路由 `RouterGenerator`**:

| provider | 行为 |
|---|---|
| `deepseek` | 只走云端 |
| `qwen` | 只走本地 Qwen(Ollama) |
| `auto`(默认) | Deepseek 优先 → 失败切 Qwen → 都失败抛异常 → service 降级检索直答 |

**在线探测**:Qwen 的 `available` 探测 `/v1/models`(Ollama 在线探测缓存 30s);Deepseek 的 `available` 看是否配了 Key。

**三层降级链**(service 层):
```
LLM 可用 + 有证据 → RAG 生成(记录 provider)
  └─ 生成抛异常(双模型均失败/网络/超时) → 检索直答(source=retrieval)
无证据 → NO_ANSWER(source=none)
```

## 五、Web 交互页面(Flask + 原生 HTML)

- **`web_app.py`**:`GET /` 渲染聊天页;`POST /api/ask` 处理问答(支持前端指定 provider);`GET /api/health` 返回服务状态(检索方式 / provider / DS / Qwen 在线 / 知识库条数);
- **`templates/index.html`**:单文件零外部资源——顶部状态条(20s 自动刷新 health)、模式下拉(自动/仅DS/仅Qwen)、消息气泡、证据折叠展示;
- **实现细节**:`/api/ask` 用 `copy(svc)` 临时副本改 provider,避免污染全局状态(并发/串扰)。
- 页面问答的一轮请求带 `provider` 字段,服务端按需路由,不改全局配置。

## 六、实测指标(固定种子 42,可复现,`eval_retrieval.py`)

| 指标 | TF-IDF(char n-gram,旧) | **BM25+jieba(现)** |
|---|---|---|
| 原始问答对 | 16,205 条 | 16,205 条 |
| 清洗后知识库 | 8,000 条 | 8,000 条 |
| 链路自检(Top-1 精确命中) | 0.9500 | **0.9600** |
| 换说法召回 Recall@1 | 0.1200 | **0.1360** |
| 换说法召回 Recall@5 | 0.3280 | 0.2960 |
| 索引构建耗时 | ~0.2s | ~1.1s |

**评测口径**(先定义清楚再测,避免"留出条目的原问题查询永远命中不到"的坑):

| 口径 | 做法 | 含义 |
|---|---|---|
| ① 链路自检 | 随机取 300 条(仍在索引),其问题作 query,看 Top-1 是否命中自身 | 验证"建索引/查询"管线正确 |
| ② 换说法召回 | 把"答案相同"的条目视为同一知识;对答案 ≥8 字且 ≥2 种问法的组,留出一条问法(不入索引)作 query | 检索器对"换种说法"的泛化能力 |

> 数字偏保守是词法检索的固有瓶颈(无同义词/语义信息),"换种说法"跨越词面就召不回;
> 这正是 `03` 决策文档里"升级向量检索"路线图的依据。

## 七、双模型链路实测(2026-08 本机验证)

| 场景 | 结果 |
|---|---|
| `LLM_PROVIDER=deepseek` | provider=deepseek,~2s 出答案 |
| `LLM_PROVIDER=qwen`(本地 Ollama) | provider=qwen,首次 47s(含加载入显存),后续秒级 |
| `auto` + DS 正常 | provider=deepseek |
| `auto` + DS 坏 Key 模拟 | 自动切 qwen 兜底,1.9s |
| 双模型均不可用 | 降级检索直答,主链路不中断 |
| Web 页面 /api/health | ds_available=True / qwen_available=True |

**Ollama 部署要点(实际踩坑)**:
- 安装器从 GitHub 下载多次超时中断 → 用**断点续传脚本**(`curl -C -` + 重试直到完整 1564.6MB)解决;
- `ollama pull` 子进程 stdout 是**二进制进度条**,直接按 GBK 读会崩(`UnicodeDecodeError`);
  - 解法:输出重定向到日志文件,不读管道;同时避免**管道缓冲 64KB 被进度刷满造成死锁**(子进程阻塞在写 stdout);
- Windows 需先杀干净残留 `ollama.exe` 再重启 serve,避免多实例抢占;
- 模型拉取后可复用已下载 blob(断点续传),`/api/tags` 确认注册 `qwen2.5:7b`。

**Flask 端口踩坑**:多进程同时监听 5000 时请求被路由到旧进程(无 Key 状态)→ 表现成"DS 不可用"。解法:杀干净旧进程再起单个服务。

## 九、难点与多次尝试(如实记录)

| 难点 | 表现 | 解法 |
|---|---|---|
| 中文分词 | 初版环境未装 jieba | 先字符 n-gram TF-IDF 起步;后装 jieba 升级 BM25 混合分词 |
| 纯词级分词退化 | jieba 丢单字后短句召回差 | 4 种分词策略实测,选"保留单字 + bigram 兜底"混合 |
| BM25 分数量纲不同 | 旧 MIN_SCORE=0.12 对 BM25 失效 | 独立 BM25_MIN_SCORE=0.5,query 按方法选阈值 |
| 索引 method 错配 | 磁盘 TF-IDF 索引被 BM25 配置加载 | save/load 带 method 标记,不匹配提示重建 |
| 客服语料大量寒暄对 | "哦→嗯嗯"污染召回 | 长度/去重/种子采样三级清洗 |
| Ollama pull 崩溃 | stdout GBK 解码 UnicodeDecodeError | 输出重定向到文件;避开管道缓冲死锁 |
| Ollama 下载超时 | GitHub 大文件多次中断 | curl -C - 断点续传 + 重试至完整 |
| 多进程端口冲突 | 5000 被旧进程占用,health 显示 DS 不可用 | 杀干净旧进程再起单个服务 |
| provider 状态污染 | ask 端点修改全局 svc.llm.provider | copy 临时副本,不改全局 |
| 评测口径踩坑 | "留出条目的原问题查询"永远命中不到(Recall=0) | 改为双口径:链路自检 + 答案分组换说法召回 |

## 十、生产化演进路径(方案 B → 方案 A)

1. 检索升级:BM25 → **向量检索**(bge/gte 中文 embedding,ModelScope 可直接下载),混合检索(BM25+向量 RRF 融合);
2. NLU 接入:复用**项目1 的 BERT 意图识别**(`项目1-大模型意图识别(依图实现)`),把咨询分流到物流/退货/促销等意图管道;
3. 图谱升级:实体/关系抽取(BiLSTM+CRF、R-BERT)→ Neo4j 存储 → 跨实体推理(方案 A);
4. 评测升级:接入 **Multi-CPR-ecom**(电商检索基准,corpus+qrels),用标准口径测 MRR/Recall;
5. 交互升级:多轮对话 + 会话记忆 + 流式输出(SSE)。
