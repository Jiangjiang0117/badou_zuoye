## 3. 被否决的方案与原因

> 以下方案在评审/预演中被明确讨论过，但未进入定稿。列出以避免后续重复争论。

| # | 被否决方案 | 来源/背景 | 否决理由 | 替代方案 |
|---|---|---|---|---|
| 1 | 用 30/30 作为 MVP 验收证据 | 原 `01`/`05` 把 30/30 当基线 | few-shot 与 gold 重合；排序后比集合；仅算 recall；不能证明泛化 | 30/30 降为 demo 基线；holdout 29/30 |
| 2 | 试点 3 人 ×15 次、总样本 ≥50 | 原 G5 写法 | 3×15=45，样本量自相矛盾；两周回访样本不足 | 4–5 人 ×≥15，总样本 ≥60 |
| 3 | 把“国家归属”算作第 6 个指标 | 原技术文档 `metrics.yaml` 有 5 指标 + 1 维度 | 国家归属是维度规则，不是可独立求和的指标；混算会导致口径错误 | 5 指标 + `country_attribution` 维度规则 |
| 4 | 把 `avg_spend_per_customer` 叫“客单价” | 原 `03` §4.4 标签 | 公式是人均消费（ARPU），不是订单均价（AOV）；Chinook 发票粒度不足以稳定定义 AOV | 改名“人均消费”；客单价询问返回 `E7005` |
| 5 | 金额单位用 CNY | 原 `03` 指标 YAML | Chinook 数据是 USD；按 CNY 标注会误导 | 数据金额 USD；模型成本 CNY，分开口径 |
| 6 | 汇总自由生成、温度 0.2 | 原 `summarizer.py`/功能文档 | 无法保证数字来自结果集；0.2 增加措辞漂移 | claims + grounding + 温度 0 + 模板回退 |
| 7 | LLM 单次 90 s + 3 次重试 + 3 次改写，同时要求 20 s deadline | 原 `llm.py` 与项目指标 | 二者不可能同时成立；deadline 只是 UI 计时器 | 20 s 共享预算；单次 ≤min(剩余,15 s)；调用上限 6 |
| 8 | 30 条 holdout 上“每个 tag ≥90%” | 原评测门槛 | 10 tag ×3 条，90% 实际要求 3/3；统计不可判定 | 6 核心 tag ×5 条，≥4/5；报告 Wilson 区间 |
| 9 | 列名 100% 精确匹配 | 原验收讨论 | 中文列名/别名/大小写差异会造成假失败 | 必需列存在 + 大小写不敏感；额外列默认允许 |
| 10 | 反馈写 JSONL | 存储方案讨论 | 赞/踩会重复提交，需要更新；JSONL 只适合追加 | 反馈 SQLite；Trace JSONL |
| 11 | MVP 抽 `LLMGateway`/`DataSource` 完整接口 | 原技术文档以 B 架构写 A | 单库单模型下没有第二实现，抽象空转；挤占 6 周 | 只抽 `TraceStore`/`SemanticCatalog` |
| 12 | 试点用户用本地 CLI | 试点方案讨论 | 3–5 人装环境、配 Key 不可控；无法观察真实使用 | 受控笔记本上的共享 Streamlit，无登录，样例数据 |
| 13 | 把“数据刷新到 2014+”升为 Must | 数据边界讨论 | 无证据表明用户需要；会增加 2–3 人日与数据治理 | 接受 `data_until=2013-12-22`；需要时再升级 |
| 14 | MVP 做多轮与完整澄清 | 原 V1 能力被部分文档提前 | 需要上下文选择、指代消解、口径继承；失败面大 | MVP 单轮；V1 多轮/完整澄清 |
| 15 | 支持因果/预测问题 | 产品期望 | ChatBI 证据只来自结果集；因果/预测没有数据支撑 | 明确拒答 `E1007`，给趋势替代 |
| 16 | V1 就做 JWT + RBAC | 原 `02`/`03` 写法 | MVP/V1 无外部用户；鉴权不提升“答得对” | V2 再做；MVP 逻辑角色 |
| 17 | 换 PostgreSQL / ORM | 技术选型讨论 | 单库 3,500 行、只读；迁移无收益 | SQLite + 原生 SQL |
| 18 | 自主 Agent 循环（多步规划） | 架构备选 | 不可观测、不可预算、难评测；6 周无法验收 | 固定七步流水线 |
| 19 | MVP 接 Prometheus/Grafana | 可观测性讨论 | 单机低并发，无告警样本；增加部署成本 | JSONL + 汇总脚本；看板 V1 |
| 20 | 微服务/HTTP API | 架构演进讨论 | 无外部集成与并发需求；超出 6 周 | 单进程；V1/V2 按触发条件演进 |
| 21 | MVP 做查询计划门槛/熔断/限流 | 原技术文档 P0 | Chinook 数据量小，收益低；熔断需要多请求统计 | 20 s deadline + 10 s SQL + 100 行；其余 V1 |
| 22 | 把表/列权限只做在 UI 隐藏 | 权限讨论 | 隐藏不等于阻止；SQL 仍可访问 | 请求级表白名单 + 校验层拦截；V2 再做真实 RBAC |

## 4. 采纳方式说明

1. **“采纳”不等于原文照搬。** 多数结论经过量化或改写，例如“6 个指标”改为“5 指标 + 1 维度”，“低置信继续”改为“有默认则标注、无默认则 `E1005`”。
2. **P0 优先于功能数量。** 评审中提出的多轮、图表、导出、权限均未进入 MVP；MVP 只保留可信闭环与治理。
3. **每个关键数字只有一个来源。** 能力计数、优先级、评测题数、目标值、工期、人日均在 01 定义，02/03 引用而不另立一套。
4. **否决项保留理由。** 若后续要重启某个方案（如多轮、RBAC、DataSource），需先回答本表对应否决理由是否已失效。
5. **ADR 是决策记录，不是设计说明。** 每条 ADR 包含决策、背景、备选、理由、影响；实现细节仍在 02/03 正文。
