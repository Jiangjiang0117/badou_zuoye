# ChatBI / Data Agent 项目需要具备哪些核心能力？

如果你要开发一个真正能够落地的 ChatBI / Data Agent 项目，而不是简单地把大模型接到数据库上，我建议从 自然语言理解、数据语义建模、SQL 生成与执行、数据分析、Agent 编排、权限治理、评估运维 七个方面设计能力体系。

最重要的认知是：

ChatBI 解决的是“用自然语言查询和分析数据”；Data Agent 解决的是“理解业务目标，自主规划并完成数据任务”。 两者有较大重叠，但 Data Agent 通常具有更强的任务规划、工具调用、多步分析和执行能力。

## 一、先理解 ChatBI 和 Data Agent 的能力边界

ChatBI：对话式商业智能

用户提问 → 理解指标 → 生成 SQL → 查询数据库 → 返回数据、图表和解释。

例如：“分析今年各地区的销售额，并与去年同期比较。”

Data Agent：自主数据分析代理

理解目标 → 制定计划 → 调用数据工具 → 分析结果 → 验证结论 → 交付报告或执行获授权的操作。

例如：“找出本季度利润下降的主要原因，验证原因，并给出改善建议。”

建议采用渐进式路线：先实现可靠的 ChatBI，再逐步增加 Data Agent 的任务规划、复杂分析和自动化执行能力。

1\. 自然语言理解与业务意图识别

- 识别用户问题、查询目标、时间范围、过滤条件和分组维度。
- 识别业务指标，例如营收、毛利率、活跃用户数、转化率。
- 处理模糊问题、上下文追问和指代消解。
- 缺少关键条件时，主动询问用户，而不是猜测。

关键产物：结构化查询意图（Query Intent）。

2\. 数据资产理解与语义层（最关键的基础能力之一）

- 自动或半自动识别数据库、表、字段、主外键和表之间的关系。
- 建立业务术语、指标口径、维度和计算公式。
- 处理同义词、字段别名、时间粒度和组织层级。
- 理解数据血缘、数据质量及指标依赖关系。

关键产物：可被模型理解和检索的业务语义模型。

3\. Text-to-SQL 与查询执行

- 根据问题、语义模型和数据库 Schema 生成 SQL。
- 支持复杂 JOIN、子查询、CTE、窗口函数和时间比较。
- 进行 SQL 语法检查、权限检查、静态风险检查和执行计划分析。
- 处理 SQL 执行失败、字段错误、空结果和查询超时。

关键产物：经过校验、受权限约束的可执行查询。

4\. 数据分析与洞察生成

- 自动选择合适的统计方法和图表。
- 支持同比、环比、趋势、排名、分布和异常检测。
- 对指标变化进行分解，分析不同维度的贡献。
- 区分数据事实、相关性、推测和经过验证的原因。

关键产物：数据结果、可追溯的结论和分析报告。

5\. Agent 规划与工具编排

- 将复杂任务拆解为多个可执行子任务。
- 选择数据库、指标查询、Python 分析、图表和报表等工具。
- 根据中间结果决定下一步操作。
- 支持失败重试、结果验证、任务状态追踪和人工审批。

关键产物：可控、可观测、可恢复的任务执行流程。

6\. 安全、权限与治理

- 用户身份认证、数据源授权和行列级数据权限。
- 防止越权查询、敏感信息泄露和危险 SQL 执行。
- 保护数据库凭据，限制查询成本、数据量和执行时间。
- 记录问题、生成 SQL、执行记录、数据来源和操作审计。

关键产物：符合企业安全要求的数据访问和审计机制。

7\. 评估、监控与持续优化

- 评估问题理解、SQL 正确性、结果准确性和业务口径一致性。
- 监控成功率、延迟、Token 成本、数据库负载和用户反馈。
- 构建标准测试集，覆盖常见问题、复杂 JOIN、歧义和权限边界。
- 分析失败案例，持续改进语义层、提示词、模型和检索策略。

关键产物：可量化、可回归测试的质量保障体系。

## 三、推荐的整体技术架构

建议将系统拆成七层，避免把所有能力都塞进一个 Agent。

交互层

Chat 对话 · BI 仪表盘 · 图表 · 报告 · 数据导出

意图理解与任务规划层

问题分类 · 上下文管理 · 任务拆解 · 澄清问题

Agent 编排层

Query Agent

查询数据

Analysis Agent

分析数据

Visualization Agent

生成图表

Report Agent

生成报告

语义层与数据工具层

指标定义 · Schema 检索 · SQL 生成 · SQL 校验 · 查询执行 · Python 分析

数据源层

MySQL · PostgreSQL · 数据仓库 · 湖仓 · API · Excel / CSV

横向贯穿的企业治理体系

认证授权 · 数据脱敏 · 审计 · 评估 · 监控 · 成本控制

这个架构的关键在于：Agent 负责理解和规划，语义层负责统一业务含义，确定性的程序负责权限检查、SQL 验证和受控执行。不要让大模型直接拥有不受限制的数据库访问权。企业级 Text-to-SQL 实践也强调语义约束与多层独立安全控制。

## 四、项目真正需要掌握的技术栈

| 技术领域        | 需要掌握的内容                         | 优先级 |
| ----------- | ------------------------------- | --- |
| 大模型         | Prompt、结构化输出、工具调用、模型路由          | P0  |
| Text-to-SQL | Schema Linking、SQL 生成、SQL 校验与纠错 | P0  |
| 数据工程        | SQL、数据仓库、元数据、指标体系               | P0  |
| 语义层         | 指标定义、实体关系、维度、业务术语映射             | P0  |
| 后端工程        | Python、FastAPI、异步任务、API 设计      | P0  |
| 数据安全        | RBAC、行列级权限、只读连接、审计              | P0  |
| Agent 工程    | 状态管理、工具调用、任务编排、失败恢复             | P1  |
| 数据分析        | Pandas、统计分析、趋势与异常检测             | P1  |
| RAG 与检索     | 向量检索、关键词检索、混合召回、重排              | P1  |
| 可视化         | ECharts、图表配置、BI Dashboard       | P1  |
| 评估与运维       | 测试集、准确率、Tracing、延迟与成本监控         | P0  |

P0 表示首个可靠版本必须考虑；P1 表示可以在基础版本稳定后完善。

## 五、从 MVP 到企业级，应该怎样建设？

## 01

第一阶段：ChatBI MVP

先跑通闭环

- 接入一个关系型数据库。
- 选择一组业务表，建立基础 Schema 元数据。
- 支持自然语言转 SQL、只读查询和结果解释。
- 支持基础表格、柱状图、折线图。
- 建立一套标准问题和正确 SQL 的测试集。

## 02

第二阶段：可靠的企业 ChatBI

- 建立业务指标语义层。
- 支持复杂 JOIN、同比环比、上下文追问。
- 增加 SQL 自动校验、受控纠错和查询成本限制。
- 实现用户权限隔离、数据脱敏和操作审计。
- 建立离线评估与线上质量监控。

## 03

第三阶段：Data Agent

- 支持多步骤任务规划和动态工具选择。
- 联合 SQL、Python、统计分析和外部数据 API。
- 自动定位异常、分解指标变化、验证候选原因。
- 生成包含证据、图表和建议的分析报告。
- 支持定时分析、任务恢复和人工审批。

## 04

第四阶段：规模化与平台化

- 多数据库、多业务域和多租户。
- 统一数据目录、语义模型和工具注册机制。
- 模型路由、缓存、并发控制和成本优化。
- 版本管理、灰度发布、回归测试与全链路可观测性。

## 六、如何衡量这个项目是否真正做好了？

不能只看“能不能生成 SQL”，而要评估完整业务链路。

| 评估维度   | 建议指标                   |
| ------ | ---------------------- |
| 问题理解   | 意图识别准确率、澄清问题有效率        |
| SQL 能力 | SQL 执行成功率、结果正确率        |
| 业务语义   | 指标口径一致率、JOIN 关系正确率     |
| 分析能力   | 结论有数据支撑的比例、分析任务完成率     |
| 用户体验   | 首次回答成功率、P95 响应延迟       |
| 安全治理   | 越权访问拦截率、审计覆盖率          |
| 运营成本   | 单次任务成本、平均查询次数、Token 消耗 |

尤其需要区分 SQL 执行成功率和业务结果正确率：SQL 可以正常运行，但由于错误的 JOIN、重复计数、时间口径或指标定义，结果仍然可能完全错误。

## 七、如果你现在要开始开发，我最建议先做这五件事

1. 选定一个具体业务场景，例如销售分析、运营分析或财务分析。
2. 选定一个数据库和一组代表性数据表。
3. 定义业务指标、维度、关联关系和权限规则。
4. 实现“问题理解 → 语义检索 → SQL 生成 → 校验执行 → 结果解释”的完整闭环。
5. 用真实业务问题构建测试集，再决定哪些场景值得升级为多步 Data Agent。

一个很重要的架构决策：不要一开始就开发多 Agent 系统。 先把单 Agent + 受控工具 + 语义层做可靠，再根据复杂任务的真实需求引入专用 Agent，通常更容易交付、测试和维护。
