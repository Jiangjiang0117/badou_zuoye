# ChatBI / Data Agent 企业内部系统：可开发技术设计方案

针对“团队项目、企业内部使用、数据来源为关系型数据库或数据仓库”的场景，我建议采用一套 以语义层为核心、以受控 Text-to-SQL 为查询引擎、以工作流编排为 Agent 执行机制 的架构。

第一版不建议一开始就构建多个自主协作的 Agent。先把数据查询、业务口径、权限控制和结果验证做可靠，再扩展复杂分析能力。

本方案将覆盖：整体架构、模块划分、数据库设计、API 接口、核心工作流、项目排期、测试方案与验收标准。

## 一、项目目标与范围

第一版必须交付

- 自然语言查询业务数据。
- 识别业务指标、时间范围、过滤条件和分组维度。
- 生成、校验、执行只读 SQL。
- 展示数据表格、常用图表和自然语言解释。
- 支持连续追问、查询历史和错误恢复。
- 提供用户权限、数据访问控制、审计日志和质量评估。

第二阶段扩展

- 多步骤数据分析和异常归因。
- SQL 与 Python 统计分析工具协同。
- 自动生成分析报告。
- 定时任务、订阅和告警。
- 多数据源、多业务域和语义模型版本管理。

### 设计原则

1. 业务指标有唯一口径：营收、利润、活跃用户等核心指标优先使用经审核的语义定义。
2. 大模型不直接掌握数据库权限：数据库访问统一经过后端查询服务。
3. 所有结果可追溯：保留问题、指标定义版本、SQL、执行状态、数据时间范围和结果依据。
4. 复杂任务可分步验证：Agent 的每一步都必须有明确输入、输出和执行边界。
5. 模型可替换、业务逻辑不依赖模型：模型调用统一封装，避免将系统绑死在某个供应商上。

## 三、技术选型：建议的第一版技术栈

采用成熟、易于团队维护的模块化单体架构。模块之间通过明确接口解耦，暂时不必拆成大量微服务。

| 层级       | 推荐技术                                                          | 选型理由               |
| -------- | ------------------------------------------------------------- | ------------------ |
| 前端       | React + TypeScript                                            | 对话、表格、图表及任务状态展示    |
| 图表       | Apache ECharts                                                | 支持常见 BI 图表与交互      |
| 后端       | Python + FastAPI + Pydantic                                   | 适合大模型、数据分析和 API 开发 |
| 主应用数据库   | PostgreSQL                                                    | 保存元数据、会话、任务和审计记录   |
| 缓存       | Redis                                                         | 缓存语义检索、短期会话状态及任务状态 |
| 数据访问     | SQLAlchemy + 数据库专用驱动                                          | 统一连接管理、参数绑定与事务控制   |
| SQL 解析   | SQLGlot 等 SQL AST 工具                                          | 解析 SQL、识别语句类型、校验方言 |
| Agent 编排 | 显式状态机；复杂流程可用 LangGraph                                        | 控制多步任务、重试、暂停和恢复    |
| 模型接入     | 统一 LLM Gateway 接口                                             | 方便切换不同模型供应商        |
| 异步任务     | 初期 FastAPI BackgroundTasks 仅用于轻量任务；长任务采用 Celery + Redis 或同类队列 | 避免长时间分析阻塞请求        |
| 监控       | OpenTelemetry + Prometheus + Grafana                          | 追踪请求、耗时、错误和资源使用    |
| 部署       | Docker + CI/CD                                                | 环境一致、便于测试与发布       |

以上是推荐方案，不是必须全部采用的组件。第一版可以不部署独立向量数据库：业务术语、指标定义和表字段可以先用 PostgreSQL 全文检索、别名匹配与结构化查询实现；当语义检索确实需要时，再增加向量检索。

```
chatbi/

│   ├── llm/                 # 模型适配、结构化输出
│   ├── semantic/            # 指标、维度、Schema 检索
│   ├── sql/                 # SQL 生成、AST 校验、方言适配
│   ├── connectors/          # 数据库连接器
```

建议遵循一个原则：`orchestrator` 只负责组织流程，`semantic` 负责业务含义，`sql` 负责查询安全与正确性，`connectors` 负责数据访问。不要让每个模块都自行调用模型或直接连接业务数据库。

## 四、核心模块的开发职责

| 模块                    | 输入                | 输出            | 必须满足的约束               |
| --------------------- | ----------------- | ------------- | --------------------- |
| Intent Parser         | 用户问题、会话上下文        | 结构化查询意图       | 不确定的业务口径必须能表达为待澄清状态   |
| Semantic Service      | 指标、维度、问题关键词       | 指标定义、表关系、字段信息 | 只返回当前用户有权使用的语义对象      |
| Query Planner         | 查询意图、语义模型         | 查询计划          | 明确粒度、时间范围、JOIN 和聚合方式  |
| SQL Generator         | 查询计划、方言、Schema    | SQL 候选及参数     | 不允许自行发明未知字段或指标定义      |
| SQL Validator         | SQL AST、用户权限、查询策略 | 通过或拒绝         | 默认只允许 SELECT / 受控只读查询 |
| Query Executor        | 校验后的 SQL、绑定参数     | 列名、结果行、执行统计   | 使用只读身份、超时和资源限制        |
| Result Validator      | 查询结果、查询意图         | 结果检查报告        | 检查空结果、异常值、粒度及数据完整性    |
| Insight Generator     | 结果、统计分析、指标定义      | 文字结论与证据       | 结论必须能对应到实际数据          |
| Visualization Builder | 结果结构、图表意图         | 图表 JSON 配置    | 输出受控配置，不能执行任意代码       |
| Audit Service         | 用户、动作、请求与结果元数据    | 审计事件          | 记录访问和执行决策，不泄露凭据       |

这些模块可以先放在同一个后端进程中，通过 Python 接口调用。等性能、团队协作或独立部署需求出现后，再拆分服务。

## 五、数据库设计：应用元数据库

建议至少建立以下 10 类核心表。这里存储的是 ChatBI 应用自己的管理数据，不是用户的业务事实表。

| 表名                      | 用途      | 关键字段                                                                        |
| ----------------------- | ------- | --------------------------------------------------------------------------- |
| `data_sources`          | 数据源注册   | `id`, `name`, `dialect`, `secret_ref`, `status`                             |
| `schema_objects`        | 表与字段元数据 | `id`, `source_id`, `object_name`, `object_type`, `metadata_json`            |
| `semantic_models`       | 业务语义模型  | `id`, `name`, `version`, `status`                                           |
| `metric_definitions`    | 指标定义    | `id`, `model_id`, `name`, `expression`, `grain`, `owner`                    |
| `dimension_definitions` | 维度定义    | `id`, `model_id`, `name`, `column_ref`, `data_type`                         |
| `join_relationships`    | 表关联关系   | `id`, `model_id`, `left_ref`, `right_ref`, `join_type`                      |
| `conversations`         | 对话会话    | `id`, `user_id`, `created_at`, `status`                                     |
| `messages`              | 用户与系统消息 | `id`, `conversation_id`, `role`, `content`, `created_at`                    |
| `analysis_runs`         | 查询或分析任务 | `id`, `conversation_id`, `status`, `plan_json`, `started_at`, `finished_at` |
| `audit_events`          | 安全与操作审计 | `id`, `user_id`, `action`, `resource_ref`, `decision`, `created_at`         |

此外，正式企业系统还需要用户与角色映射、数据源授权、行列权限策略、模型版本发布记录，以及查询执行记录等表或等价的数据结构。

### 关键数据建模要求

- 指标不能只有名称，还必须有计算表达式、统计粒度、适用时间字段、过滤条件、单位、所有者和版本。
- JOIN 关系应记录连接键、关系基数及允许使用的关联路径，防止多对多 JOIN 造成重复计数。
- `secret_ref` 只保存密钥管理系统中的引用，不直接保存明文数据库密码。
- `analysis_runs` 记录任务状态和引用，结果集较大时应存储在受控结果存储中，而不是无限制地塞入 JSON 字段。
- 会话、任务、消息和审计表需要索引、保留周期及访问权限策略。

例如，营收指标可以定义为：

```
{
  "name": "net_revenue",
  "display_name": "净营收",
  "expression": "SUM(order_items.net_amount)",
  "base_model": "sales",
  "grain": ["order_date", "region_id"],
  "time_column": "order_date",
  "unit": "CNY",
  "definition_version": 3,
  "status": "published"
}
```

这只是一个示例定义。真实项目中，`net_amount` 是否已经扣除退款、折扣、税费，以及订单取消如何处理，都必须由业务负责人明确后再发布。

## 六、端到端数据流：从一句话到可信的分析结果

以用户提问为例：

> 分析 2026 年各地区净营收的同比变化，并找出下降最明显的地区。

系统不能只生成一条 SQL，而应当分成两个层次：先完成可靠的 ChatBI 查询，再在数据结果之上执行多步骤分析。

### 01

接收问题

验证用户身份，加载会话和数据访问权限

### 02

解析意图

提取指标 net_revenue、地区维度、2026 年时间范围和同比要求

### 03

检索语义

找到净营收定义、订单日期、地区关系、去年同期口径

### 04

生成查询计划

确定按地区汇总、同比计算、退款规则和时间过滤

### 05

生成 SQL

依据数据库方言生成候选查询及绑定参数

### 06

校验与执行

检查权限、表字段、JOIN、查询成本；使用只读账号执行

### 07

验证结果

检查数据覆盖、分母为零、缺失地区和异常结果

### 08

分析与呈现

排序下降幅度，生成表格、图表和带证据的文字结论

### 一个必须明确的业务规则：同比变化怎么算？

通常需要同时计算：

- 本期净营收。
- 去年同期净营收。
- 同比变化金额。
- 同比变化率。

同比变化率的常见定义是：

\\[ \text{同比变化率}= \frac{\text{本期净营收}-\text{去年同期净营收}} {\text{去年同期净营收}}\times100\\% \\]

但如果去年同期营收为零或缺失，不能直接将同比变化率当作普通数值；应按业务约定标记为不可计算、无基数或数据缺失。

对于“下降最明显”，也要明确排序依据是下降金额还是下降百分比。如果两种口径可能产生不同答案，系统应同时展示两者，或在执行前向用户澄清。

## 七、SQL 生成与执行：这是系统最需要重点测试的链路

建议将查询链路设计成一个独立的、可测试的流水线：

用户问题 + 已授权的语义对象

结构化查询计划

SQL 候选生成

SQL AST 解析与方言校验

权限、JOIN 与资源策略校验

EXPLAIN / 成本检查（适用时）

受控只读执行

结果与口径验证

### SQL 安全规则

1. 使用 SQL AST 解析器识别查询结构，不能只靠正则表达式判断 SQL 是否安全。
2. 对第一版默认只开放单条只读查询，拒绝 DDL、DML、存储过程调用和多语句执行。
3. 使用独立的只读数据库账户，并在数据库端配置最小权限；应用层校验不能替代数据库权限。
4. 采用绑定参数处理用户提供的值，避免将输入直接拼接进 SQL。
5. 通过允许访问的表、字段、函数和关联路径进行校验；禁止访问系统目录及未授权对象。
6. 配置查询超时、最大返回行数、并发限制和数据库资源上限。对大查询使用适当的扫描量或执行成本策略。
7. 行级权限应在 SQL 编译或受控数据访问层中落实，并使用数据库侧权限作为额外防线。
8. SQL 自动纠错后必须重新走完整校验流程；不能因为模型说“已修复”就直接执行。

特别注意：`LIMIT 1000` 不代表查询成本一定低。 聚合、全表扫描和大规模 JOIN 仍可能消耗大量资源，需要结合执行计划、数据库资源限制和数据分区策略进行控制。

### SQL 自动纠错策略

可以设置有限的纠错流程：

- 第一次：生成 SQL 并执行静态检查。
- 如果出现可恢复的语法错误或未知字段错误：提取经过脱敏的错误信息和相关 Schema，最多重新生成 1～2 次。
- 如果出现权限拒绝、危险查询或超出资源预算：立即停止，不得通过重试绕过限制。
- 如果结果与用户意图不匹配：回到查询计划阶段重新评估，而不是无限重写 SQL。

每次重试都应记录原因、模型版本、SQL 哈希和执行状态，便于后续回归测试。

## 八、API 接口设计

第一版建议使用 REST API；长任务通过任务 ID 轮询或 SSE 推送状态。接口响应应有稳定的 Pydantic Schema，便于前端和自动化测试使用。

| 方法   | 接口                                     | 作用        |
| ---- | -------------------------------------- | --------- |
| POST | `/api/v1/conversations`                | 创建会话      |
| POST | `/api/v1/conversations/{id}/messages`  | 发送问题      |
| GET  | `/api/v1/conversations/{id}/messages`  | 获取对话历史    |
| GET  | `/api/v1/runs/{id}`                    | 获取任务状态    |
| GET  | `/api/v1/runs/{id}/result`             | 获取数据与分析结果 |
| POST | `/api/v1/runs/{id}/feedback`           | 提交回答反馈    |
| GET  | `/api/v1/semantic/models`              | 查询可用语义模型  |
| POST | `/api/v1/semantic/models`              | 创建语义模型草稿  |
| POST | `/api/v1/semantic/models/{id}/publish` | 审核后发布语义模型 |
| GET  | `/api/v1/admin/audit-events`           | 管理员查看审计事件 |

### 核心请求示例

```
{
  "conversation_id": "conv_123",
  "message": "分析2026年各地区净营收的同比变化",
  "options": {
    "include_sql": true,
    "include_chart": true
  }
}
```

服务端不能仅凭请求中的 `conversation_id` 判定用户有权访问会话，必须重新校验当前登录用户的身份和资源授权。

### 核心响应示例

```
{
  "run_id": "run_456",
  "status": "completed",
  "result": {
    "columns": [
      {"name": "region", "type": "string"},
      {"name": "net_revenue", "type": "number"},
      {"name": "yoy_rate", "type": "number"}
    ],
    "rows": [
      {
        "region": "华东",
        "net_revenue": 1250000,
        "yoy_rate": -0.08
      }
    ],
    "chart": {
      "type": "bar",
      "x": "region",
      "y": "yoy_rate"
    }
  },
  "metadata": {
    "semantic_model_version": 3,
    "row_count": 1
  }
}
```

这里的地区、营收和同比数值仅用于说明响应结构，不代表实际业务数据。真实响应还应包含必要的单位、时间范围、数据新鲜度、结果截断标记和可追溯的执行记录。

建议将 SQL 放在独立的 `query_metadata` 字段中，并且只有当前用户被授权查看 SQL 时才返回；对敏感参数进行脱敏。

## 九、Data Agent 工作流：如何从查询升级为多步骤分析

第一版可以将 ChatBI 实现为固定流程，Data Agent 再使用显式状态机处理动态步骤。

任务目标

分析营收下降的主要原因

任务规划器

拆解为趋势查询、地区分解、产品分解和验证任务

查询工具

SQL 查询与汇总

分析工具

分解、排序、统计

验证工具

对比数据与口径

报告工具

生成证据与结论

结果汇总与验证

不支持的推断应明确标记，不允许编造原因

例如，营收下降可以按地区、产品、客户、销量和单价逐层分解。但系统必须先确认数据是否包含这些维度；如果缺少销量或价格字段，就不能声称已经完成销量与价格的归因。

### 每个 Agent 工具的统一契约

每个工具应定义：

- 输入 Schema 和输出 Schema。
- 所需权限和可访问的数据范围。
- 超时、重试次数和资源预算。
- 成功、失败、拒绝和部分成功等状态。
- 是否有副作用，以及是否需要人工审批。

第一版的所有数据工具都应为只读。涉及修改业务系统、发送通知或触发其他有副作用的操作时，应使用单独授权与审批流程。

## 十、测试体系：如何证明项目真正可用？

建议在项目开始时就建立评估集，而不是开发完成后才补测试。

### 1. 测试分层

| 测试层级     | 测试内容                   | 示例                |
| -------- | ---------------------- | ----------------- |
| 单元测试     | 指标解析、SQL AST、权限策略、结果格式 | 是否正确识别聚合函数        |
| 集成测试     | 模型、语义服务、数据库执行器协同       | 真实生成 SQL 并验证结果    |
| 业务验收测试   | 指标口径与业务答案              | 营收是否正确排除取消订单      |
| 安全测试     | 越权、注入、危险 SQL、数据泄露      | 是否能查询未授权部门的数据     |
| Agent 测试 | 规划、工具选择、重试、恢复          | 第一个查询无结果时能否合理调整计划 |
| 性能测试     | 并发、延迟、资源消耗             | 多用户同时查询时是否稳定      |
| 回归测试     | 模型、Prompt、语义模型升级       | 升级后原有问题是否仍然正确     |

### 2. 第一版验收指标

以下是建议的初始目标，需要结合真实数据量、模型选择和业务风险调整，不应当视为行业统一标准。

标准问题结果正确率

# ≥ 90%

固定测试集，按业务结果判定

只读 SQL 策略拦截

# 100%

预设危险语句与越权用例

标准查询执行成功率

# ≥ 95%

排除外部依赖故障后统计

审计覆盖率

# 100%

所有受控数据访问均有记录

验收时应区分 SQL 执行成功率、查询结果正确率、指标口径一致率和任务完成率，不能用其中一个指标代替其他指标。

对于行列级权限，建议按每一种权限规则设计正向和反向测试。测试不仅要证明合法用户能访问授权数据，还要证明越权查询在任何工具调用路径上都会被拒绝。

## 十一、项目实施排期：8 周完成首个可验收版本

以下按一个 4～6 人的跨职能团队估算，前提是数据库可访问、业务负责人能及时确认指标口径、企业模型服务已可使用或能够按时开通。数据治理基础薄弱时，需要增加时间。

第 1 周

需求梳理与数据盘点

确定业务场景、指标口径、数据库表、权限矩阵和验收测试集。

交付物：需求说明、数据目录、指标清单

第 2 周

工程骨架与安全基础

完成前后端工程、登录鉴权、元数据库、数据源连接器和只读账户。

交付物：可登录、可连接数据库的基础系统

第 3 周

语义层与 Text-to-SQL

完成指标定义、Schema 检索、结构化查询计划和 SQL 生成。

交付物：可生成候选 SQL 的查询链路

第 4 周

SQL 校验与结果执行

实现 AST 校验、权限策略、参数绑定、超时控制和查询结果结构化。

交付物：安全可控的端到端查询闭环

第 5 周

对话与图表

实现会话上下文、表格、图表、SQL 查看和查询历史。

交付物：可供业务人员试用的 ChatBI

第 6 周

质量与安全加固

完善异常恢复、指标一致性验证、权限测试、审计和回归评估。

交付物：可量化评估的候选发布版本

第 7 周

Data Agent 工作流

实现多步分析、工具编排、任务状态管理和报告生成。

交付物：限定场景的分析 Agent

第 8 周

试点与验收

开展业务验收、并发测试、缺陷修复、部署和运维交接。

交付物：企业内部试点版本

建议第一阶段以第 6 周的 ChatBI 可靠版本作为主要里程碑。第 7～8 周的 Agent 能力可根据基础版本的质量和团队资源调整，避免为了赶进度而牺牲数据正确性与权限安全。

## 十二、团队分工与最终交付物

对于 4～6 人团队，可以采用以下分工：

| 角色                    | 主要责任                 |
| --------------------- | -------------------- |
| 技术负责人 / 架构师           | 技术方案、模块契约、代码评审、安全边界  |
| 后端 / Agent 工程师（1～2 人） | API、编排、模型网关、任务管理     |
| 数据工程师                 | 元数据、语义模型、SQL 执行、业务指标 |
| 前端工程师                 | 对话界面、表格、图表、任务状态      |
| 测试 / 质量工程师            | 标准测试集、自动化测试、权限和性能测试  |

角色可以兼任，尤其是早期团队；但业务指标口径的确认必须由懂业务的数据负责人或指标所有者参与，不能完全交给开发人员或大模型决定。

最终至少交付以下内容：

- 可部署的前后端代码与环境配置。
- 数据源连接器与只读访问策略。
- 语义模型与业务指标管理机制。
- SQL 生成、校验、执行和结果验证模块。
- ChatBI 对话、图表及查询历史功能。
- Agent 工作流及工具输入输出契约。
- 数据权限、审计和密钥管理方案。
- 自动化测试集、业务验收报告和性能报告。
- 部署、回滚、故障排查及运维文档。

我的最终建议： 先把“受控 SQL 查询 + 统一业务语义 + 可验证的查询结果”作为系统核心。Agent 的价值不是多调用几次大模型，而是能将复杂数据问题拆成一系列可执行、可验证、可追溯的步骤。

如果按照这个方案推进，下一步最有价值的工作是把它进一步拆成可直接交给开发团队的详细设计包：模块接口定义、PostgreSQL 建表 SQL、Pydantic 数据模型、API 契约、状态机定义以及逐模块开发任务清单。
